# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**What's on Radar** (repo/working dir `event-radar`; the product name in every user-facing string, the FastAPI app title, and the README is "What's on Radar") is an AI-powered event discovery platform for Tallinn, Estonia. It ingests events from multiple sources, deduplicates and classifies them via LLM, then delivers a personalized "Daily 5" curated feed per user. MVP complete plus a post-MVP self-service organizer portal (see Organizer Event Submission); soft launch pending E2E QA.

```
  ├── Routers: /auth  /admin  /onboarding  /events  /explore  /feed  /feedback  /public  /users/me  /contact  /email  /webhooks  /organizer/auth  /organizer/events
  └── APScheduler (embedded, kept alive by a cron-job.org ping of /internal/tick every 10 min)
      ├── Weekly Sun 03:00: sync_fienta_organizers (auto-discover new organizers, retire long-dead ones)
      ├── Weekly Sun 03:30: cleanup_stale_data (data retention — prunes satellite tables, never events)
      ├── Hourly:   ingest_all_enabled
      ├── 6-hourly: dedup_pass + classify_pending (each "drained" — re-run on a 15-min retry, up to LLM_BACKLOG_MAX_DRAIN_PASSES passes, until its backlog clears) + publish_pending + geocode_pending
      ├── Daily 04:30: refetch_event_details (reconcile venue/price/coords from source detail pages, before the 06:00 feed build)
      ├── Daily 06:00: build_daily_feeds
      └── Daily 07:00: send_daily_digests (one hour after feeds are built)
        ↓
Neon Postgres (eu-central-1, free tier, pgvector available for v1.1)
        ↓
LLM Router: Groq (primary) → Cerebras → Mistral (fallback chain)
```

**No Celery/Redis** — embedded APScheduler suffices for a single-process MVP.

## Deployment

Production runs on three free-tier services:

- **Backend — Render web service** (`render.yaml`): `rootDir: backend`, health check `/health`, `plan: free`. Migrations run at boot — `startCommand` chains `alembic upgrade head && uvicorn ...` because Render's `preDeployCommand` is paid-only. Secrets (`DATABASE_URL` in asyncpg form `postgresql+asyncpg://...?ssl=require`, `ADMIN_PASSWORD`, `INTERNAL_TOKEN`, LLM/Resend keys, `CORS_ORIGINS`, `FRONTEND_URL`, `BACKEND_URL` — the API's own absolute URL, `https://event-radar-api.onrender.com`, needed by the digest email's RFC 8058 `List-Unsubscribe` header since mail providers call it server-side and can't go through the SPA's relative `/api` proxy, `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` — organizer image upload, see Organizer Event Submission) are `sync: false` env vars; `SECRET_KEY` is auto-generated. There is **no Render cron service** — Render cron jobs are paid.
- **Frontend — Vercel** (`frontend/vercel.json`): static Vite build. The API client calls a relative `/api` prefix, so a rewrite proxies `/api/:path*` to the Render URL **and strips the `/api` prefix** (backend routes have no `/api` prefix — mirrors the dev Vite proxy); a second rewrite is the SPA fallback to `index.html`. Same-origin proxying also sidesteps CORS. `vercel.json` also carries a `headers` block applying security headers to the served HTML document (`X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, HSTS, and a **tailored** CSP) — the backend's `default-src 'none'` CSP only covers JSON API responses, not the app document. The SPA CSP is `default-src 'self'` with `img-src 'self' https: data:` (event images come from arbitrary source hosts), `style-src 'self' 'unsafe-inline'` (React inline styles), and `script-src`/`connect-src`/`font-src` all `'self'` — the latter works because fonts are **self-hosted** (`@fontsource/dm-sans` + `@fontsource/cormorant-garamond`, imported in `src/main.tsx`, bundled into the build; the former Google Fonts `<link>` is gone) and Vercel Analytics/Speed Insights are served first-party under the same-origin `/_vercel/` path (excluded from the SPA-fallback rewrite). If any of those move off-origin (a CDN font host, an off-platform analytics beacon), the CSP must be widened to match or they break silently. `App.tsx` also mounts Vercel `<Analytics>` + `<SpeedInsights>`; analytics URLs pass through `maskAnalyticsUrl()` (`frontend/src/utils.ts`) first, which strips query/hash and collapses `/events/:id` to `/events/[id]` so no event id or token reaches the analytics vendor. Any new dynamic route added to the app must be masked the same way.
- **Keepalive — cron-job.org**: Render free tier sleeps after 15 min idle, which would halt APScheduler. A cron-job.org job pings `https://event-radar-api.onrender.com/internal/tick` every 10 minutes with the `X-Internal-Token` header (same value as Render's `INTERNAL_TOKEN`). GitHub Actions cron was tried and dropped — its schedule is too imprecise for a keepalive cadence.

## Data Flow

1. **Ingestion** — 3 live source types plus one stored-but-not-yet-ingested path: Fienta API (~10 seed Tallinn organizer IDs, with a full stale/retire lifecycle — see Organizer Lifecycle below; for each *new* event — not yet in `event_sources` — the adapter concurrently fetches the detail page and parses its schema.org JSON-LD into `raw["_detail"]`, capped at `DETAIL_FETCH_CONCURRENCY`; `normalize()` (`app/ingestion/sources/fienta.py`) merges listing + detail per a fixed per-field authority table — deterministic, no LLM: `venue_name` listing-wins/detail-fallback; `venue_address` prefers whichever side carries a 5-digit postal code, else listing-wins/detail-fills-when-empty; `lat`/`lng` come only from detail JSON-LD, bbox-gated to Estonia (`coords_in_estonia`); `price_min`/`price_max` use the listing's deterministic `parse_price_from_string` (`app/ingestion/pricing.py`) as the baseline, overridden per-bound by a present detail offer price — absent `_detail` degrades cleanly to listing-only behavior, same as before this merge existed), HTML listing scrapers (Piletilevi, KUMU, Estonia Concert Hall) sharing `HtmlListingAdapter` (`app/ingestion/sources/html_base.py`; adapters in `piletilevi.py`, `kumu.py`, `estonia_concert_hall.py`), and organizer self-submission (adapter-less `user_submission` source, `app/routers/organizer_events.py` — see Organizer Event Submission below) — an organizer's `POST /organizer/events` inserts directly via the shared `insert_normalized_event()` helper rather than through a polling adapter. Per-source full-res image normalization happens at ingest: `full_res_wp_image()` strips the WordPress `-WxH` thumbnail suffix for concert.ee and kumu.ekm.ee; `full_res_piletilevi_image()` rewrites the `/height=N/` path segment for piletilevi.ee (`full_res_wp_image` in `html_base.py`, `full_res_piletilevi_image` in `piletilevi.py`; constants in `app/ingestion/selectors.py`). Telliskivi, Kultuurikatel, and Fotografiska are disabled (`enabled=False`) in `app/ingestion/registry.py` (Telliskivi's data was unfixably mis-dated; Kultuurikatel/Fotografiska pending a rewrite onto the shared base). Eventbrite was never added (its API was deprecated for non-partners before integration). **Skip set per run:** adapters call `ingest_skip_ids()` (`app/ingestion/adapter.py`) rather than `existing_external_ids()` alone — it unions the already-stored `event_sources` external_ids with every `raw_events` external_id fetched within `INGEST_REJECT_RECHECK_DAYS` (7), so an event that was fetched but rejected by `normalize()` isn't re-fetched and re-stored on every hourly run; it gets one recheck a week. **Newsletter inbound (stored, not yet ingested):** `app/routers/webhooks.py` accepts a Resend Inbound email webhook and can parse it via `app/llm/newsletter_extractor.py`, but `app/ingestion/registry.py` registers the newsletter source with no adapter (excluded from `ADAPTER_REGISTRY`), so its `raw_events` rows never become `events`; `NEWSLETTER_SENDER_ALLOWED_DOMAINS` is also empty by default, so extraction is skipped for every sender until that allowlist is populated. Treat this as a landed-but-dormant path, not a live ingestion source, until an adapter is wired up.
2. **Deduplication** — Two-stage: rule-based pre-filter (SQL time-window self-join + Python fuzzy title/venue, `app/dedup/rules.py`), then LLM tiebreaker only on the surviving candidate pairs (keeps token usage low, `app/dedup/llm_tiebreaker.py`). The scheduled job (`jobs.dedup_pass`) runs `run_dedup_pass_llm`, which degrades to the rule-only `run_dedup_pass` when no LLM provider key is configured. Near-exact title matches (`title_ratio >= TITLE_RATIO_VENUE_BYPASS_THRESHOLD`, 85) bypass the venue check on the LLM path, so cross-source dupes with differently-spelled venues (incl. cross-language spellings) still reach the LLM tiebreaker. Before the tiebreaker, `apply_same_day_title_unions` deterministically collapses events that share a normalized title **and** Tallinn calendar day **and** a compatible venue (`_venue_compatible`, unknown = compatible) into one group with no LLM call — folding timed-entry / session ticket slots (e.g. a museum's many same-day slots) into one canonical event; these pairs are skipped on the LLM path (`same_group`). Multi-day series are intentionally **not** collapsed across days (one canonical event per day). The representative (canonical `dedup_group_id == id`) of each group is chosen by sorting on `_representative_status_rank` first (an already-published/classified member is pinned ahead of a merely-drafted one), then `_event_quality_rank` (price/address/coords/description) as the tiebreak, then `min(event_id)` as the final fallback — not simply the lowest id.
3. **Classification** — LLM assigns fixed 14-category / 10-vibe taxonomy, quality score 0–1, 3-bullet "why go?" text, an `is_explicit` flag (NSFW layer 2, see below), a `non_event` flag (OR-merged into `Event.is_non_event` — non-event filter layer 2, see below), an `in_target_city` flag (location signal, inverted and stored as `Event.is_out_of_area`; feeds the publish gate), `price_min`/`price_max`/`currency` parsed from the ingested `price_hint` (capped at `PRICE_HINT_MAX_CHARS`), and a `has_free_tier` flag (a paid event that also has a free/companion/member tier — OR-merged into `Event.has_free_tier`, never un-set once true). Fixed taxonomy prevents ontology drift. **Ingest-set prices are authoritative:** `classify_event` only writes LLM-derived prices when `event.price_min is None` — a source that parses price deterministically at ingest (Fienta, see below) keeps its values; the LLM, which sees "not stated" for those events, must not clobber them. On the LLM-priced path (`price_min` was None), `_reconcile_event_price_fields` first deterministically **widens** — never shrinks — the LLM's envelope to cover any literal €/EUR amount found in `price_hint` (`eur_price_bounds_from_text` over `strip_fee_amounts`), catching a tier the model under-reported; gated to a None/EUR currency so a correctly-detected non-EUR price isn't polluted by an incidental €-looking match. `has_free_tier` only makes sense alongside a paid price (`price_min > 0`); the classifier zeroes a model-hallucinated `has_free_tier` on an otherwise-free event. Events already flagged `is_explicit`/`is_non_event` by the layer-1 keyword prefilters skip the LLM call but **still advance to `classified`**, so a flagged dedup-group representative doesn't strand its cluster in `draft`. Before each batch, `classify_pending` bulk-cancels (`draft` → `cancelled`) drafts that have already ended — they can never pass the publish gate, so an LLM slot on them is wasted — skipping any dedup-canonical representative that still has a live sibling (`_no_live_dedup_sibling_clause`), which would otherwise orphan that sibling outside `canonical_event_filter()` until the next dedup pass.
4. **Ranking** — `score = 0.45·persona_affinity + 0.20·recency_boost + 0.20·feedback_signal + 0.10·quality_score + 0.05·locality_bonus`
5. **Daily 5 builder** — runs 06:00 Europe/Tallinn; scores events in next 14 days; MMR-lite diversity, capped at `DAILY_5_MAX_PER_CATEGORY` (2) per category; writes to `daily_feeds`. **Series cooldown:** before scoring, a candidate whose `event_series_key` (`normalized_title` + lowercased venue, `app/routers/utils.py`) appeared in that user's feeds within the last `DAILY5_SERIES_COOLDOWN_DAYS` (3) days is routed into a separate `cooled_scored` pool instead of the primary candidate pool — so a recurring multi-day series (one canonical event per day) isn't re-picked night after night *while the primary pool is healthy*. The window is bulk-fetched (one feed query + one event query, no per-user N+1); suppression never touches `user_event_scores`. **Backfill tiers:** `_select_with_backfill()` (`app/ranking/score.py`) guarantees `n=5` events when the primary pool is thin by relaxing constraints tier by tier: tier 1 is `_mmr_pick` on the primary (fresh) pool at the true `DAILY_5_MAX_PER_CATEGORY` cap; tiers 2–3 are `_greedy_fill` at the relaxed `DAILY_5_BACKFILL_MAX_PER_CATEGORY` (3) cap — tier 2 over the fresh pool again, tier 3 over the cooled pool; tiers 4–5 repeat that fresh-then-cooled order with the per-category cap dropped entirely (`max_per_category=None`) as a last resort. Diversity is preferred over freshness in the relaxed tiers; each pool is sorted by score once up front and the sorted list reused across every tier that consumes it (fresh feeds tiers 1/2/4, cooled feeds tiers 3/5). So a series-cooled event *can* reappear the next day, and a thin candidate pool can legitimately yield 3+ events in one category — the 2-per-category cap and series cooldown are both soft under scarcity, not hard guarantees.
6. **Publish gate** — `app/publish.py::publish_pending()` promotes `classified` events to `published` once `quality_score >= PUBLISH_MIN_QUALITY_SCORE` (0.4), `is_explicit` is false, `is_non_event` is false (non-event filter layer 3, see below), `is_out_of_area` is false (LLM `in_target_city` signal, set in `classify_event`), the event hasn't ended yet (`event_not_ended_filter()`, `app/routers/utils.py` — live until `ends_at`, or `starts_at` when `ends_at` is unset; a past `starts_at` with a future `ends_at` stays live, covering multi-day runs and ongoing exhibitions), `title_orig` is present (NSFW layer 3), and — defense-in-depth — any present `lat`/`lng` fall within `TALLINN_REGION_BBOX` (coords-less events still pass; only an out-of-bbox coord blocks). Events failing the gate stay `classified`; the returned summary breaks down reject counts by reason (`fail_quality`/`fail_explicit`/`fail_non_event`/`fail_out_of_area`/`fail_ended`/`fail_no_title`/`fail_coords_bbox`, non-exclusive). The same `event_not_ended_filter()` also gates the Daily 5 feed builder's candidate window (`app/ranking/score.py`). Runs every 6h via `publish_pending_job`.
7. **Geocoding backfill** — `app/ingestion/geocode/__init__.py::geocode_pending()` (sub-passes in `geocode/nominatim.py`, `geocode/venue_extract.py`, `geocode/sibling_copy.py`) fills `lat`/`lng` for events that have `venue_address` but no coordinates, via Nominatim (1 req/sec, `GEOCODE_REQUEST_DELAY_SECONDS`, capped at `GEOCODE_MAX_PER_RUN` events per run; an address that fails is not retried for `GEOCODE_RETRY_INTERVAL_DAYS`, tracked via `geocode_attempted_at`). It runs four sub-passes in order: (0) `_self_heal_out_of_bbox_coords()` — NULLs any stored coord outside `TALLINN_REGION_BBOX`, run **first** so a bad donor coord can't propagate into the sibling copy or the Nominatim cache in the same run. (a) `extract_address_from_venue_name()` — LLM pass that mines street addresses glued into `venue_name` into `venue_address` so events with no prior address become geocodable; uses a Python prefilter (digit / comma / direction keyword / length) to limit LLM calls to suspect names only; caches decisions in `llm_calls` by content hash; caps fresh calls at `VENUE_EXTRACT_MAX_FRESH_LLM_CALLS_PER_RUN`. (b) `copy_venue_from_siblings()` — copies `venue_address`+`lat`/`lng` onto address-less events from a geocoded sibling. Matching is on the **canonical** venue name (`canonical_venue_name` strips a `(parens)` suffix and any glued-on address tail after the first comma) via symmetric `fuzz.ratio >= VENUE_SIBLING_RATIO_THRESHOLD` (90; canonicalization makes intended matches near-exact — a symmetric ratio avoids `token_set_ratio` scoring a short comma-split core 100 against an unrelated longer donor), so `"Sõltumatu Tantsu Lava"` matches a `"Sõltumatu Tantsu Lava (STL)"` donor. The ambiguity guard keys on distinct **coordinates** — one physical venue legitimately carries several address spellings at one coord, so only a name spanning >1 distinct coord is skipped + logged; a single coord copies a representative (most-common, lex tie-broken) `venue_address`. Non-physical venue names (`NON_GEOCODABLE_VENUE_NAMES`, e.g. `"online"`) are skipped on both target and donor sides. (c) the Nominatim pass itself (`geocode/nominatim.py`), seeded from a normalized-query→coords cache built over **all** already-geocoded events, so spelling/format variants of a known address cost no HTTP call. Runs every 6h via `geocode_pending_job`.
8. **Detail-refetch sync** — `app/ingestion/refetch.py::refetch_event_details()` re-fetches every future event's detail page (`event.url`), parses the schema.org JSON-LD `Event` block via the shared `app/ingestion/jsonld.py` module (`extract_jsonld_event_location`/`_offers`/`_text`), and reconciles stored `venue_name`/`venue_address`/`lat`/`lng`/price fields against the source — updating on a differing value, filling when empty, never clobbering a good stored value with nothing. It also backfills missing locale keys of `title_localized`/`description_localized` from the page's locale variants (`_backfill_localized_text`), gated per-locale (not per-column) and merged into the existing dict so a partially-filled column self-heals; a stored title that looks like site-level homepage boilerplate (`_is_suspect_locale_title`) counts as missing and is re-fetched. Generic JSON-LD parsing, not Fienta-specific (no-ops on pages without an `Event` block; the same module also backs Fienta's own detail-page parsing at ingest); HTML-listing sources already fetch detail at ingest so Fienta is the main beneficiary today. Candidates exclude organizer submissions on two independent signals (`_select_candidates`): `Event.submitted_by_organizer_id IS NULL`, plus a `NOT EXISTS` check that the event isn't linked to a `user_submission`-kind source — the latter guards against a future insert that forgets to set `submitted_by_organizer_id`, since that's the same `source.kind` signal `insert_normalized_event()` keys its host-pin decision off. An organizer owns their row and edits it directly via PATCH, and never fetching an organizer-controlled url is what lets the submit path drop the SSRF host allowlist (see Organizer Event Submission and Security Hardening → External-URL sanitization). Throttled like geocoding (`REFETCH_REQUEST_DELAY_SECONDS`, capped at `REFETCH_MAX_PER_RUN`/run, re-checks an event only after `REFETCH_MIN_INTERVAL_DAYS`). A coord NULLed by a detail-driven address change is repaired by the next `geocode_pending` pass. Runs daily 04:30 Europe/Tallinn via `refetch_event_details_job`, before the 06:00 feed build.

## Read Paths (Daily 5 feed vs. Explore)

Four user-facing surfaces read `published` events — three authenticated, one public:

- **Daily 5 feed** (`GET /feed`, route `/`) — serves the pre-built `daily_feeds` snapshot (built 06:00, see Daily 5 builder).
- **Explore** (`GET /explore`, `app/routers/browse.py`, route `/explore`) — searchable/filterable/sortable discovery grid over all upcoming published events. Query params: `q` (keyword, capped at `BROWSE_QUERY_MAX_LEN` — `_keyword_filter` builds a `%...%` pattern against two trigram GIN indexes, so an unbounded string is cheap to send and expensive to scan), `category`/`vibe` (comma-separated slugs, validated against `VALID_CATEGORIES`/`VALID_VIBES`), `date_from`/`date_to`, `free`, `for_you` (default true), `sort` (`VALID_BROWSE_SORTS` = relevance/date/price/quality), `limit`/`offset` (`BROWSE_PAGE_SIZE`/`BROWSE_MAX_PAGE_SIZE`), `locale` (per-request override of the user's stored locale, via the shared `resolve_locale_param()`). **Two execution paths:** a pure-SQL path (`_browse_sql_path`) for the non-personalized `date`/`price`/`quality` sorts, and a Python-scored path (`_browse_scored_path`, reuses `ranking/score.py`) whenever `for_you` narrowing or `relevance` ranking is requested (persona affinity + feedback soft-filter aren't expressible as SQL `ORDER BY`). Authenticated (`get_current_user`), rate-limited `RATE_LIMIT_BROWSE`. Paginate any new list output via the same `limit`/`offset` + cap pattern.
- **Saved Events** (`GET /feedback/events`, `app/routers/feedback.py`, route `/saved`) — lists the current user's published events carrying a given preference `signal` (like/dislike/bookmark — restricted to `PREFERENCE_SIGNALS`, not the full `VALID_SIGNALS`, since passive view/click_external rows are multi-row per event), most-recently-signaled first. Shares the `public_event_filter()` + `select_events_with_classification()` + `serialize_event()` read stack with the other surfaces; paginated via `limit`/`offset` (`BROWSE_PAGE_SIZE`/`BROWSE_MAX_PAGE_SIZE`), rate-limited `RATE_LIMIT_FEEDBACK`. Powers the Saved Events page tabs (`routes/SavedEvents/`, infinite-query).
- **Landing showcase** (`GET /public/showcase`, `app/routers/browse.py`'s sibling `app/routers/public.py`, route `/` when signed out) — the only **unauthenticated** *list* read path (the single-event `GET /events/{id}` detail endpoint is also public — optional-auth, see Conventions): a fixed-size grid of `SHOWCASE_EVENT_COUNT` (6) top-quality published events happening this week (`SHOWCASE_WINDOW_DAYS`, widening to `SHOWCASE_FALLBACK_WINDOW_DAYS` on a thin week). Pure SQL, mirroring `_browse_sql_path`'s quality sort minus every user/persona/feedback concern — no PII, no personalization. Rate-limited `RATE_LIMIT_PUBLIC`. Reuses the same `public_event_filter()` + `select_events_with_classification()` + `serialize_event()` stack; keep it that way, and never add a user-scoped field to this response.

## Organizer Lifecycle (Fienta)

`settings.FIENTA_ORGANIZER_IDS`/`FIENTA_ORGANIZER_NAMES` (`app/config.py`) are a **bootstrap seed floor only** — used to populate `sources.config` on a fresh DB (`app/seeds.py::_upsert_fienta`). At runtime, `sources.config["organizer_ids"]` (DB) is the source of truth; `FientaAdapter.fetch_raw()` (`app/ingestion/sources/fienta.py`) reads only from there.

`app/ingestion/organizer_sync.py::sync_fienta_organizers()` runs weekly (Sun 03:00 Europe/Tallinn) and manages the full lifecycle:

1. **Detect** — each current organizer is probed; one returning 0 events is marked stale, recorded with a first-seen timestamp in `sources.config["stale_since"]` (JSONB, keyed by organizer id). A transient HTTP error neither flags nor clears staleness that run (avoids false stale/revival flips on a network blip).
2. **Skip at ingest** — `FientaAdapter.fetch_raw()` filters out any id in `sources.config["stale_organizer_ids"]` before the hourly poll, so a known-dead organizer stops burning API calls immediately. The weekly sync still re-probes every id in `organizer_ids` (including stale ones), so a revival is still detected.
3. **Revive** — an organizer that returns events again has its `stale_since` entry cleared (rejoins normal polling); one already retired can also rejoin via auto-discovery (below) if it resurfaces with enough events.
4. **Retire** — an organizer continuously stale for `STALE_ORGANIZER_RETIRE_DAYS` (30, `app/constants.py`) is dropped out of `organizer_ids` into `sources.config["retired_organizer_ids"]`. `app/seeds.py::_upsert_fienta` subtracts `retired_organizer_ids` from its seed union on every startup, so a retired **hardcoded** id is never resurrected.
5. **Discover** — a city-filtered scan (`FIENTA_CITY_FILTER`) auto-adds any organizer not already known with `>= ORGANIZER_MIN_EVENTS_FOR_AUTO_ADD` (3) Tallinn events, same as before this lifecycle existed.

`POST /admin/sync-organizers` triggers this synchronously; it is also stage 1 of `POST /admin/pipeline/run`.

## Organizer Event Submission (self-service)

**Naming note:** this is a distinct concept from "Organizer Lifecycle (Fienta)" above — a Fienta "organizer" there is a ticketing-source id being polled; an `Organizer` here (`app/models/models.py`) is its own account entity, a venue/promoter submitting events directly through a dedicated portal.

- **Auth** — a parallel track to the user magic-link/session stack (`app/routers/organizer_auth.py`, prefix `/organizer/auth`), with its own DB table (`organizers`, `organizer_magic_links`) and distinct signing salts (`AUTH_ORGANIZER_MAGIC_SALT`, `AUTH_ORGANIZER_SESSION_SALT`, `app/constants.py`) so an organizer token can never verify as a user token or vice versa, even though both use the same `URLSafeTimedSerializer(settings.SECRET_KEY)`. TTLs (`ORGANIZER_MAGIC_LINK_TTL_MINUTES`, `ORGANIZER_SESSION_TTL_DAYS`) mirror the user-facing defaults. `organizers.session_token_version` supports the same logout-all revocation pattern as `users.session_token_version`.
- **Submission** — `app/routers/organizer_events.py` (prefix `/organizer/events`) lets an authenticated organizer `POST` a new event (inserted on the adapter-less `user_submission` source via the shared `insert_normalized_event()` helper, then classified + published inline within the request instead of waiting for the next scheduled pass), `PATCH`/`DELETE` (soft-delete via cancel) their own events, `GET` their own submission list, and `POST /organizer/events/image` for a signed Cloudinary image upload (secrets: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `app/config.py` — log-only/`501` when unconfigured, like the contact-email Resend fallback; server-side signature so the API secret never reaches the SPA, gated by `IMAGE_UPLOAD_ALLOWED_MIME` (415) and `IMAGE_UPLOAD_MAX_BYTES` (413)). A per-organizer daily submission cap (`ORGANIZER_DAILY_SUBMISSION_CAP`, 20) and a separate per-organizer daily **image upload** cap (`ORGANIZER_DAILY_IMAGE_UPLOAD_CAP`, 20, tracked via the `organizer_image_uploads` table since an upload can happen before any submission) are both DB-backed anti-abuse ceilings, since the IP-keyed rate limiter can't enforce a per-account cap (an organizer can trivially exceed it across IPs); both are a count-then-insert with no row lock, so both are soft ceilings (concurrent requests from one organizer can overshoot slightly) rather than a hard guarantee. **Per-locale text:** `title`/`description`/`important_info` each take optional `_en`/`_ru` siblings; `_localized()` folds them (et = the base field) into the `*_localized` JSONB columns, dropping blank locales. **Organizer-chosen category:** an optional `category` (validated against `VALID_CATEGORIES` by a Pydantic `field_validator`, 422 otherwise) is *prepended* onto `EventClassification.categories` by `_apply_organizer_category()` after inline classification, so the organizer's pick leads and any LLM-derived categories follow; a bare classification row is created if the LLM call failed, so the pick is never silently dropped. Both `url` and `image_url` are scheme-checked only (`safe_external_url()`, not the host-pinned `safe_fetchable_url()`) — an organizer's own ticketing domain is never on `ALLOWED_SOURCE_HOSTS`, and these events are excluded from the daily refetch pass (see Data Flow §8), so `url` is never fetched server-side and needs no host pin.
- **Auto-publish + post-hoc review, gated on organizer trust** — a submitted/edited event is flagged `Event.needs_review` and goes live immediately if it clears the normal publish gate (see Publish gate above) **and** the submitting `Organizer.verified` is true; `submitted_by_organizer_id` (indexed) attributes it back to its organizer. A brand-new organizer defaults `verified=false`, so its first submission stays `classified`/`needs_review` — never auto-published — until an admin reviews it: this closes the hole where any address that can receive one magic-link email could otherwise push a plausible-looking event with an arbitrary link straight into every user's feed and inbox with no human in the loop. Admin review queue: `GET /admin/submissions` (paginated, excludes cancelled), `POST /admin/submissions/{event_id}/retract` (pulls a submission back out of `published`), `POST /admin/submissions/{event_id}/approve` (clears `needs_review`, flips the organizer to `verified`, and runs the publish gate — every subsequent submission from that organizer auto-publishes as before). `app/publish.py::publish_pending()` enforces the gate itself (excludes any `classified` event whose `submitted_by_organizer_id` resolves to an unverified organizer, NULL-safe for non-organizer events), not just the inline call in `submit_event` — so an unapproved submission can't slip through on the next scheduled `publish_pending` pass either.

## Data Retention & Cleanup

`app/cleanup.py::cleanup_stale_data()` runs weekly (Sun 03:30 Europe/Tallinn, right after organizer sync) and prunes aged rows from satellite/audit tables via a fixed set of bulk `DELETE`s (one per table, no N+1). **`events` rows are never deleted** — only satellite data (auth tokens, audit logs, raw payloads, old feed snapshots, cached scores, never-verified user/organizer account rows) — preserving event history and the `user_event_feedback` indirect-feedback signal indefinitely.

| Table | Retention window (`app/constants.py`) | Notes |
|---|---|---|
| `auth_magic_links` | `MAGIC_LINK_RETENTION_DAYS` (7) | sweeps both expired-unused and long-used rows |
| `organizer_magic_links` | `MAGIC_LINK_RETENTION_DAYS` (7) | mirrors `auth_magic_links` (organizer auth track) |
| `llm_calls` | `LLM_CALLS_RETENTION_DAYS` (90) | also the dedup/classification cache window — a content hash re-seen after 90 days costs one fresh LLM call instead of a cache hit |
| `raw_events` | `RAW_EVENTS_RETENTION_DAYS` (90) | a one-off forensic/backfill script that reads `raw_events.payload` cannot recover a row pruned past this window |
| `ingestion_runs` | `INGESTION_RUNS_RETENTION_DAYS` (90) | |
| `raw_inbound_emails` | `RAW_INBOUND_EMAILS_RETENTION_DAYS` (90) | |
| `daily_feeds` | `DAILY_FEEDS_RETENTION_DAYS` (30) | |
| `user_event_scores` | `USER_EVENT_SCORES_RETENTION_DAYS` (30) | keyed on the underlying event's end date via `event_not_ended_filter` (inverted, evaluated at the retention cutoff), not the score's own `computed_at` |
| `users` (unverified only) | `UNVERIFIED_ACCOUNT_RETENTION_DAYS` (30) | only `email_verified = false` rows with no unused, unexpired magic link — a row `_get_or_create_user` inserts on an unauthenticated `POST /auth/request-link` before the address is proven reachable |

`POST /admin/cleanup` triggers this on demand — like every other destructive admin/maintenance tool in this codebase, it **defaults to dry-run** (`?dry_run=false` to actually delete).

## Key Database Tables

- `users` — email (citext unique), email_verified (bool, set true on first successful magic-link verification — see Auth; gates `build_daily_feeds`/`send_daily_digests`), locale (et|en|ru), home_city, email_digest_opt_in (bool, gates the daily digest send), session_token_version (int, bumped to revoke all sessions — see Auth)
- `auth_magic_links` — token_hash (sha256), expires_at, used_at; one-use only
- `personas` — 9 static personas with JSONB affinity vectors; display names in et/en/ru
- `user_personas` — M2M join with a per-rank `weight`. Onboarding is a ranked 1–`PERSONA_MAX_SELECTABLE` (3) multi-pick; each pick's weight comes from `PERSONA_RANK_WEIGHTS` by position (1.0 / 0.4 / 0.2), first pick leads (`routers/onboarding.py`)
- `sources` — ingestion source registry
- `raw_events` — source payload as JSONB
- `event_sources` — M2M: links events to source + external_id; unique index on `(source_id, external_id)` enforces ingestion idempotency at the DB level (migration 0007)
- `events` — normalized: slug, title_orig, description_orig, important_info (ticket/access notes block scraped from HTML-listing sources), url, image_url, price_hint (raw price text from ingestion, fed to LLM classification), starts_at/ends_at, venue_name/venue_address, lat/lng (backfilled by the geocoding job when missing), price_min/price_max/currency (parsed from price_hint by classification), has_free_tier (paid event that also offers a free/companion/member tier; OR-merged, see Classification), status (draft→classified→published|cancelled — `published` is set by the publish gate, not directly by classification), is_explicit (NSFW filter flag), is_non_event (non-event filter flag: gift cards/merch/webinars; blocks the publish gate), is_out_of_area (LLM `in_target_city` signal; blocks the publish gate), detail_refetched_at/detail_refetch_count (bookkeeping for the daily detail-refetch sync), geocode_attempted_at (bookkeeping for the geocoding backfill), title_localized/description_localized/important_info_localized (JSONB `{locale: html}`, filled by per-locale page fetches at ingest, by the organizer submit/edit form's per-locale fields, and backfilled per-missing-locale by the daily detail-refetch pass — a source publishing one page with multiple languages concatenated in a single field is stored as-is, unsplit), dedup_group_id, created_at
- `event_classifications` — categories[], vibes[], quality_score, why_go_bullets[3], why_go_localized JSONB ({locale: [bullets]}), language_detected, model_used
- `user_event_feedback` — two signal classes: **preference** signals (like/dislike/bookmark, `PREFERENCE_SIGNALS`) are a current-state model — one row per (user, event), enforced by a partial unique index (migration 0019); POST `/feedback` upserts, DELETE `/feedback/{event_id}` removes. **Passive** signals (view/click_external, the rest of `VALID_SIGNALS`) stay append-only/multi-row (page-view + ticket-click analytics, not covered by the index). `GET /feedback/events?signal=` reads the preference rows (Saved Events page). Mixing the two under one upsert-by-(user,event) rule would let a ticket click overwrite a bookmark — keep them split.
- `user_event_scores` — cached ranking score per (user, event); unique constraint. Cache is invalidated by deleting **all** rows for a user whenever that user records or removes a **score-affecting** feedback signal (`like`/`dislike` — `SCORE_AFFECTING_SIGNALS`, `app/constants.py`) or changes their personas — the affinity / indirect-feedback terms mean either change shifts scores on every co-categorical event, so per-row invalidation would leave neighbours stale. `bookmark` and the passive `view`/`click_external` signals are never read by the scorer (`ranking/score.py`, `browse.py` both filter feedback to `like`/`dislike` only), so recording/removing those does **not** invalidate — gating on `SCORE_AFFECTING_SIGNALS` keeps the cache warm across every ticket click and bookmark instead of wiping it on every one. Shared via `invalidate_user_scores()` (`routers/utils.py`), called from `routers/feedback.py` (record/delete, gated) and `routers/onboarding.py` (`set_persona`, before the feed rebuild, unconditional).
- `daily_feeds` — user_id, feed_date, event_ids BigInteger[]
- `organizers` — self-service submission account (see Organizer Event Submission): email (citext unique), locale, session_token_version (int, bumped to revoke all organizer sessions), verified (bool, default false — gates auto-publish, flipped true by an admin's first `POST /admin/submissions/{id}/approve`)
- `organizer_magic_links` — mirrors `auth_magic_links` for the organizer auth track: token_hash (sha256), expires_at, used_at
- `organizer_image_uploads` — one row per successful `POST /organizer/events/image` upload (organizer_id, created_at); exists purely to count-then-act against `ORGANIZER_DAILY_IMAGE_UPLOAD_CAP` (an upload can happen before the organizer ever submits/edits an event, so it can't be derived from `Event.created_at` the way `ORGANIZER_DAILY_SUBMISSION_CAP` is). Never read back; no retention sweep.
- `events.submitted_by_organizer_id` (FK → `organizers.id`, indexed) / `events.needs_review` (bool, partial index on true) — attribute an organizer-submitted event back to its account and flag it for the admin post-hoc review queue (`GET /admin/submissions`)

## LLM Usage Constraints

- **Hard cap:** ≤600 tokens per LLM call to avoid quota exhaustion.
- **Dedup cache:** Cache decisions by content hash — never re-call LLM for identical pairs.
- **Fallback order:** Groq (primary, `llama-3.3-70b-versatile`) → Cerebras (`gpt-oss-120b`) → Mistral (`mistral-small-latest`, overnight batch, 1B tok/mo). Provider chain defined in `app/constants.py::LLM_PROVIDERS`. Cerebras's `gpt-oss-120b` is a reasoning model — its entry overrides `reasoning_effort=low` and a 600-token cap (`LLM_REASONING_MAX_TOKENS`, vs the 400-token default) so reasoning tokens don't crowd out the JSON answer.
- Groq's 30 req/min burst means no sleep loop needed in the classification batch job.
- **Backlog drain** — `dedup_pass` and `classify_pending` run via `_drain_backlog()` (`app/ingestion/jobs.py`): each re-runs its single pass while work remains, retrying every `LLM_BACKLOG_RETRY_SECONDS` (15 min) up to `LLM_BACKLOG_MAX_DRAIN_PASSES` (12) before deferring the remainder to the next 6h cycle. Admin-triggered runs (`POST /admin/dedup`, `POST /admin/classify`) use `*_drain_now()`, which drains synchronously with no inter-pass sleep since the caller is blocking on the HTTP response.

## Content Safety (NSFW / Explicit Content Filter)

Three layers, each cheaper than the next:

1. **Ingest-time keyword prefilter** — `app/ingestion/content_filters.py::is_explicit_text()` (variadic — called with title/description/venue_name/important_info) matches `EXPLICIT_KEYWORDS` (frozenset of en/et/ru phrases in `app/constants.py`, covering porn/striptease/escort and kink/BDSM/fetish content) via word-boundary regex, setting `Event.is_explicit`. Events flagged here skip the LLM classification call entirely (token savings) but still advance to `classified` (see Data Flow §3).
2. **LLM classification flag** — `app/llm/classifier.py` asks the model to set `is_explicit` for events that pass layer 1, catching content the keyword list misses.
3. **Publish gate** — `app/publish.py::publish_pending()` excludes any event with `is_explicit = true` from ever reaching `published`, regardless of how the flag was set.

## Non-Event Filter (gift cards / merch / webinars)

Mirrors the NSFW three-layer pattern for listings that are not real attendable events — gift cards/vouchers, merchandise (books, VIP/club cards), donations, and online-only webinars/courses/recordings (target audience wants in-person Tallinn events):

1. **Ingest-time keyword prefilter** — `app/ingestion/content_filters.py::is_non_event_text()` matches `NON_EVENT_TITLE_KEYWORDS` against the **title only** (descriptions mention "gift cards available" as a payment option — false positive) and `NON_EVENT_VENUE_KEYWORDS` (online/онлайн/veebis/mamaonline) against `venue_name`, setting `Event.is_non_event`. Flagged events skip the LLM classification call (like `is_explicit`) but still advance to `classified`.
2. **LLM classification flag** — `app/llm/classifier.py` asks the model for a `non_event` boolean, OR-merged into `Event.is_non_event` (never un-sets a layer-1 flag). In-person workshops/trainings with a set time are explicitly NOT non-events.
3. **Publish gate + read paths** — `publish_pending()` blocks `is_non_event = true` (reject reason `fail_non_event`); the Daily 5 candidate query (`ranking/score.py`), feed hydration (`routers/feed.py`), event detail (`routers/events.py`), and the email digest event query (`email/digest.py`) all filter it as defense-in-depth. The detail-refetch sync (`ingestion/refetch.py`) re-runs `is_non_event_text()` after a `venue_name` change (mirroring its `is_explicit` re-check) and demotes a newly-flagged published event.

New email types add their own header/body/footer templates and reuse `EMAIL_DOCUMENT` rather than duplicating the shell.
- **Email digest** — `backend/app/email/digest.py` handles data formatting + assembly and Resend delivery, filling `EMAIL_DOCUMENT` with `DIGEST_HEADER`/`DIGEST_FOOTER`. The digest matches the site's visual design: each event block includes its `image_url` (escaped, falls back to a plain color band when absent) and the header carries an "open feed" button linking to the frontend app (`feed_url`). HTML only, no plain-text part. All subjects, labels, and day/month names resolved via `app/i18n.py`. New email types must follow the same three-file split: presentation CSS in `styles.py`, markup in `templates.py`, assembly + delivery in a dedicated module.

Sends both an HTML and a plain-text part — unlike the digest, since this is a transactional/deliverability-sensitive send. Called from `app/auth/email.py::send_magic_link`, which stays on a raw (non-retrying) `httpx` call for the reason documented inline (see Auth section below).
- **Contact email** — `backend/app/email/contact.py` (`send_contact_message`) delivers a contact-form submission to the owner inbox (`settings.CONTACT_TO_ADDRESS`, `reply_to` set to the sender) via Resend. This is **internal-only** mail (not user-facing branding), so it deliberately skips the `EMAIL_DOCUMENT` shell / `styles.py` / `templates.py` split and inlines escaped plain markup — the documented exception to the three-file rule. Falls back to log-only when `RESEND_API_KEY` is unset. Called from `app/routers/contact.py::submit_contact` (`POST /contact`, honeypot + `RATE_LIMIT_CONTACT`), which swallows send errors so no email failure surfaces to the caller.
- **Drift guard** — `backend/tests/test_generated_sync.py` runs the generator into a temp dir and asserts byte-identical output. If it fails: `python scripts/generate_shared.py` and commit.

## Auth

Magic-link email via `itsdangerous` tokens (no third-party auth). Token generation/verification lives in `app/auth/tokens.py`; magic-link delivery in `app/auth/email.py` (Resend, 3k/mo free tier). The signed session token is the credential — it is **not** stored server-side, so there is no per-token row to delete.

Session tokens are issued after magic-link verification and passed as an `Authorization: Bearer <token>` header (`frontend/src/api/client.ts`, `routers/auth.py::get_current_user`). TTL is 2 days (`SESSION_TTL_DAYS`); magic-link TTL is `MAGIC_LINK_TTL_MINUTES`. Both are settings in `app/config.py` defaulting to values in `shared/app-config.json`.

**Per-email resend cooldown:** `POST /auth/request-link` (and its organizer twin) short-circuits — still returning the same 200 anti-enumeration body, no new row, no send — when an *unused* link for that account was issued within `MAGIC_LINK_RESEND_COOLDOWN_SECONDS` (120). Derived from `expires_at` rather than a stored issued-at (a link created T ago has `expires_at = now + TTL − T`). This is the per-account guard against Resend quota exhaustion from rapid repeats; the `@limiter.limit` decorator is the per-IP one.

**Session revocation:** each session token embeds a `v` (version) claim equal to `users.session_token_version` at issue time; `get_current_user` rejects any token whose `v` no longer matches the stored value. `POST /auth/logout-all` increments that counter (atomic `UPDATE ... RETURNING`, mirroring the magic-link consume pattern), invalidating every previously issued token — including the one making the request. This is the only server-side state in the auth flow.

**Email verification gate:** `_get_or_create_user` (`app/routers/auth.py`) inserts a `User` row on an unauthenticated `POST /auth/request-link` before the address is ever proven reachable — `users.email_verified` defaults `false` at row creation. `verify_magic_link` durably flips it to `true` (atomic `UPDATE ... RETURNING`, same idiom as `logout_all`) the first time that user's magic link is successfully consumed; since a session token can only ever be issued from inside `verify_magic_link`, an `email_verified = false` row is provably one nobody has ever logged into — that guarantee holds going forward from migration `0024_users_email_verified.py`, which blanket-backfilled every pre-migration row to `true` (an already-purged `auth_magic_links` history made deriving real verification status for old rows impossible; see the migration's own comment). `build_daily_feeds` (`_verified_user_ids`, `app/ranking/score.py`) and `send_daily_digests` (`app/email/digest.py`) both filter on `email_verified` so an anonymous POST with someone else's address can't enroll them in the daily digest going forward.

**Known residual risk — magic token in URL query string:** `/auth/verify?token=...` carries the one-time sign-in token in the URL (`AuthVerify.tsx`). URLs can leak via browser history, `Referer` headers, and proxy/server access logs. This is mitigated by the token being single-use (atomic `UPDATE ... WHERE used_at IS NULL ... RETURNING`, closes the TOCTOU race) and short-lived (`MAGIC_LINK_TTL_MINUTES`), so a leaked link has a narrow exploitation window. Moving verification to a POST body would close this gap entirely but adds friction to the email-link UX (the whole point of magic links is a single click) — left as a documented trade-off rather than changed.

**Known residual risk — session tokens in `localStorage`:** both the consumer session token (`frontend/src/lib/auth.ts`) and the organizer session token (`frontend/src/lib/organizerAuth.ts`) are stored in `localStorage`, readable by any script running in the origin. The signed session token is the entire credential (2-day TTL, no server-side row — see above), so a successful XSS is a full, silent account takeover; recovery requires the affected user to hit `logout-all`. This is accepted rather than fixed because the XSS surface is already narrow: the SPA CSP is `script-src 'self'` with no `eval`, and every `dangerouslySetInnerHTML` site runs through DOMPurify (`sanitizeHtml()`, `frontend/src/utils.ts`) on top of the server-side `nh3` sanitization at ingest. An httpOnly + Secure + SameSite=Lax cookie issued by `/auth/verify` would close this residual gap (the Vercel `/api` rewrite already makes the SPA same-origin with the API, so no cross-site cookie problem, and `allow_credentials=False` on CORS still holds since the browser would send it same-origin) — left as a documented trade-off, matching the magic-token-in-URL entry above, rather than a cross-cutting auth-flow change.

**Digest unsubscribe:** `app/routers/unsubscribe.py` (`POST /email/unsubscribe`, `POST /email/resubscribe`) flips `email_digest_opt_in` with no login, using a separately-salted (`AUTH_UNSUBSCRIBE_SALT`) `itsdangerous` token minted per-recipient into every digest email (`UNSUBSCRIBE_TOKEN_TTL_DAYS`, 365 — long-lived so an old inbox email keeps working). The digest's visible link points at the frontend `/unsubscribe?token=...` page (`routes/Unsubscribe/`), which POSTs on mount and offers an Undo/resubscribe button; `send_digest_email` (`app/email/digest.py`) also emits the same token as an RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post: List-Unsubscribe=One-Click` header pair (absolute URL via `settings.BACKEND_URL`, since mail providers call it server-side) so Gmail/Apple Mail render a native one-click button. **Known residual risk — no revocation, unlike session tokens:** the token carries no version claim, so a leaked one stays valid for the full year; accepted because the only effect is toggling a reversible preference flag, mirroring the magic-link residual-risk trade-off above.

**Organizer auth:** a separate parallel track for the self-service submission portal — see Organizer Event Submission above for the full auth/salt/table breakdown.

## Admin Endpoints

`/admin/*` uses HTTP Basic auth (`ADMIN_USERNAME`, default `"admin"`, + `ADMIN_PASSWORD` env vars), checked with `secrets.compare_digest`. Failed auth attempts log a warning (audit trail). With no password set, any credentials are accepted (logs a warning) **only** when both `APP_ENV=development` and `ALLOW_INSECURE_DEV=true` (`app/config.py`) — a dev-shaped `APP_ENV` alone is never sufficient, so a stray/never-overridden env var on a real deployment fails closed rather than silently opening the admin surface (`require_configured_secret`, `app/routers/utils.py`; the same double gate protects the inbound webhook and `/internal/tick`). Otherwise the password is required — unset = 503. `app/main.py`'s lifespan also logs an ERROR if `APP_ENV=development` but `DATABASE_URL` resolves to a non-local host (`DEV_DB_LOCAL_HOSTS`), flagging exactly that misconfiguration. Every `/admin/*` route is also rate-limited (`RATE_LIMIT_ADMIN`, see Security Hardening).

List endpoints that can grow unbounded (e.g. `/admin/dedup/groups`) are paginated via `limit`/`offset` query params with caps in `app/constants.py` (`ADMIN_*_PAGE_SIZE`, `ADMIN_*_MAX_PAGE_SIZE`). Pagination is by logical unit (dedup group, not row) so a single noisy cluster cannot dominate a page. Add the same pattern to any new admin list endpoint.

Manual pipeline triggers: `POST /admin/dedup`, `POST /admin/classify`, `POST /admin/publish`, `POST /admin/geocode`, `POST /admin/refetch` run the corresponding scheduled job synchronously (dedup/classify use the drain-now variant, see Backlog drain above) for ad-hoc operation outside the cron cadence. `POST /admin/geocode` and `POST /admin/refetch` run standalone (`geocode_pending_job` / `refetch_event_details_job`) — neither is part of `POST /admin/pipeline/run`. Run `/admin/refetch` before a manual `/admin/geocode` if you want coords NULLed by an address change re-resolved in the same operation. `POST /admin/cleanup` runs `cleanup_stale_data` (see Data Retention & Cleanup) standalone, outside `/admin/pipeline/run`; defaults to `dry_run=true`. The remaining routes are `POST /admin/ingest` (runs ingestion for every enabled source) + `POST /admin/ingest/{slug}` (single source), `POST /admin/build-feeds`, `POST /admin/send-digests`, `GET /admin/dedup/groups`, `GET /admin/stats`, and the organizer submission review queue — `GET /admin/submissions` (paginated, excludes cancelled), `POST /admin/submissions/{event_id}/retract`, `POST /admin/submissions/{event_id}/approve` (see Organizer Event Submission above). Every synchronous job trigger goes through the shared `run_admin_job()` helper (`routers/utils.py`) — use it for any new one rather than calling the job directly. **Exception:** `POST /admin/pipeline/run` (`admin_pipeline_run`) hand-rolls its own per-stage `try`/`except` instead, because it needs stop-on-first-failure semantics with a per-stage result dict — `run_admin_job()`'s single-shot success/500 conversion can't express "run stage N, stop and report which stage failed, but still return the results of stages before it." This is the only endpoint that should bypass the helper for this reason.

## Security Hardening

The backend was hardened against the OWASP Top 10 (2021). The middleware stack and these invariants are wired in `app/main.py`:

- **Rate limiting** — `slowapi` limiter lives in `app/rate_limit.py` (its own module to avoid a circular import between `main.py` and routers), keyed by `client_key()` rather than slowapi's default `get_remote_address` — see the "Rate-limit / audit-log key derivation" bullet below for why. **Every router endpoint** carries `@limiter.limit(...)` — authenticated ones included — with the limit string sourced from a `RATE_LIMIT_*` constant in `app/constants.py` (the only exceptions are `/health` and `/internal/tick`, see below): public unauthenticated routes (`/auth/request-link` + `/organizer/auth/request-link` → `RATE_LIMIT_AUTH_REQUEST_LINK`, `/auth/verify` + `/organizer/auth/verify` → `RATE_LIMIT_AUTH_VERIFY`, `/webhooks/inbound-mail` → `RATE_LIMIT_WEBHOOK_INBOUND_MAIL`, `/public/showcase` → `RATE_LIMIT_PUBLIC`, `/contact` → `RATE_LIMIT_CONTACT`, `/email/unsubscribe` + `/email/resubscribe` → `RATE_LIMIT_UNSUBSCRIBE`, the optional-auth `/events/{id}` → `RATE_LIMIT_EVENTS_DETAIL`); authenticated reads and writes (`/explore` + `/feed` + `/auth/me` → `RATE_LIMIT_BROWSE`, `/feedback*` → `RATE_LIMIT_FEEDBACK`, `/onboarding/persona` + `/users/me` → `RATE_LIMIT_AUTHENTICATED_WRITE`, `/auth/logout-all` + `/organizer/auth/logout-all` → `RATE_LIMIT_LOGOUT_ALL`, every `/organizer/events*` route → `RATE_LIMIT_SUBMIT`); plus every `/admin/*` route sharing **one** bucket via `limiter.shared_limit(RATE_LIMIT_ADMIN, scope="admin")` rather than a separate bucket per route (`"10/minute"` total across the whole `/admin` prefix per client — a per-endpoint `@limiter.limit` would let an attacker cycling all ~17 admin routes attempt far more than the nominal cap per minute; see also the consecutive-failure lockout below). Add the same decorator + constant to any new endpoint, public or not. `ProxyHeadersMiddleware(trusted_hosts="*")` is registered **last** (so it runs outermost) to rewrite `request.client` from `X-Forwarded-For` before the limiter reads it — without it, Render's proxy would collapse all clients into one bucket. **Ops-verification dependency (accepted trade-off, see the invariant comment at `main.py`):** `trusted_hosts="*"` trusts any peer's `X-Forwarded-For` verbatim, so its safety hinges on the process being reachable *only* through Render's proxy and on Render's edge overwriting inbound `X-Forwarded-For`. Render publishes no stable egress CIDR to pin `trusted_hosts` to, so this stays `"*"` — confirm Render's XFF handling on the dashboard rather than in code, and re-derive if the deployment ever sits behind an additional CDN/proxy or gets a public port.
- **Rate-limit / audit-log key derivation (`app/rate_limit.py::client_key`)** — `ProxyHeadersMiddleware(trusted_hosts="*")` itself rewrites `request.client` from the **leftmost** `X-Forwarded-For` entry (uvicorn's `_TrustedHosts.get_trusted_client_address`), which is attacker-controlled: a client can prepend an arbitrary `X-Forwarded-For` value and every `@limiter.limit(...)`/`shared_limit(...)` becomes a no-op, and every `client=%s`-style log line becomes forgeable. `client_key()` instead derives the key from the **rightmost** XFF entry — the one appended by the single trusted hop immediately adjacent to this process (Render's proxy) — which is correct whether Render appends to or overwrites the header, but depends on there being exactly **one** trusted hop between the client and this process (see the `HOP-COUNT ASSUMPTION` comment next to `ProxyHeadersMiddleware` in `main.py`, alongside the pre-existing `trusted_hosts="*"` invariant). `/internal/tick`'s invalid-token log line also goes through `client_key()` rather than raw `request.client.host` for the same reason.
- **Security headers** — the `add_security_headers` middleware sets CSP/`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`Cache-Control: no-store` (nothing from a pure JSON API should ever be cached by an intermediary — most importantly `GET /auth/verify`, whose body carries a bearer session token) on every response from the `SECURITY_HEADERS` dict in `app/constants.py`; HSTS (`HSTS_HEADER_*`) is added only outside development (safe only over HTTPS). The CSP is `default-src 'none'` — the app is a pure JSON API with no first-party HTML/script surface. `TrustedHostMiddleware` (outside development only, `allowed_hosts` derived from `settings.BACKEND_URL`'s hostname) rejects requests with an unexpected `Host` header — low impact today (nothing builds an absolute URL from the request `Host`) but a one-line hardening against intermediary cache-poisoning scenarios.
- **Request body size ceiling** — `MaxBodySizeMiddleware` (`app/main.py`) rejects any request whose body exceeds `MAX_REQUEST_BODY_BYTES` (10 MiB) with 413, before a handler ever reads it. A `Content-Length` request is rejected up front; a chunked request (no `Content-Length`) is rejected mid-stream once the running total crosses the limit, via a wrapped `receive` ASGI callable. It sends the 413 response itself (an ASGI `Response.__call__`) rather than raising `HTTPException` — Starlette places every `add_middleware` entry **outside** its internal `ExceptionMiddleware` (which sits innermost, right next to the router), so an `HTTPException` raised from user-added middleware never reaches it and would surface as a generic 500 instead. Registered so it wraps *inside* `ProxyHeadersMiddleware` (still sees the rewritten client for logging/rate-limiting) — this is the whole-request-body ceiling `IMAGE_UPLOAD_MAX_BYTES` alone doesn't provide (that constant only bounds what the upload handler reads after Starlette has already spooled the full body).
- **API docs** — `/docs`, `/redoc`, and `/openapi.json` are enabled **only** in development (`APP_ENV == "development"`); the strict CSP would block their CDN assets in production anyway.
- **CORS** — `CORSMiddleware` with `allow_credentials=False` (auth is a Bearer header, never a cookie); origins from `settings.CORS_ORIGINS`, methods/headers from `CORS_ALLOWED_METHODS`/`CORS_ALLOWED_HEADERS` constants.
- **`/internal/tick`** — guarded by a constant-time `X-Internal-Token` check against `INTERNAL_TOKEN`; fail-closed outside development (see `require_configured_secret` below).
- **`require_configured_secret` double gate (dev fail-open)** — `app/routers/utils.py::require_configured_secret()` protects every secret-gated surface (`/admin/*` Basic auth, the inbound webhook's Svix signature check, `/internal/tick`'s token check). With the secret unset, it fails open (logs a warning, skips verification) **only** when both `APP_ENV == "development"` **and** the separate `settings.ALLOW_INSECURE_DEV` flag are true — a dev-shaped `APP_ENV` alone is never sufficient, so a stray or never-overridden env var on a real deployment fails closed (503) instead of silently unprotecting the admin surface. `app/main.py`'s lifespan additionally logs an ERROR if `APP_ENV == development` but `DATABASE_URL` resolves to a non-local host (`DEV_DB_LOCAL_HOSTS`), flagging exactly that misconfiguration pattern.
- **Admin auth lockout** — beyond the shared per-client rate-limit bucket above, `routers/admin.py::_require_admin` tracks consecutive Basic-auth failures per `client_key()` in an in-memory dict and locks out further attempts (429) for `ADMIN_AUTH_LOCKOUT_SECONDS` after `ADMIN_AUTH_MAX_FAILURES` consecutive failures — a static username/password pair otherwise has no brute-force damper beyond the rate limit itself. In-memory and single-process (matches this codebase's no-Celery/no-Redis design), so it resets on deploy/restart; accepted since it's a supplement to, not a replacement for, a strong `ADMIN_PASSWORD`.
- **Rate-limit-exempt by design** — `GET /health` and `GET /internal/tick` (`app/main.py`) carry no `@limiter.limit(...)`. `/health` is a platform health-check probe (Render); rate-limiting it risks the platform marking the service unhealthy under legitimate probe traffic. `/internal/tick` is hit every 10 min by the cron-job.org keepalive and is already access-controlled by the `X-Internal-Token` check above — a second layer of IP throttling adds no real protection over a token an attacker doesn't have. Both are deliberate exceptions to the "every public route gets a rate limit" rule above.
- **External-URL sanitization** — the guard picked for a URL field is decided by *whether the server itself fetches it*, not by which field it is. Untrusted `image_url` (rendered into an `href`/`src`, never fetched server-side) passes through `safe_external_url()` (`app/ingestion/http_client.py`), which drops any scheme not in `SAFE_URL_SCHEMES` (guards stored XSS via `javascript:`/`data:` URLs). `event.url` for an adapter-kind source (scraped, **fetched** daily by the refetch job) instead goes through the stronger `safe_fetchable_url()`, which layers a host-allowlist plus `resolves_to_private_ip()` (a DNS-rebinding / private-IP guard) on top of the scheme check. `event.url` for a `user_submission`-kind source is render-only — organizer submissions are excluded from the refetch job (`refetch.py::_select_candidates`, `submitted_by_organizer_id IS NULL`) since an organizer edits their own row directly via PATCH — so `insert_normalized_event()` (`app/ingestion/adapter.py`) picks `safe_external_url()` for it too, off `source.kind == SOURCE_KIND_USER_SUBMISSION`; an organizer's own ticketing domain is otherwise never on `ALLOWED_SOURCE_HOSTS`. Apply the matching guard to any new field, keyed on the same fetched-vs-rendered question. The frontend repeats the scheme check as defense-in-depth in `safeUrl()` (`frontend/src/utils.ts`) — route every untrusted URL through it before putting it in an `href`/`src`; `sanitizeHtml()` (same file) is the matching defense-in-depth pass for the HTML fields below, applied at both `dangerouslySetInnerHTML` sites (`EventDetail.tsx`). **Organizer `image_url` is additionally host-restricted** (`routers/organizer_events.py::_check_image_host`, `ALLOWED_IMAGE_HOSTS = {"res.cloudinary.com"}`): the scheme check alone would let an organizer point `image_url` at an arbitrary https host, which the daily digest embeds as an `<img>` — an unconsented tracking pixel leaking each recipient's IP/open-time to a third party. Submissions must go through the signed `POST /organizer/events/image` Cloudinary upload instead; scraped (non-organizer) sources are unaffected.
- **Stored-HTML sanitization** — every scraped rich-text field the frontend renders as HTML (the localized `description`/`important_info` blocks — `title` is rendered as escaped text, not HTML, so it is not in scope here) is run through `sanitize_html()` (`app/ingestion/sanitize.py`) at ingest — a strict `nh3` (Rust ammonia) tag/attribute allowlist plus block-to-`<br>`, whitespace-collapse, and Cloudflare email-obfuscation-decode passes. `html_to_text()` in the same module is the plain-text converter used by every non-HTML consumer (LLM prompts in `classifier.py`, keyword matching in `content_filters.py`, fuzzy dedup in `dedup/rules.py`). Any new stored field that will be rendered as HTML must pass through `sanitize_html()`; any that feeds an LLM or matcher uses `html_to_text()`. This applies to new `HtmlListingAdapter` subclasses too: the default `extract_localized_text()` (`app/ingestion/sources/html_base.py`) sanitizes its JSON-LD description before returning it, so a subclass that doesn't override the method still stores sanitized HTML.
- **Redirect SSRF guard** — `httpx`'s `follow_redirects=True` has no same-origin restriction on its own, so any client that follows redirects to an untrusted host (e.g. `FientaAdapter`, which needs it for Fienta's localized-path 302s) must pin every hop to the expected host via a `request` event hook (`host_guard_hook` in `app/ingestion/http_client.py`, shared by `fienta.py`, `html_base.py`, and `refetch.py`) — httpx fires that hook once per redirect hop, making it the only point that can validate the redirect's actual destination. Pre-fetch URL checks alone only validate the un-redirected URL. Apply the same hook pattern to any future adapter that enables `follow_redirects`.
- **Webhook signature verification** — `routers/webhooks.py::inbound_mail()` verifies the Resend inbound-mail webhook via Svix HMAC-SHA256 over `"{svix-id}.{svix-timestamp}.{raw body}"` using `settings.RESEND_WEBHOOK_SECRET`, checking the `svix-id`/`svix-timestamp`/`svix-signature` headers (constants `SVIX_ID_HEADER`/`SVIX_TIMESTAMP_HEADER`/`SVIX_SIGNATURE_HEADER`/`SVIX_SECRET_PREFIX` in `app/constants.py`) plus a `WEBHOOK_TIMESTAMP_TOLERANCE_SECONDS` (300s) replay-window check. Fails closed outside development via the shared `require_configured_secret()` helper (`routers/utils.py`) — replaces the old `?secret=` query-string check.
- **Dependency CVE audit** — `.github/workflows/dependency-audit.yml` runs `pip-audit` (backend) and an `npm-audit` job (`npm audit --audit-level=high`, frontend) on push/PR to `master` and weekly (Mon 04:00 UTC) to catch newly-disclosed CVEs in pinned deps.

## Logging

`app/logging_config.py::configure_logging()` is the single logging entry point. It is called at import time in `app/main.py` — deliberately *after* uvicorn configures its own logging, so it runs last and wins. It strips the framework loggers (`uvicorn`, `uvicorn.error`, `uvicorn.access`, `sqlalchemy.engine`) of their own handlers and re-points them at the root logger, so every line (app, uvicorn, SQL echo) shares one timestamped format. `configure_logging()` is idempotent (safe under `--reload` and in tests).

- **Development** — human-readable text to the console **and** a rotating file under `backend/logs/` (sizes/names in the `LOG_*` constants). SQL echo logs at INFO.
- **Production** (`APP_ENV != development`) — JSON-lines (`JsonLogFormatter`) to the console. SQL echo drops to WARNING. If `LOG_SHIP_URL` is set, logs are also shipped to an HTTP drain (e.g. Axiom) via a `QueueHandler` → background `QueueListener` thread so the request path never blocks; auth is `Bearer LOG_SHIP_TOKEN`. An `_AccessPathFilter` drops successful (`< 400`) uvicorn access lines for the paths in `LOG_SHIP_SUPPRESS_ACCESS_PATHS` (`/health`) before shipping, so the platform health probe doesn't dominate the drain; errors on those paths still ship. Each record is POSTed as a single-element JSON array (`[{…}]`) because Axiom's ingest endpoint expects an array of events, not a bare object — also accepted by other JSON drains.
- **Never crash the app** — log-shipping network failures are swallowed (`handleError`); `shutdown_log_shipping()` stops the listener thread on app shutdown (wired into the lifespan in `main.py`).
- All logging literals (formats, date format, file size/backup count, queue size, timeouts) live in `app/constants.py` (`LOG_*`); `LOG_LEVEL` / `LOG_SHIP_URL` / `LOG_SHIP_TOKEN` are settings in `app/config.py`.
- **Monitoring spec** — `docs/observability.md` is the version-controlled source of truth for the Axiom side: the shipped log-record shape, the `LOG_EVENT_*` `event` taxonomy, and the APL queries behind each hand-created Axiom monitor (Axiom's free tier has no monitors-as-code, so the doc stands in for it). Update it whenever a `LOG_EVENT_*` constant or a shipped log field is added or renamed.

## Code Quality & Best Practices

This project follows production best practices throughout:

- **Backend constants** — all literals (numbers, strings, thresholds, weights, sentinel values) live in `app/constants.py`, except LLM prompt templates, which live in `app/llm/prompts.py` (kept apart so prompt-engineering diffs stay clean) and CSS-selector/scraping constants in `app/ingestion/selectors.py`. Cross-stack scalars (TTLs, locale set, weights, signals, category/vibe taxonomies) are sourced from `shared/app-config.json` and imported via `app._generated.shared_constants`. Never define a constant near business logic — always add it to `app/constants.py` (or `shared/` + regenerate) first, then import it. Never duplicate constants across files.
- **Backend utilities** — all shared helper functions live in `backend/app/routers/utils.py`. Before writing a new utility function anywhere in the backend, check this file first. If the function is reusable, add it here and import it — never duplicate helpers across routers or modules.
- **Frontend constants** — all magic values (numbers, strings, breakpoints, timeouts, limits) live in `frontend/src/constants.ts`. Cross-stack values (`LOCALES`, `PERSONAS`, `MAGIC_LINK_EXPIRY_MINUTES`, `PERSONA_PRIMARY_WEIGHT_THRESHOLD`) are sourced from `shared/` and imported via `frontend/src/_generated/sharedConstants.ts`. Apply the same discipline: never inline a literal near component logic — add it to `constants.ts` (or `shared/` + regenerate) first. Never duplicate constants across components.
- **Frontend utilities** — all shared helper functions live in `frontend/src/utils.ts`. Before writing a new utility function anywhere in the frontend, check this file first. If the function is reusable, add it here and import it — never duplicate helpers across components or pages.
- **CSS design tokens** — the following categories are fully tokenized in `:root` (`frontend/src/index.css`) and **must never be hardcoded** in component stylesheets: colors (semantic names, no common prefix — `--accent*`, `--bg*`, `--text*`, `--border*`, `--danger*`, `--success*`, `--on-accent`, `--overlay-scrim`, …), border-radius (`--radius`, `--radius-sm`/`-lg`/`-pill`/`-full`), shadows (`--shadow-*`), z-indices (`--z-*`), transitions (`--transition`, `--transition-transform`), animation easing + durations (`--easing`, `--easing-breathe`, `--anim-*`), blur (`--blur-*`), spacing (`--space-0-1`…`--space-9`, including fractional steps like `--space-1-25`), typography (`--fs-2xs`…`--fs-xl` plus role-specific `--fs-*`, `--heading-display`/`--heading-3xl`…`--heading-xs`, `--numeral-*`, `--leading-*`, `--tracking-*`, `--font-display`), and component-geometry vars (e.g. `--calendar-cell-size`, `--picker-pop-width`, `--toggle-*`, `--spinner-*`). When any of these are needed, define the token in `:root` first, then reference it via `var(--token-name)`.
- **CSS shared base classes** — structural CSS patterns (card chrome, button styles, menu/popover chrome) live in `frontend/src/components/shared/` (`Card.module.css`, `Button.module.css`, `Menu.module.css`). Use CSS Modules `composes: baseClass from '...'` to inherit shared rules — **never duplicate card, button, or menu CSS** across route or component stylesheets. Add new shared patterns to the shared files and compose from them.
- **Retry logic** — all HTTP calls use `http_get()` / `http_post()` from `app/ingestion/http_client.py`, which wrap `httpx` with tenacity exponential-backoff retry (`HTTP_RETRY_MAX_ATTEMPTS` 5, `HTTP_RETRY_WAIT_MIN`–`MAX` 2–30s, plus up to `HTTP_RETRY_JITTER_MAX` 1s of jitter). A 429's `Retry-After` header is honored verbatim instead of the backoff curve, capped at `HTTP_RETRY_AFTER_MAX_SECONDS` (60s). Retryable: `HTTP_RETRYABLE_STATUS_CODES` (429/502/503/504) and `RequestError`. Non-retryable: 4xx except 429.
- **DB connection pooling** — `app/db.py` sets `pool_pre_ping=True` (pings before reuse) and `pool_recycle=DB_POOL_RECYCLE_SECONDS` (280s, below Neon's 5-min idle auto-suspend) so the pool never hands out a connection the server has already dropped.
- **HTML listing adapters** — Piletilevi, KUMU, and Estonia Concert Hall share `HtmlListingAdapter` (`app/ingestion/sources/html_base.py`), which handles pagination, parsing, dedup, and detail fetches. New HTML-scraped sources should subclass it rather than duplicating the fetch/parse loop. Per-locale page discovery + the shared locale-variant fetch loop (`fetch_locale_variants`) live in `app/ingestion/locale_urls.py` — reused by `html_base.py`, `fienta.py`, and `refetch.py`; don't duplicate hreflang/locale-detection logic in an adapter. Low-level BeautifulSoup helpers (`attr_str`) live in `app/ingestion/html_utils.py`, kept separate from `html_base.py` to avoid a circular import with `locale_urls.py`.
- **Presentation layer separation** — never inline static CSS or HTML markup inside business-logic or delivery modules. Extract CSS into a dedicated `styles.py` and HTML markup into a dedicated `templates.py` sibling, then import the constants into the assembly module. The email package (`app/email/styles.py`, `app/email/templates.py`, `app/email/digest.py`) is the canonical example: CSS constants in `styles.py`, `.format()`-style markup constants in `templates.py`, data formatting + Resend delivery in `digest.py`. Apply the same three-file split to any future rendering feature (new email types, report generation, etc.). Do not introduce a templating engine (Jinja2, etc.) — plain Python string constants with `str.format()` are sufficient and keep dependencies minimal. **Exception:** `app/email/contact.py` is internal-only owner-inbox mail (no user-facing branding), so it inlines a small escaped-plain-markup body and skips the split — user-facing emails must not.
- **Encapsulation** — a leading underscore signals module-private; never import a `_name` from another production module. If a helper is imported cross-module, drop the underscore to make the API surface honest. Exceptions: `_is_retryable`, `_find`, `_venue_compatible`, `_make_slug` are intentionally private (used only within their defining module). Tests may import private names for white-box testing — that is an accepted pattern.
- **Error visibility** — HTTP failures in source adapters propagate to `SourceAdapter.run()` so `IngestionRun.error` and `source.last_status` are always set correctly. Never swallow exceptions in `fetch_raw()`.
- **Taxonomy** — LLM classification uses the fixed 14-category / 10-vibe frozensets `VALID_CATEGORIES` / `VALID_VIBES` (sourced from `shared/app-config.json` via `app/constants.py`). Filter LLM output against these frozensets before persisting — unknown values are silently dropped (see `_parse_classification` in `app/llm/classifier.py`).
- **Migrations** — always chain migrations correctly (`down_revision = "PREV"`). Keep migrations small and reversible. If a new unique index could collide with pre-existing duplicate rows (e.g. `event_sources(source_id, external_id)` in `0007`), include a defensive `DELETE` keeping the smallest `id` per key **before** `create_index` — never assume application-level gating prevents historical dupes.
- **Batch jobs — bulk-load, no N+1** — periodic jobs (`build_daily_feeds`, `classify_pending`, `run_dedup_pass`, `send_daily_digests`) must use a fixed number of queries independent of row count. Bulk-fetch all per-user / per-event data with one `WHERE col IN (...)` query and group in Python; never `SELECT` inside a `for user in users:` loop. When extending these jobs, group fetches before the inner loop, mirroring the pattern already in `ranking/score.py::build_daily_feeds` and `llm/classifier.py::classify_pending`.
- **External-API fan-out — bounded concurrency** — when sending many independent outbound calls (e.g. Resend digest emails), use `asyncio.gather(..., return_exceptions=True)` wrapped with an `asyncio.Semaphore` whose limit lives in `app/constants.py` (see `DIGEST_SEND_CONCURRENCY`). Pick the cap from the upstream provider's documented rate limit, leaving headroom for retries. Never serial-await one call at a time, and never unbounded-gather without a semaphore.
- **Dedup self-join pre-filter** — the shared `candidate_pair_ids_in_window()` helper (`app/dedup/rules.py`) SQL-pre-filters candidate pairs via an aliased self-join on a sargable `BETWEEN` time window. Both dedup passes consume it: `run_dedup_pass` (rule-only) feeds the pairs to `cluster_events`, and `run_dedup_pass_llm` (rule + LLM) runs the Python fuzzy `is_candidate_pair` check then the LLM tiebreaker on them. The Python fuzzy step always runs only on the pre-filtered pairs. Preserve this split: don't push the time check into Python, and don't push the fuzzy check into SQL.
- **Quote style** — Backend Python uses **double quotes** (enforced by Ruff `Q` rules in `backend/ruff.toml`: `inline-quotes`, `multiline-quotes`, `docstring-quotes` all set to `double`). Frontend TypeScript uses **single quotes** for JS/TS string literals and **double quotes** for JSX attributes (enforced by ESLint `quotes: ['error', 'single', { avoidEscape: true, allowTemplateLiterals: true }]` + `'jsx-quotes': ['error', 'prefer-double']` in `frontend/eslint.config.js`). Template literals and strings containing the preferred quote character may use the alternate form (`avoidEscape`). Run `ruff check --fix` and `eslint --fix` before committing.
- **Python lint rules** — Ruff is configured in `backend/ruff.toml` with `select = ["E", "F", "W", "Q"]` (pycodestyle errors/warnings, Pyflakes, quotes), `line-length = 88`, `ignore = ["E501"]` (long lines allowed when wrapping would hurt readability), and `extend-exclude = ["app/_generated"]` (generated modules are not hand-formatted). `python -m ruff check backend` must pass clean before commit. (`ruff` is not on PATH — always invoke via `python -m ruff`.)
- **Type checking** — `mypy` (`==2.1.0`, pinned in `backend/requirements-dev.txt`) must pass clean: `python -m mypy app` from `backend/`. No mypy config file exists — defaults are sufficient. A loop/result variable reused across blocks with structurally incompatible types (e.g. different ORM models) will fail under mypy's inference even though each block is independently correct; give each block its own variable name. Third-party imports with no type stubs (e.g. `apscheduler`) get a targeted `# type: ignore[import-untyped]` on the import line rather than a blanket per-module ignore.
- **Type annotations** — Use modern PEP 604 / PEP 585 syntax: `X | None` not `Optional[X]`, `list[T]` / `dict[K, V]` / `tuple[T, ...]` not `List` / `Dict` / `Tuple`. Annotate return types on all public functions (including FastAPI route handlers — `-> dict`, `-> list[Schema]`, `-> None`). Import from `typing` only for things still required there (e.g. `Any`, `TypeVar`, `Protocol`).
- **Shared test fixtures** — Common pytest fixtures (`mock_db`, `make_user`, `make_event`) live in `backend/tests/conftest.py`. Use them instead of inlining `AsyncMock()` DB scaffolding or constructing user/event objects by hand in each test. When a new fixture would be reused across two or more test files, add it to `conftest.py`.
- **Frontend test fixtures** — `renderWithProviders` (wraps in `QueryClient` + `MemoryRouter`) and `makeEvent` live in `frontend/src/test/utils.tsx`. Never inline `QueryClient`/`Router` scaffolding in a test — import from there. Mock the `api` module (`vi.mock('../../api/client')`) for component and route tests rather than mocking `fetch`.
- **Numeric truthiness** — never gate a numeric field on truthiness; `0` is falsy, so `price_raw.get("min") or fallback` and `raw.get("price") or {}` silently drop legitimate zero prices (free events). Use explicit `is not None` checks and `isinstance(x, dict)` guards. Currency normalization goes through `normalize_currency(raw, has_price)` in `app/ingestion/pricing.py`.

## Conventions

- All datetimes are timezone-aware — no naive datetimes anywhere. User-visible timestamps and scheduling logic use `zoneinfo` (`Europe/Tallinn`) via `TALLINN_TZ`. Auth/token expiry arithmetic (`generate_magic_token`, session TTL, `_mark_processed`) may use `datetime.now(timezone.utc)` since DST-ambiguity is undesirable for TTL math.
- Email columns use `citext` (case-insensitive) to prevent duplicate accounts.
- Persona affinity vectors and source config stored as JSONB for easy extension without migrations.
- Feedback decay formula: `0.9^days_since_feedback` — recent signals weighted higher, dislike is a hard exclude.
- Public event endpoints (`/events/{id}`) return only `status == published` events and never expose internal metadata (`dedup_group_id`, draft/cancelled rows). Filter at the query level (`routers/events.py`), not in the serializer.
