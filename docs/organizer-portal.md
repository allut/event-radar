# Organizer Portal (self-service event submission)

What's in here: the post-MVP self-service organizer portal — auth, submission, rich-text authoring, auto-publish trust gating, admin review queue, organizer settings, and the authenticated organizer contact form. Read this before touching `app/routers/organizer_auth.py`, `app/routers/organizer_events.py`, `app/routers/organizer_profile.py`, `app/routers/organizer_contact.py`, or `frontend/src/routes/EventSubmit/`. Saved Venues (`app/routers/organizer_venues.py`, `VenuePicker`) are documented in `docs/data-model.md`'s `venues` entry.

**Naming note:** this is a distinct concept from "Organizer Lifecycle (Fienta)" in `docs/pipeline.md` — a Fienta "organizer" there is a ticketing-source id being polled; an `Organizer` here (`app/models/models.py`) is its own account entity, a venue/promoter submitting events directly through a dedicated portal.

- **Auth** — a parallel track to the user magic-link/session stack (`app/routers/organizer_auth.py`, prefix `/organizer/auth`), with its own DB table (`organizers`, `organizer_magic_links`) and distinct signing salts (`AUTH_ORGANIZER_MAGIC_SALT`, `AUTH_ORGANIZER_SESSION_SALT`, `app/constants.py`) so an organizer token can never verify as a user token or vice versa, even though both use the same `URLSafeTimedSerializer(settings.SECRET_KEY)`. TTLs (`ORGANIZER_MAGIC_LINK_TTL_MINUTES`, `ORGANIZER_SESSION_TTL_DAYS`) mirror the user-facing defaults. `organizers.session_token_version` supports the same logout-all revocation pattern as `users.session_token_version`. Like the user track, the organizer session token is set as an httpOnly + Secure + `SameSite=Strict` cookie (`ORGANIZER_SESSION_COOKIE_NAME`, `app/constants.py`) rather than returned to client JS — but scoped `Path=/api/organizer` instead of `/api`, so an organizer endpoint ever added outside `/organizer/*` would silently 401 (see `docs/security.md`'s Auth section and `docs/adr/0001-session-tokens-in-httponly-cookies.md`). **Google sign-in coexists with magic link, organizer-first:** per `docs/adr/0002-google-sign-in-oauth-pkce.md`'s rollout order, the organizer track got the server-side OAuth 2.0 + PKCE flow first (no real organizer users yet — the safe live-test surface), with the consumer track following once proven; magic link never goes away on either track. Gated by `GOOGLE_SIGNIN_ORGANIZER_ENABLED` (backend, authoritative) / `VITE_GOOGLE_SIGNIN_ORGANIZER_ENABLED` (frontend, cosmetic-only).
- **Submission** — `app/routers/organizer_events.py` (prefix `/organizer/events`) lets an authenticated organizer `POST` a new event (inserted on the adapter-less `user_submission` source via the shared `insert_normalized_event()` helper, then classified + published inline within the request instead of waiting for the next scheduled pass), `PATCH`/`DELETE` (soft-delete via cancel) their own events, `GET` their own submission list, and `POST /organizer/events/image` for a signed Cloudinary image upload (secrets: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `app/config.py` — log-only/`501` when unconfigured, like the contact-email Resend fallback; server-side signature so the API secret never reaches the SPA, gated by `IMAGE_UPLOAD_ALLOWED_MIME` (415) and `IMAGE_UPLOAD_MAX_BYTES` (413)). A per-organizer daily submission cap (`ORGANIZER_DAILY_SUBMISSION_CAP`, 20) and a separate per-organizer daily **image upload** cap (`ORGANIZER_DAILY_IMAGE_UPLOAD_CAP`, 20, tracked via the `organizer_image_uploads` table since an upload can happen before any submission) are both DB-backed anti-abuse ceilings, since the IP-keyed rate limiter can't enforce a per-account cap (an organizer can trivially exceed it across IPs); both are a count-then-insert with no row lock, so both are soft ceilings (concurrent requests from one organizer can overshoot slightly) rather than a hard guarantee. **Per-locale text:** `title`/`description`/`important_info` each take optional `_en`/`_ru` siblings; `_localized()` folds them (et = the base field) into the `*_localized` JSONB columns, dropping blank locales. **Organizer-chosen category:** an optional `category` (validated against `VALID_CATEGORIES` by a Pydantic `field_validator`, 422 otherwise) is *prepended* onto `EventClassification.categories` by `_apply_organizer_category()` after inline classification, so the organizer's pick leads and any LLM-derived categories follow; a bare classification row is created if the LLM call failed, so the pick is never silently dropped. Both `url` and `image_url` are scheme-checked only (`safe_external_url()`, not the host-pinned `safe_fetchable_url()` — see `docs/security.md`'s External-URL sanitization bullet for the full fetched-vs-rendered rationale) — an organizer's own ticketing domain is never on `ALLOWED_SOURCE_HOSTS`, and these events are excluded from the daily refetch pass (see Data Flow §8 in `docs/pipeline.md`), so `url` is never fetched server-side and needs no host pin.
- **Auto-publish + post-hoc review, gated on organizer trust** — a submitted/edited event is flagged `Event.needs_review` and goes live immediately if it clears the normal publish gate (see Data Flow §6 in `docs/pipeline.md`) **and** the submitting `Organizer.verified` is true; `submitted_by_organizer_id` (indexed) attributes it back to its organizer. A brand-new organizer defaults `verified=false`, so its first submission stays `classified`/`needs_review` — never auto-published — until an admin reviews it: this closes the hole where any address that can receive one magic-link email could otherwise push a plausible-looking event with an arbitrary link straight into every user's feed and inbox with no human in the loop. Admin review queue: `GET /admin/submissions` (paginated, excludes cancelled), `POST /admin/submissions/{event_id}/retract` (pulls a submission back out of `published`), `POST /admin/submissions/{event_id}/approve` (clears `needs_review`, flips the organizer to `verified`, and runs the publish gate — every subsequent submission from that organizer auto-publishes as before). `app/publish.py::publish_pending()` enforces the gate itself (excludes any `classified` event whose `submitted_by_organizer_id` resolves to an unverified organizer, NULL-safe for non-organizer events), not just the inline call in `submit_event` — so an unapproved submission can't slip through on the next scheduled `publish_pending` pass either.

## Rich-text authoring (#267)

`description`/`important_info` (and their `_en`/`_ru` siblings) are authored as HTML in `RichTextEditor` (`frontend/src/components/RichTextEditor/`), a Tiptap toolbar wired into `EventSubmit` — bold, italic, underline, bullet/ordered list, link, heading 3-4, blockquote. Nothing else.

- **The allowlist tracks the toolbar.** `ORGANIZER_HTML_SANITIZE_ALLOWED_TAGS`/`ORGANIZER_HTML_SANITIZE_ALLOWED_ATTRS` (`app/constants.py`) are exactly the tags those extensions emit, and are backend-only (deliberately *not* generated into `shared/`, so the frontend never carries a second copy). `_organizer_sanitize()` in `organizer_events.py` passes them to `sanitize_html()` on every submit/edit; the shared ingestion allowlist is wider and stays untouched. Add a Tiptap extension → add its tag here, in the same commit.
- **Limits are per-field, not shared with ingestion:** `ORGANIZER_TITLE_MAX_LEN` (300), `ORGANIZER_DESCRIPTION_MAX_LEN` (30000), `ORGANIZER_IMPORTANT_INFO_MAX_LEN` (15000) — raised alongside rich text, since markup counts against the character budget.
- **Rendering** — `EventDetail` and `AdminEventDetail` render these fields as sanitized HTML (client-side `dompurify` as defense in depth); the server-side sanitize at write time is the real boundary. See `docs/security.md`'s Stored-HTML sanitization bullet.

## Organizer contact form

`app/routers/organizer_contact.py` (prefix `/organizer/contact`) is the sibling of the public `routers/contact.py` form, scoped to `get_current_organizer`: the body is a `message` only — name and email come off the session, so there is no honeypot and no spoofable identity. It reuses `send_contact_message()` (`app/email/contact.py`) and swallows send errors exactly as the public form does, and is rate-limited by `RATE_LIMIT_ORGANIZER_CONTACT`. The prefix must stay under `/organizer/*`: `ORGANIZER_SESSION_COOKIE_PATH` scopes the session cookie to `Path=/api/organizer`, so an organizer endpoint mounted anywhere else would silently 401. Frontend: `/organizer/contact` (`frontend/src/routes/OrganizerContact/`, `useOrganizerContactSubmit`), linked from `OrganizerTopBar`'s nav and its `MobileMenu`.

## Organizer Settings

An optional, lightweight organizer identity (#175) — a display name plus a theme preference, no logo or contact-info fields (out of scope per the parent spec, issue #173). Independent of the Saved Venues work (#171/#174, `app/routers/organizer_venues.py`): nothing on the profile prefills into `SubmitEventBody`. Restyled to match the consumer Settings page's section-based layout (Account / Display name / Security), replacing the old bespoke centered-card look.

- **Backend** — `Organizer.name` (nullable `String(255)`, `app/models/models.py`). `app/routers/organizer_profile.py` (prefix `/organizer/profile`, scoped to `get_current_organizer`) exposes `GET`/`PATCH`; `PATCH` strips whitespace and stores a blank/whitespace-only name as `NULL` rather than an empty string. The same `PATCH` also carries `theme_preference` (`Organizer.theme_preference`, `String(10)`, validated against `VALID_THEME_PREFERENCES`), mirroring `User.theme_preference` on the consumer track — an explicitly-sent `null` clears it back to System, which is why the handler keys off `model_fields_set` rather than a `None` check. See `docs/design-system.md`'s theming section for the `account → localStorage → OS` resolution order. The Security section's "log out everywhere" reuses `POST /organizer/auth/logout-all` (`app/routers/organizer_auth.py`), which mirrors the consumer `session_token_version`-bump logout-all pattern and previously had no frontend caller.
- **Frontend** — a dedicated route, `/organizer/settings` (`frontend/src/routes/OrganizerSettings/`), not folded into `/organizer/dashboard`, reachable from `OrganizerTopBar`'s nav. Renamed from `/organizer/profile` — the Account section (read-only email), Security section (log out everywhere), and Sign-in methods section (Google identity, below) are new; the display-name field/save is unchanged, just restyled into a Settings-style section.
- **Sign-in methods** — `GET /organizer/profile` additionally returns `google_linked: bool` (an `organizer_identities` existence check, `app/routers/organizer_profile.py::_is_google_linked()`); the Settings page renders linked/not-linked copy off it and, when linked, an unlink button calling `DELETE /organizer/profile/identities/google` (unconditional, no last-factor guard, bumps `session_token_version` and re-issues the caller's own cookie — see ADR 0002). No prefill of name/photo — neither is ever stored.
- **Nudge banner** — `OrganizerProfileNudge` (`frontend/src/components/OrganizerProfileNudge/`) is shown on the dashboard and submit form whenever the fetched profile's `name` is `null`, and never blocks submission. Dismissal is client-only (`localStorage`, `ORGANIZER_PROFILE_NUDGE_DISMISSED_KEY`) — there's no backend field for it, so a cleared browser just re-shows the nudge once. Its own name is unchanged (it nudges toward filling in a name, not toward "the settings page" per se) — only its link target moved to `/organizer/settings`.
