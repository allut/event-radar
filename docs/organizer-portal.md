# Organizer Portal (self-service event submission)

What's in here: the post-MVP self-service organizer portal — auth, submission, auto-publish trust gating, admin review queue. Read this before touching `app/routers/organizer_auth.py`, `app/routers/organizer_events.py`, or `frontend/src/routes/EventSubmit/`.

**Naming note:** this is a distinct concept from "Organizer Lifecycle (Fienta)" in `docs/pipeline.md` — a Fienta "organizer" there is a ticketing-source id being polled; an `Organizer` here (`app/models/models.py`) is its own account entity, a venue/promoter submitting events directly through a dedicated portal.

- **Auth** — a parallel track to the user magic-link/session stack (`app/routers/organizer_auth.py`, prefix `/organizer/auth`), with its own DB table (`organizers`, `organizer_magic_links`) and distinct signing salts (`AUTH_ORGANIZER_MAGIC_SALT`, `AUTH_ORGANIZER_SESSION_SALT`, `app/constants.py`) so an organizer token can never verify as a user token or vice versa, even though both use the same `URLSafeTimedSerializer(settings.SECRET_KEY)`. TTLs (`ORGANIZER_MAGIC_LINK_TTL_MINUTES`, `ORGANIZER_SESSION_TTL_DAYS`) mirror the user-facing defaults. `organizers.session_token_version` supports the same logout-all revocation pattern as `users.session_token_version`. Like the user track, the organizer session token is set as an httpOnly + Secure + `SameSite=Strict` cookie (`ORGANIZER_SESSION_COOKIE_NAME`, `app/constants.py`) rather than returned to client JS — but scoped `Path=/api/organizer` instead of `/api`, so an organizer endpoint ever added outside `/organizer/*` would silently 401 (see `docs/security.md`'s Auth section and `docs/adr/0001-session-tokens-in-httponly-cookies.md`).
- **Submission** — `app/routers/organizer_events.py` (prefix `/organizer/events`) lets an authenticated organizer `POST` a new event (inserted on the adapter-less `user_submission` source via the shared `insert_normalized_event()` helper, then classified + published inline within the request instead of waiting for the next scheduled pass), `PATCH`/`DELETE` (soft-delete via cancel) their own events, `GET` their own submission list, and `POST /organizer/events/image` for a signed Cloudinary image upload (secrets: `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`, `app/config.py` — log-only/`501` when unconfigured, like the contact-email Resend fallback; server-side signature so the API secret never reaches the SPA, gated by `IMAGE_UPLOAD_ALLOWED_MIME` (415) and `IMAGE_UPLOAD_MAX_BYTES` (413)). A per-organizer daily submission cap (`ORGANIZER_DAILY_SUBMISSION_CAP`, 20) and a separate per-organizer daily **image upload** cap (`ORGANIZER_DAILY_IMAGE_UPLOAD_CAP`, 20, tracked via the `organizer_image_uploads` table since an upload can happen before any submission) are both DB-backed anti-abuse ceilings, since the IP-keyed rate limiter can't enforce a per-account cap (an organizer can trivially exceed it across IPs); both are a count-then-insert with no row lock, so both are soft ceilings (concurrent requests from one organizer can overshoot slightly) rather than a hard guarantee. **Per-locale text:** `title`/`description`/`important_info` each take optional `_en`/`_ru` siblings; `_localized()` folds them (et = the base field) into the `*_localized` JSONB columns, dropping blank locales. **Organizer-chosen category:** an optional `category` (validated against `VALID_CATEGORIES` by a Pydantic `field_validator`, 422 otherwise) is *prepended* onto `EventClassification.categories` by `_apply_organizer_category()` after inline classification, so the organizer's pick leads and any LLM-derived categories follow; a bare classification row is created if the LLM call failed, so the pick is never silently dropped. Both `url` and `image_url` are scheme-checked only (`safe_external_url()`, not the host-pinned `safe_fetchable_url()` — see `docs/security.md`'s External-URL sanitization bullet for the full fetched-vs-rendered rationale) — an organizer's own ticketing domain is never on `ALLOWED_SOURCE_HOSTS`, and these events are excluded from the daily refetch pass (see Data Flow §8 in `docs/pipeline.md`), so `url` is never fetched server-side and needs no host pin.
- **Auto-publish + post-hoc review, gated on organizer trust** — a submitted/edited event is flagged `Event.needs_review` and goes live immediately if it clears the normal publish gate (see Data Flow §6 in `docs/pipeline.md`) **and** the submitting `Organizer.verified` is true; `submitted_by_organizer_id` (indexed) attributes it back to its organizer. A brand-new organizer defaults `verified=false`, so its first submission stays `classified`/`needs_review` — never auto-published — until an admin reviews it: this closes the hole where any address that can receive one magic-link email could otherwise push a plausible-looking event with an arbitrary link straight into every user's feed and inbox with no human in the loop. Admin review queue: `GET /admin/submissions` (paginated, excludes cancelled), `POST /admin/submissions/{event_id}/retract` (pulls a submission back out of `published`), `POST /admin/submissions/{event_id}/approve` (clears `needs_review`, flips the organizer to `verified`, and runs the publish gate — every subsequent submission from that organizer auto-publishes as before). `app/publish.py::publish_pending()` enforces the gate itself (excludes any `classified` event whose `submitted_by_organizer_id` resolves to an unverified organizer, NULL-safe for non-organizer events), not just the inline call in `submit_event` — so an unapproved submission can't slip through on the next scheduled `publish_pending` pass either.

## Organizer Settings

An optional, lightweight organizer identity (#175) — currently just a display name, no logo or contact-info fields (out of scope per the parent spec, issue #173). Independent of the Saved Venues work (#171/#174, `app/routers/organizer_venues.py`): nothing on the profile prefills into `SubmitEventBody`. Restyled to match the consumer Settings page's section-based layout (Account / Display name / Security), replacing the old bespoke centered-card look.

- **Backend** — `Organizer.name` (nullable `String(255)`, `app/models/models.py`). `app/routers/organizer_profile.py` (prefix `/organizer/profile`, scoped to `get_current_organizer`) exposes `GET`/`PATCH`; `PATCH` strips whitespace and stores a blank/whitespace-only name as `NULL` rather than an empty string. The Security section's "log out everywhere" reuses `POST /organizer/auth/logout-all` (`app/routers/organizer_auth.py`), which mirrors the consumer `session_token_version`-bump logout-all pattern and previously had no frontend caller.
- **Frontend** — a dedicated route, `/organizer/settings` (`frontend/src/routes/OrganizerSettings/`), not folded into `/organizer/dashboard`, reachable from `OrganizerTopBar`'s nav. Renamed from `/organizer/profile` — the Account section (read-only email) and Security section (log out everywhere) are new; the display-name field/save is unchanged, just restyled into a Settings-style section.
- **Nudge banner** — `OrganizerProfileNudge` (`frontend/src/components/OrganizerProfileNudge/`) is shown on the dashboard and submit form whenever the fetched profile's `name` is `null`, and never blocks submission. Dismissal is client-only (`localStorage`, `ORGANIZER_PROFILE_NUDGE_DISMISSED_KEY`) — there's no backend field for it, so a cleared browser just re-shows the nudge once. Its own name is unchanged (it nudges toward filling in a name, not toward "the settings page" per se) — only its link target moved to `/organizer/settings`.
