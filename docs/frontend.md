# Frontend

What's in here: the routes/components/hooks folder structure, and the i18n data pipeline (shared JSON → generated TS/Python).

Read this before touching `frontend/src/routes/`, `frontend/src/components/`, `frontend/src/hooks/`, `frontend/src/lib/`, `frontend/src/content/`, `frontend/scripts/`, `frontend/api/`, `shared/i18n/`, or `backend/app/email/`.

## Frontend Structure

Each component and route lives in its own folder containing `Name.tsx`, `Name.module.css`, and a one-line `index.ts` barrel (`export { default } from './Name'`). The barrel keeps import strings short — callers write `./components/EventCard`, not `./components/EventCard/EventCard`. **Exceptions:** `LocaleSelector/` has no `Name.module.css` — it fully delegates rendering to `SelectMenu` and has no styles of its own to hold; `Privacy/` and `Terms/` likewise have none, being one-line wrappers over `LegalPage` (which owns the styling); `SeoTags/` likewise has none, being a thin `react-helmet-async` shell with no rendered DOM to style; `AdminApp/` likewise has none, being a pure pathname dispatcher (see below) that renders no styled DOM of its own. **Route-private subcomponents skip the own-folder/barrel convention entirely** — they sit as a bare `Name.tsx` beside their parent route/component instead, since nothing outside that parent ever imports them and a folder+barrel would be indirection with no caller to shorten: `Explore/UpsellCard.tsx`, `AdminPipeline/ConfirmRunModal.tsx`, `AdminPipeline/PipelineRunBreakdown.tsx`, `RichTextEditor/icons.tsx` (toolbar glyphs, not a component). The pattern is consistent and intentional — don't promote one to a folder without a second, cross-parent importer showing up.

- Routes (pages) in `frontend/src/routes/`: `Landing/`, `Login/`, `AuthVerify/`, `Onboarding/`, `Feed/`, `Explore/`, `SavedEvents/`, `EventDetail/`, `Settings/`, `Unsubscribe/`, `Privacy/`, `Terms/`, `Contact/`, `NotFound/`, plus the organizer portal's `OrganizerLogin/`, `OrganizerVerify/`, `OrganizerDashboard/`, `OrganizerSettings/`, `OrganizerContact/`, `EventSubmit/` (routed at `/organizer/login`, `/organizer/verify`, `/organizer/dashboard`, `/organizer/settings`, `/organizer/contact`, `/organizer/submit`, and reused at `/organizer/events/:id/edit` — see `docs/organizer-portal.md`). The admin console — `AdminLogin/`, `AdminDashboard/`, `AdminReports/`, `AdminSubmissions/`, `AdminPipeline/`, `AdminDedup/`, `AdminEventDetail/` (`/admin/login`, `/admin`, `/admin/reports`, `/admin/submissions`, `/admin/pipeline`, `/admin/dedup`, `/admin/events/:id`) — is the operator-facing replacement for curl-driven `/admin/*` calls (see `docs/backend-ops.md`'s Admin Endpoints section); its own `AdminApp.tsx` dispatches on `pathname` outside `App.tsx`'s `ROUTE_DEFS`/locale-prefix loop (no i18n, entry is typed-URL/bookmark only) and is behind one `React.lazy` chunk so a signed-out visit to a public route never downloads it; `AdminShell/` (`frontend/src/components/`) is the persistent nav-rail chrome every authenticated `/admin/*` screen renders inside. `AdminPipeline/ConfirmRunModal` and `AdminPipeline/PipelineRunBreakdown` are route-local subcomponents beside it, as is `Explore/UpsellCard` (the signed-out sign-in upsell rendered on `/explore`). `Landing/` is the logged-out marketing page (hero markup lives directly in `Landing.tsx` — there is no separate `RadarHero` subcomponent); `App.tsx`'s `Home` picks `Landing` vs `Feed` off `useAuth()` — a live subscription, **not** a one-shot `isAuthenticated()` read, so signing out while already on `/` swaps the page instead of stranding a stale Feed. `Privacy/` and `Terms/` are one-line wrappers over the shared `LegalPage` component (which renders `TopBar` + a structured legal doc loaded per-locale from `frontend/src/content/legal/`, e.g. `privacy.en.ts`); `Contact/` renders its own `TopBar` + the contact form (via `useContactSubmit`). The organizer routes sit behind their own `OrganizerProtected` guard (`App.tsx`, mirrors `Protected` but reads `useOrganizerAuth()` and redirects to `/organizer/login`) — the user and organizer auth tracks never share a route guard, matching their separate token/salt tracks (see `docs/security.md`).
- Shared components in `frontend/src/components/`: `EventCard/`, `PersonaCard/`, `ErrorBoundary/`, `PageState/`, `LocaleSelector/`, `FeedbackButtonRow/`, `EmptyState/`, `Toast/` (transient success/error banner, driven by `useToast`), `TopBar/`, `OrganizerTopBar/` (top nav for the organizer portal routes, parallel to `TopBar/`), `MobileMenu/`, `Footer/`, `StaticPage/`, `LegalPage/`, `AuthCard/` (shared page/card/radar/brand shell + status block for `AuthVerify`, `OrganizerVerify`, and `Unsubscribe`), `MagicLinkForm/` (email input + submit + success/resend block shared by `Login` and `OrganizerLogin`), `SeoTags/` (thin `react-helmet-async` shell — see `useSeoMeta` below), plus the Explore filter-control primitives `Chip/`, `FacetMenu/`, `SelectMenu/`, `SegmentedControl/`, `Toggle/`, and the themed form controls `DatePicker/`, `SelectField/`, `FileField/`. `EventCard/index.ts` also re-exports `type EventData`. `Modal/` is a generic dialog shell (focus trap, Escape/backdrop close, ARIA) used by the report-event flow; `EventOverflowMenu/` is the kebab trigger + Share/Report popover shared by `EventCard` and `EventDetail`, built on `useDropdown` like `FacetMenu`/`SelectMenu`. The admin console's own shared components: `AdminQueueActionPanel/` (the note-field + action-buttons block shared by `AdminReports`/`AdminSubmissions`/`AdminEventDetail`'s resolve/take-down/approve/retract flows) and `AdminQueueSplitView/` (the generic list-column + detail-panel layout `AdminReports`/`AdminSubmissions` both render their queue through). `TopBar/` is the shared top nav (home/explore/saved links + `LocaleSelector` + `MobileMenu` hamburger on mobile); `OrganizerTopBar/` reuses the same `MobileMenu` component for its own mobile hamburger, passing organizer nav links via `MobileMenu`'s `navItems`/`navAriaLabelKey` props; `FacetMenu`/`SelectMenu` are trigger-button + popover dropdowns built on the `useDropdown` hook (multi-select `Chip` grids and single-select respectively). `Footer/` is the globally mounted site footer (Privacy/Terms/Contact links + social links, reads locale via `useLocale`); `LegalPage/` renders a localized legal document (own `TopBar` + rich sections from `content/legal/`) and backs the Privacy/Terms routes; `StaticPage/` is a shared flat-text page scaffold (`TopBar` + body) whose component has no importer today — only its stylesheet is live (`Contact.module.css` composes `.page`/`.main`/`.title`/`.body` from it) — kept as a scaffold for future static pages. The themed form controls back the organizer submit/edit form (`EventSubmit/`), replacing native `datetime-local`/`<select>`/`<input type="file">`: `DatePicker/` is a calendar + time popover built on `useDropdown` (date/grid helpers in `utils.ts`, literals in `constants.ts`), `SelectField/` is a single-select listbox popover over `ChipOption`s, `FileField/` is a file-picker + preview shell for the Cloudinary image upload, `VenuePicker/` is the saved-venue directory picker + inline create/edit (`organizerApi`, see `docs/data-model.md`'s `venues` entry), and `RichTextEditor/` is the Tiptap toolbar + editor backing the submit form's `description`/`important_info` fields (its toolbar glyphs are local inline SVGs in `RichTextEditor/icons.tsx`; the server re-sanitizes against the narrower organizer allowlist — see `docs/organizer-portal.md`). The remaining shared components: `DateRangeMenu/` is Explore's from/to calendar popover with presets (`DATE_PRESETS`), parallel to `DatePicker` but range-valued; `ReportModal/` is the report-an-event form built on `Modal` (`POST /reports`); `SignInModal/` is the signed-out upsell (`Modal` + `MagicLinkForm`, copy variant per `SIGN_IN_TRIGGER_COPY`, GA4-tracked) shown when an anonymous Explore visitor tries to save or rate; `ThemeSelector/` is the `TopBar`/`OrganizerTopBar` theme control (`SelectMenu` over `THEME_OPTIONS`, writes `lib/theme.ts` and `PATCH`es whichever auth track is signed in), with `AdminThemeToggle/` its localStorage-only counterpart in `AdminShell`'s foot area (the console has no accounts to sync to); `OrganizerProfileNudge/` is the dashboard/submit "set a display name" banner.
- **Locale-prefixed routing** — every route in `App.tsx`'s `ROUTE_DEFS` is registered twice: once at its bare `ROUTES.*` path (Estonian) and once under a `/:locale` prefix (`localePrefixedPattern`), so `/en/...`/`/ru/...` reach the same element. Two route classes: Home (`/`), `Explore` (`/explore`, issue #236) and `EventDetail` (`/events/:id`) are `noRedirect: true` — the three public SEO routes, whose bare path always renders Estonian and never redirects, regardless of any stored preference (crawler/prerender stability). Every other route is wrapped in `BareLocaleGate`, which redirects a bare visit to the stored preference's prefixed URL when that preference (`getStoredLocale()`, distinct from `getLocale()`'s UI-default fallback) is explicitly set to something other than Estonian; a first-time visitor with no stored preference is left on the bare path. An unrecognized `:locale` segment (e.g. `/xx/...`) falls back to Estonian content without redirecting the URL. `useRouteLocale()` (`frontend/src/hooks/`) resolves the current `:locale` param the same way, for callers that just need the value. `useLocaleMutation` resolves its `locale` from the URL segment when present, else from the stored preference (or Estonian for `publicRoute: true` callers — Feed/Landing/Explore/EventDetail); switching locale navigates to the equivalent prefixed path (`localizedPath`/`stripLocalePrefix`, defined in `frontend/src/lib/urlLocale.ts` and re-exported through `utils.ts` — the one deliberate exception to "all shared helpers in `utils.ts`", explained in that module's own comment) in addition to its existing `localStorage`/`PATCH /users/me` persistence. `Protected`/`OrganizerProtected` guards sit inside this wrapper, unaffected by it.
- Tests co-located as `Name.test.tsx` / `Name.test.ts` beside each subject file. Shared test helpers and factories live in `frontend/src/test/` (`setup.ts`, `utils.tsx`). Stack: Vitest + @testing-library/react + jsdom.
- Shared CSS base classes in `frontend/src/components/shared/`: `Card.module.css` (`.card`, `.cardAccentTop`, `.cardDangerTop`, `.cardPage`), `Button.module.css` (`.btnPrimary`, `.btnOutline`), `Menu.module.css` (`.menu`, `.menuPop`, `.triggerButton`/`.triggerButtonActive`, `.triggerInline`/`.triggerInlineActive` — the popover/trigger chrome shared by `FacetMenu`, `SelectMenu`, `MobileMenu`, `DatePicker`, and `SelectField`), and `Animations.module.css` (`.spin`, `.breathe`, `.rise` + their `@keyframes`, tuned per call site via `--spin-duration` / `--breathe-duration` / `--rise-distance` custom properties). Compose from these via CSS Modules `composes` — never copy-paste the same card/button/menu rules into route or component stylesheets. Component CSS composes from `'../shared/X.module.css'`; route CSS from `'../../components/shared/X.module.css'`. All 16 shared modules, the token system they draw on, and the visual rules governing them are documented in `docs/design-system.md` — read it before a visual change. `GoogleSignInButton/` (`frontend/src/components/shared/`) is a plain `<a href>` to the backend's OAuth `start` endpoint — no client-side OAuth logic — composing `btnOutline` and rendering `GoogleGMark`, the real Google "G" mark lifted verbatim from `signin-assets.zip` and inlined in the DOM (never `<img>` — see `docs/adr/0002-google-sign-in-oauth-pkce.md`); its Light/Dark plate colors are Google-mandated hex triples held as `--google-btn-*` tokens in `index.css`, not the app's own palette. Gated by `VITE_GOOGLE_SIGNIN_ORGANIZER_ENABLED`/`VITE_GOOGLE_SIGNIN_CONSUMER_ENABLED` (Vercel build vars, unset in dev, pattern of `VITE_GA_MEASUREMENT_ID`/`VITE_API_BASE`) — frontend-only convenience gate, the backend `start` endpoint 404s independently when its own flag is off.
- API client in `frontend/src/api/client.ts` — `api` (consumer session token) plus a thin `organizerApi` wrapper that passes `{ organizer: true }` on every call, so organizer routes/hooks never have to remember the flag; a 401 clears the matching token and redirects to `/login` or `/organizer/login` respectively. `FormData` bodies (the image upload) skip JSON stringification and the explicit `Content-Type`. React Query used for server state (`@tanstack/react-query`).
- Custom hooks in `frontend/src/hooks/`: `useAuth.ts` (live auth-state subscription), `useLocale.ts` (live locale subscription, mirroring `useAuth` — lets the globally mounted `Footer` re-render on a locale switch from any page), `useLogout.ts` (clear token + redirect), `useMagicLinkRequest.ts` (request-link mutation), `useFeedback.ts` (feedback signal dispatch), `useLocaleMutation.ts` (locale-switch mutation), `useContactSubmit.ts` (contact-form submit mutation), `useDropdown.ts` (open/close + outside-click + Escape + focus + mobile-flip for trigger-button popovers), `useToast.ts` (transient success/error toast state with auto-clear), `useEventReport.ts` (report-modal open/close + sign-in gate + cache invalidation for `ReportModal`), `usePrefersReducedMotion.ts` and `useThemePreference.ts` (both `useSyncExternalStore` subscriptions — the media query and `lib/theme.ts`'s stored preference), and the locale-routing trio `useLocalePath.ts` (locale-prefix an internal `to` against the current URL — every `<Link to>`/`navigate()` target goes through it), `useLocaleNavigate.ts` (the `useNavigate()` wrapper that does the same for programmatic navigation), and `useLocalLocale.ts` (local mirror of the global locale for the switcher routes, so their own tree re-renders immediately). Plus the organizer-track equivalents `useOrganizerAuth.ts` (live organizer-session subscription, backs `OrganizerProtected`), `useOrganizerLogout.ts`, `useOrganizerEventForm.ts` (submit/edit form state for `EventSubmit/`), `useOrganizerContactSubmit.ts` (the `/organizer/contact` mutation, parallel to `useContactSubmit`), and the admin-track ones `useAdminAuth.ts`/`useAdminLogin.ts`/`useAdminLogout.ts` (a third, independent auth track over `lib/adminAuth.ts`) and `useTriggerRun.ts` (streams one `AdminPipeline` trigger's NDJSON run, tracking cold-start/streaming/disconnected state). `useSeoMeta.ts`/`useStaticSeoMeta.ts`/`useRouteLocale.ts` are covered in their own sections below.
- Auth helpers in `frontend/src/lib/auth.ts` (token + locale storage, `isAuthenticated()`, `beginLogout()`/`isLoggingOut()`, a `subscribeAuth()` emit/subscribe store that `useAuth()` reads, and a parallel `getLocale()`/`subscribeLocale()` store that `useLocale()` reads), with `frontend/src/lib/organizerAuth.ts` mirroring it for the organizer track (its own `ORGANIZER_TOKEN_KEY` storage key, `isAuthenticatedOrganizer()`, `beginOrganizerLogout()`/`isOrganizerLoggingOut()`, `subscribeOrganizerAuth()` behind `useOrganizerAuth()`; no locale store of its own — locale stays in `auth.ts`) — the two token stores never share a key, matching the separate backend salts. Components must go through `useAuth()`/`useOrganizerAuth()` — never read `isAuthenticated()` directly in render, or auth changes won't re-render.

## i18n

**Single source of truth:** `shared/i18n/{en,et,ru}.json` — split into `"ui"` (frontend strings) and `"email"` (backend digest/magic-link strings). `shared/personas.json` holds persona names + vibes per locale. `shared/app-config.json` holds cross-stack scalars and taxonomies. `shared/calendar.json` holds localized `day_names`/`month_names` (generated into the backend's `DAY_NAMES`/`MONTH_NAMES`).

**Workflow:** Edit the JSON files in `shared/` → run `python scripts/generate_shared.py` → commit both the JSON and the updated `_generated` files. Never edit `_generated/` directly.

- **Frontend** — `frontend/src/i18n.ts` re-exports helpers (`t`, `ti`, `personaName`, `personaVibe`) and imports strings from `frontend/src/_generated/i18nData.ts`. `frontend/src/constants.ts` imports `LOCALES`, `PERSONAS`, TTL, and weight thresholds from `frontend/src/_generated/sharedConstants.ts`.
- **Backend** — `backend/app/i18n.py` re-exports helpers (`t`, `ti`, `day_name`, `month_name`) and imports `TRANSLATIONS`, `DAY_NAMES`, `MONTH_NAMES` from `backend/app/_generated/i18n_data.py`. `backend/app/constants.py` imports cross-stack scalars and frozensets from `backend/app/_generated/shared_constants.py`.
- **Email styling** — `backend/app/email/styles.py` holds `EMAIL_CSS` (shared progressive-enhancement `<style>` block) plus `S_*` inline-style constants, split into shared page chrome (reused by every email type) and per-email groups (event card for the digest, body/note styles for the magic link). `backend/app/email/templates.py` holds the shared `EMAIL_DOCUMENT` page shell (header/content/footer row placeholders) plus per-email header/body/footer templates that fill those slots, and the digest's `EVENT_*` card markup. New email types add their own header/body/footer templates and reuse `EMAIL_DOCUMENT` rather than duplicating the shell.
- **Email digest** — `backend/app/email/digest.py` handles data formatting + assembly and Resend delivery, filling `EMAIL_DOCUMENT` with `DIGEST_HEADER`/`DIGEST_FOOTER`. The digest matches the site's visual design: each event block includes its `image_url` (escaped, falls back to a plain color band when absent) and the header carries an "open feed" button linking to the frontend app (`feed_url`). HTML only, no plain-text part. All subjects, labels, and day/month names resolved via `app/i18n.py`. New email types must follow the same three-file split: presentation CSS in `styles.py`, markup in `templates.py`, assembly + delivery in a dedicated module.
- **Magic-link email** — `backend/app/email/magic_link.py` (`build_magic_link_html`/`build_magic_link_text`) fills `EMAIL_DOCUMENT` with `MAGIC_LINK_HEADER`/`MAGIC_LINK_BODY`/`EMAIL_FOOTER_BRAND`, matching the digest's visual system (dark page, gold CTA button). Sends both an HTML and a plain-text part — unlike the digest, since this is a transactional/deliverability-sensitive send. Called from `app/auth/email.py::send_magic_link`, which stays on a raw (non-retrying) `httpx` call for the reason documented inline (see `docs/security.md`'s Auth section).
- **Contact email** — `backend/app/email/contact.py` (`send_contact_message`) delivers a contact-form submission to the owner inbox (`settings.CONTACT_TO_ADDRESS`, `reply_to` set to the sender) via Resend. This is **internal-only** mail (not user-facing branding), so it deliberately skips the `EMAIL_DOCUMENT` shell / `styles.py` / `templates.py` split and inlines escaped plain markup — the documented exception to the three-file rule. Falls back to log-only when `RESEND_API_KEY` is unset. Called from `app/routers/contact.py::submit_contact` (`POST /contact`, honeypot + `RATE_LIMIT_CONTACT`), which swallows send errors so no email failure surfaces to the caller.
- **Drift guard** — `backend/tests/test_generated_sync.py` runs the generator into a temp dir and asserts byte-identical output. If it fails: `python scripts/generate_shared.py` and commit.

## SEO: meta tags, structured data, prerendering

- **`useSeoMeta`** (`frontend/src/hooks/useSeoMeta.ts`, pure builder `buildSeoMeta`) — every route's `<title>`/`<html lang>`/default `noindex`; Landing and `/events/:id` additionally pass `indexable: true` for OG tags, a self-referential canonical, and hreflang alternates (`en`/`et`/`ru` + `x-default`). Every other route goes through the thin `useStaticSeoMeta` wrapper (`frontend/src/hooks/useStaticSeoMeta.ts`). Rendered via `<SeoTags meta={...} jsonLd={...} />` (`frontend/src/components/SeoTags/`), a thin `react-helmet-async` shell.
- **Structured data** — `frontend/src/lib/structuredData.ts` builds schema.org JSON-LD typed against `schema-dts`: `buildEventJsonLd` (event detail — never emits `organizer` or `offers.availability`, since neither is backed by real data; emits an `AggregateOffer` with `lowPrice`/`highPrice`/`priceCurrency` whenever `price_min !== null` — numeric-truthiness, so a free event's `price_min: 0` still emits `lowPrice: 0` — falling back to a plain `Offer` otherwise, issue #236; `priceCurrency` defaults to `DEFAULT_CURRENCY` when `event.currency` is null, since `seoValidation.ts`'s validator requires `priceCurrency` unconditionally once `lowPrice` is present and a free event legitimately loses its currency at ingest — dropping it would silently drop the price offer's rich-result eligibility instead), `buildWebsiteJsonLd` (Landing — `name`/`url`/`inLanguage` only), and `buildExploreItemListJsonLd` (`/explore`, issue #236 — one `ListItem` per rendered card, `position` matching render order; each `item` is the *full* `buildEventJsonLd` payload per event — issue #224 governs over #232's since-superseded "minimal item" note, see issue #236's own contradiction writeup — plus a top-level `url` on that item pointing at the locale-matched canonical detail page, distinct from `offers.url`'s external ticket link).
- **Build-time prerender pipeline** (`frontend/scripts/prerender.ts`) — runs as the last step of `npm run build` (after `tsc --noEmit && vite build`) whenever `$VERCEL` or `$PRERENDER_LOCAL` is set, so `vercel build` produces it automatically; a plain local `npm run build` skips both the Playwright browser install and this pass entirely (see "Local dry run" below for the opt-in). It fetches every published event id from `GET /public/prerender-events` (`backend/app/routers/public.py::prerender_events` — the single source of truth for "what's published", also reused by `sitemap.xml` generation), boots the just-built `dist/` under `vite preview` (its `preview.proxy` config in `vite.config.ts` forwards `/api` to a real backend — `PRERENDER_API_ORIGIN` env var, defaulting to the same Render origin `vercel.json`'s `/api/:path*` rewrite already targets), and drives it with Playwright (bounded worker pool, `RENDER_POOL_CONCURRENCY` in the script — `PRERENDER_CONCURRENCY`'s width off Vercel, forced down to 1 on Vercel to avoid adding contention on top of `@sparticuz/chromium`'s `--single-process` launch; `NAV_TIMEOUT_MS`/`CONTENT_READY_TIMEOUT_MS` are also both 3x wider on Vercel — confirmed by local repro that this same single-process, software-rendered Chromium is simply slower on Vercel's shared 2-core build machine, independent of concurrency) to snapshot Landing, `/explore` (issue #236), and every published `/events/:id`, across all three locale-prefixed URL variants. `/explore`'s target carries no `eventId`/`updatedAt` (same shape as home) and is appended right after home in `buildTargets`, never at index 0 — the live audit reads sitemap freshness off the *first* `<lastmod>`, which depends on home staying first; that same no-`eventId` shape is what makes `classifyTarget` treat it as always-render-fresh (never copy-forward) for free. `eventDetailRateGate` (`GET /events/{id}`'s budget) is keyed on `target.eventId !== undefined`, not `bare !== ROUTES.home`, so `/explore` doesn't consume it. Readiness is deliberately decoupled from indexability for `/explore` (unlike Landing/`/events/:id`, whose canonical-link-attached wait doubles as both signals): `Explore.tsx` sets a `data-prerender-ready="true"` marker once its query settles — `isSuccess` **or** `isError`, never `isLoading` — which `snapshotTarget` waits on instead of the canonical-link selector, and a sibling `data-prerender-error="true"` marker on `isError` that makes `snapshotTarget` throw (routed through the same `failures[]`/build-throw path as any other render failure) rather than silently shipping a `noindex` page. Browser launch (`launchBrowser`) is environment-gated: off Vercel it's Playwright's own bundled Chromium (`playwright install chromium`, the `npm run build` step ahead of this script — skipped on Vercel, since the binary it fetches would go unused there) unchanged; on Vercel (`process.env.VERCEL` set) it launches `@sparticuz/chromium` explicitly instead, with `VERCEL` left visible through the import/`executablePath()` call — `@sparticuz/chromium`'s own AL2023 self-detection keys off `VERCEL` being set to decide whether to extract its bundled `libnspr4.so`/`libnss3.so`/`libnssutil3.so` and point `LD_LIBRARY_PATH` at them; hiding `VERCEL` (an earlier attempt, since reverted — see "Traceability: Vercel prerender build hang + crash-loop" issue #72) skips that extraction and crashes the launch with a missing-shared-library error instead. Each snapshot is written to `dist/<locale-prefix>/.../index.html` — the same directory-index shape Vercel's static file server resolves before falling through to a rewrite, so a prerendered path is served as-is without touching `vercel.json`. A page is considered "rendered" once its `<link rel="canonical">` is attached (only present once `useSeoMeta`'s `indexable` flips true, which for `/events/:id` only happens after the event has actually loaded — see `EventDetail.tsx`). The script fails the build (non-zero exit) if the published-events fetch fails or if any target can't be reached/rendered within its timeout.
- **The SPA fallback shell** — `dist/index.html` (the plain CSR entry `vite build` produces) is copied to `dist/app-shell.html` *before* the bare-Estonian Landing snapshot overwrites `dist/index.html`. `vercel.json`'s catch-all rewrite (`/((?!api/|assets/|_vercel/).*)`) targets `app-shell.html`, not `index.html`, so every non-prerendered route (`/saved`, `/settings`, etc.) keeps serving the untouched CSR shell rather than a stale/mismatched snapshot — `/explore` is prerendered as of issue #236 and lands at `dist/explore/index.html`, no longer part of this untouched-CSR-shell set. `assets/` was added to the negative lookahead (issue #97) so a `dist/assets/*` path that doesn't actually exist 404s for real instead of silently matching the catch-all and getting served `app-shell.html` as a 200 `text/html` response — a browser then rejects that as a stylesheet/module script under strict MIME sniffing, which is exactly the failure mode the next bullet's fix targets. Vercel's static file server resolves an existing hashed asset before rewrites run, so this exclusion changes nothing for a real asset request.
- **Change detection & copy-forward asset refs** (issue #80/#82/#97) — every round, `classifyTarget` fetches each event route's *currently-live* production page and diffs its embedded `dateModified` marker (`embedChangeMarker`/`extractChangeMarker`, keyed on `Event.updated_at`) against the target's. An exact match (`unchanged`) copies that live HTML straight to `dist/` with no Playwright render at all — the mechanism that keeps a 4000+-route catalog's per-round render budget survivable; a mismatch (or no live page yet) renders fresh. The same live HTML is also held as a stale-but-real fallback (issue #82) for a route the render budget runs out before reaching, written out after the render pool once it's known which targets were actually skipped. Both write sites route through `rewriteSnapshotAssetRefs(html, shellHtml)` before hitting disk: a copied-forward page is a byte-for-byte capture of a *previous* build's rendered HTML, complete with that build's content-hashed `dist/assets/*` filenames, which Vite re-mints on every source change — with nothing else re-validating a copied-forward snapshot (see the in-build gate's `selectValidationTargets` scoping below), those dead references would otherwise ship to users indefinitely, silently, across every future deploy once the current build's real assets replace the ones being referenced. `rewriteSnapshotAssetRefs` swaps the stale `<head>` `<script>`/`<link>` asset nodes for `shellHtml`'s current ones (order preserved, everything else — JSON-LD, the change marker, Helmet's `data-rh` tags — untouched byte-for-byte) and throws if `shellHtml` itself carries zero asset references, since a silent no-op there would just reintroduce the bug. `shellHtml` is read once per round from `dist/app-shell.html` (`APP_SHELL_FILENAME`), never `dist/index.html` — the latter gets overwritten by the home-route snapshot partway through the same round, so it's not guaranteed pristine. Self-healing: every target is reclassified every round, so the very next production build rewrites every previously-shipped copied-forward snapshot's stale refs, no manual backfill needed. The in-build validation gate's exemption for copied-forward routes (`selectValidationTargets`, issue #94) stays correct despite this: that gate only checks SEO structure (title/canonical/hreflang/JSON-LD), never asset references, so nothing it does was ever aware of — or a defense against — this asset-hash class of bug in the first place.
- **Snapshots are theme-neutral** (theme-revert-on-refresh fix) — every write site (`snapshotTarget`'s fresh render, and both copy-forward/stale-fallback writes in `main()`) routes through `finalizeSnapshotHtml`, a single choke point that runs `rewriteSnapshotAssetRefs` (copy-forward sites only) then `stripBakedThemeAttr` on the way to disk. `page.content()` captures the build browser's own `document.documentElement.dataset.theme` — set by `index.html`'s pre-paint script against whatever OS theme the build machine happens to have, since there's no `localStorage` in that browser — and without stripping it, every visitor would see the build machine's theme baked in until client JS re-resolved it. `stripBakedThemeAttr` leaves every other `<html>` attribute (`lang`, `data-rh`) untouched and is idempotent; an absent `data-theme` falls through to the dark origin palette only until the pre-paint script (unblocked by the CSP hash — see `docs/security.md`) sets the real value before first paint.
- **`sitemap.xml` + `robots.txt`** (`frontend/scripts/prerender.ts`'s `buildSitemapXml`/`buildRobotsTxt`) — written to `dist/` before the Playwright snapshot pass, off the same `targets` list `buildTargets` produces from the published-event ids, so the sitemap can never list a URL the snapshot pass doesn't also cover. Each target becomes one `<url>` entry (`<loc>` + a `<lastmod>` — `target.updatedAt` when the target has a backing `Event`, else the build timestamp for e.g. home/`/explore`) plus `en`/`et`/`ru`/`x-default` `<xhtml:link rel="alternate">` cross-references, mirroring `useSeoMeta`'s hreflang set. `robots.txt` is an inverse allowlist (`Disallow: /` then explicit `Allow:`s for `/`, `/events/`, `/explore` (**not** `$`-anchored, unlike the home-route `Allow: /$` — a filtered `/explore?category=…` URL must stay crawlable per the canonical-alone crawl-control decision: no `Disallow` on query strings, no param-conditional `noindex`), and their `/en`/`/ru` equivalents, plus a `Sitemap:` directive) so a new authenticated route added later is excluded by default with no robots.txt edit required.
- **Local dry run** — `PRERENDER_LOCAL=1 PRERENDER_API_ORIGIN=http://127.0.0.1:8000 npm run build` (with a local backend running) opts back into the full pipeline against dev data instead of production; `PRERENDER_LOCAL` alone (without `PRERENDER_API_ORIGIN`) exercises it against production data instead.
- **In-build validation gate** (issue #53, `frontend/src/lib/seoValidation.ts` + `prerender.ts`'s `validateTarget`) — runs immediately after every snapshot is written (still inside `prerender.ts`'s `main()`), reads each one back off disk, and checks two assertion categories, **blocking the deploy (non-zero exit)** on either. Scoped to only this round's newly-rendered routes (`selectValidationTargets`, issue #94) — copied-forward routes are byte-identical to what already passed this same gate in an earlier round, so the `prerender: validated N snapshot(s)` log line's `N` is this round's `newlyRendered` count, not the full route set: (1) *structural correctness* — `validateSnapshotStructure` requires a non-default `<title>` (not the app-shell's bare `t('brand', locale)`), a `<link rel="canonical">` on `PRODUCTION_ORIGIN`, all of `SEO_HREFLANG_CODES`'s `<link rel="alternate" hreflang>` alternates, `<meta name="robots" content="index, follow">`, and exactly one valid `<script type="application/ld+json">` — validated by `assertEventJsonLd`/`assertWebsiteJsonLd`/`assertListJsonLd` (`kind: 'event' | 'website' | 'list'`), a hand-rolled runtime check against Google's documented *required* Event fields (`name`, `startDate`, `location`) plus its "image or offers" recommendation (never `eventStatus`/`organizer`/`offers.availability` — those stay unchecked, matching `structuredData.ts`'s deliberate omissions), plus a narrow structural check on `offers.lowPrice`/`highPrice`/`priceCurrency` that only fires once `lowPrice` is present (issue #236); `assertListJsonLd` (issue #236, `/explore`'s `ItemList`) additionally checks `@type`/`itemListElement` shape, exact `1..n` `position` sequencing, every entry's `item` against `assertEventJsonLd` itself (prefixed `item[i]: …`), `item.url` uniqueness/origin/no-fragment, and `item.image` presence (stricter than `assertEventJsonLd`'s own image-or-offers check) — its `itemListElement.length >= 3` check is skipped when a passed-in `liveItemCount` (a live re-query of `GET /explore`, mirroring `compareEventStaleness`'s live re-fetch, `prerender.ts`'s `fetchLiveExploreCount`) proves the catalog itself would render fewer than 3 items, distinguishing a genuinely thin calendar from a builder regression without hardcoding a minimum — `fetchLiveExploreCount` returns not the raw `total` but that count adjusted for the anonymous-view upsell card, which always drops exactly one fetched event to make room for itself (`Explore.tsx`'s `gridItems`); prerendering is always anonymous (Playwright never signs in), so comparing against the unadjusted total would fail every 3-event catalog's build over a UI layout decision, not an actual regression; (2) *non-staleness* — `compareEventStaleness` re-fetches `GET /events/{id}` (sharing `prerender.ts`'s `eventDetailRateGate` budget) and diffs the snapshot's title/venue (read straight off its own JSON-LD, an exact mirror of `event.title`/`venue_name`/`venue_address`) and price against what the live API returns right now. Price isn't part of the JSON-LD payload (issue #46 defers `AggregateOffer`), so `EventDetail.tsx`'s price `<span>` carries `data-testid="event-price"` plus `data-price-min`/`data-price-max`/`data-currency`/`data-has-free-tier` attributes as a machine-readable marker, present exactly when `formatPrice` would render (i.e. `price_min !== null` — see the comment on `compareEventStaleness`). `seoValidation.ts` is deliberately filesystem/network-free (parses an HTML string, compares against a passed-in live-event object) so the independent live-audit ticket (issue #54) can reuse `parseSnapshotHtml`/`validateSnapshotStructure` unchanged against a `fetch()`-ed production page instead of a local `dist/` file, rather than reimplementing the checks. `/explore` has no non-staleness diff (issue #236) — it's exempt from copy-forward (always renders fresh, see above), so there's no earlier snapshot to diff against.
- **Independent live audit** (issue #54, `frontend/api/seo-audit.ts` + `src/lib/seoAudit.ts`/`seoAuditIssue.ts`/`seoAuditAuth.ts`) — a Vercel Serverless Function, hit every 6h by its own cron-job.org job (offset from the issue #52 prerender-rebuild job), that checks *production*, not a build in progress: the one check that can catch a silently-dead Deploy Hook/cron, since it doesn't depend on any build having run at all. `evaluateLiveAudit` (network-free, unit-tested) checks robots.txt crawlability plus freshness plus structural regressions: (1) reuses `isPathAllowedByRules` (Google's robots.txt matching semantics) against the just-fetched `robots.txt` to flag `sitemap.xml`, the OG fallback image, the built `/assets/`, and each `CRAWLABLE_ICON_PATHS` entry as blocked — the motivating bug for issue #54: a stray `Disallow: /` silently caught `/sitemap.xml` and Google Search Console reported "Couldn't fetch" with nothing else in the pipeline any wiser; (2) treats sitemap.xml's `<lastmod>` (`target.updatedAt` when available, else the build timestamp) older than `SEO_AUDIT_STALE_THRESHOLD_HOURS` (8h — the 6h backend publish/geocode cadence plus a 2h buffer) as a dead cadence; (3) reuses `parseSnapshotHtml`/`validateSnapshotStructure` unchanged (the same reuse `seoValidation.ts`'s module comment anticipated) against `PRODUCTION_ORIGIN/`'s live HTML (`kind: 'website'`) to catch a structural regression that made it to production; (4) does the same against one live `/events/:id` page (`kind: 'event'`, so `assertEventJsonLd` is actually exercised against production, not just Landing's `assertWebsiteJsonLd`) — `api/seo-audit.ts` picks the first bare-Estonian event URL off sitemap.xml via `parseSitemapEventUrls`, best-effort (an empty catalog, or a single flaky event fetch, doesn't fail the whole audit — freshness and Landing are still checked either way); (5) does the same against `/explore`'s canonical URL, all 3 locales (`kind: 'list'`, issue #236) — also best-effort per locale, and with no `liveItemCount` re-query here (unlike the in-build gate), so `assertListJsonLd`'s `>=3` check simply no-ops for the live audit. Separately, `api/seo-audit.ts` itself (not `evaluateLiveAudit`) fetches `/favicon.ico` and flags a non-`image/*` content-type — catching Vercel's SPA-catch-all-rewrite fallthrough, where a missing favicon silently 200s as the HTML app shell instead of 404ing (see `FAVICON_ICO_PATH`'s comment in `constants.ts`). The same app-shell-fallthrough failure mode, for the fetched event snapshot's own built assets rather than the favicon (issue #97): `parseSnapshotAssetUrls` (`src/lib/seoAudit.ts`, pure — pulls every `/assets/*` `src`/`href` out of `eventHtml`) feeds `api/seo-audit.ts`'s fetch of each one, asserting a `text/css`/`javascript` content-type; a mismatch means the snapshot still references a previous build's now-dead asset hash. Alert-only — never blocks anything, per issue #46's Regression checks; a failure calls `seoAuditIssue.ts`'s `reportAuditFailure` (files a new GitHub issue labeled `seo-audit-failure`, or comments on the existing open one instead of duplicating on repeat failures), a pass calls `reportAuditRecovery` (closes the open issue, if any — a no-op otherwise). Auth is a shared-secret header (`x-seo-audit-token` against `SEO_AUDIT_TOKEN`, constant-time-compared by `seoAuditAuth.ts`'s `isValidAuditToken`, mirroring the backend's `/internal/tick` pattern in spirit but with its own distinct header name) plus a `GH_ISSUE_TOKEN` (GitHub PAT, Issues: write on `allut/event-radar`) for the issue-filing calls — both are Vercel project env vars, set only in the dashboard (see `docs/backend-ops.md`).
  - **Routing**: this function lives at `/api/seo-audit`, which collides with `vercel.json`'s `/api/:path*` → Render-backend rewrite unless that rewrite explicitly excludes it. The rewrite's `source` is `/api/:path((?!seo-audit/?$|prerender-cadence/?$).*)` — a negative-lookahead group (the same pattern Vercel's own docs use for a locale-style catch-all exclusion; each `/?` also excludes an accidental trailing-slash request, e.g. `/api/seo-audit/`), so every `/api/*` request except the exact `/api/seo-audit` and `/api/prerender-cadence` paths still proxies to the backend unchanged. **Any further path added under `frontend/api/`** needs the same exclusion added to this pattern, or it'll silently 404 through the backend proxy instead of reaching the new function. Verify this kind of rewrite change against a Vercel preview deployment (`/api/health` still proxying, `/api/seo-audit` reaching the function) before it reaches production — this pattern was never tested against a live Vercel deployment as part of implementing issue #54, only reasoned from Vercel's documented routing rules.
  - **Types — don't reinstall `@vercel/node`**: the handler's `VercelRequest`/`VercelResponse` are hand-rolled at the top of `api/seo-audit.ts` on top of `node:http`'s `IncomingMessage`/`ServerResponse`, deliberately. `@vercel/node` is the platform's own build toolchain (21 MB) and Vercel supplies it at build time, so listing it as a devDependency changed nothing about the deployed function — but it was the sole source of all 9 `npm audit` findings in the frontend tree (`undici`, `path-to-regexp`, `js-yaml`, `ajv`, `smol-toml`, all transitive), and none of them were fixable without downgrading it to 3.x. It was dropped; the shim models only the members this handler uses. Adding a second function under `api/` means lifting the shim into `frontend/api/vercel.ts`, not reinstalling the package. Trade-off accepted: `tsc` no longer checks the handler against the platform's real request/response contract, so any future use of a member the shim doesn't declare (`req.cookies`, `res.send`, `res.redirect`) has to be added there by hand.
- **`prerender-cadence` gate** (issue #92, `frontend/api/prerender-cadence.ts`) — a second Vercel Serverless Function, same shape as `seo-audit.ts` (thin handler, `isValidAuditToken` shared-secret auth, the same `api/vercel.ts` request/response shim). cron-job.org hits it every 6h *instead of* POSTing straight to the prerender rebuild's Deploy Hook URL; the handler reads the production branch's tip commit message and skips forwarding to the real Deploy Hook when `shouldSkipCadenceTick` (`src/lib/prerenderChain.ts`) says a chain round is genuinely in flight, closing a race where a cadence-triggered build would resume the same fresh marker a legitimate chain continuation is using and both push to `commitRoundMarker`'s branch. See the Routing bullet above for its `vercel.json` rewrite exclusion.
