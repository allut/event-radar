# Frontend

What's in here: the routes/components/hooks folder structure, and the i18n data pipeline (shared JSON → generated TS/Python).

Read this before touching `frontend/src/routes/`, `frontend/src/components/`, `frontend/src/hooks/`, `frontend/src/lib/`, `frontend/src/content/`, `frontend/scripts/`, `frontend/functions/`, `shared/i18n/`, or `backend/app/email/`.

## Frontend Structure

Each component and route lives in its own folder containing `Name.tsx`, `Name.module.css`, and a one-line `index.ts` barrel (`export { default } from './Name'`). The barrel keeps import strings short — callers write `./components/EventCard`, not `./components/EventCard/EventCard`. **Exceptions:** `LocaleSelector/` has no `Name.module.css` — it fully delegates rendering to `SelectMenu` and has no styles of its own to hold; `Privacy/` and `Terms/` likewise have none, being one-line wrappers over `LegalPage` (which owns the styling); `SeoTags/` likewise has none, being a thin `react-helmet-async` shell with no rendered DOM to style; `AdminApp/` likewise has none, being a pure pathname dispatcher (see below) that renders no styled DOM of its own; `ThemeSelector/` and `AdminThemeToggle/` likewise have none — like `LocaleSelector/`, both fully delegate rendering to `SelectMenu`; `ChevronIcons/` likewise has none, being the shared prev/next inline-SVG chevrons `DatePicker`/`DateRangeMenu` page months with (styled by their consumers). (Those eight are the complete set — `AdminApp/`, `Privacy/`, `Terms/`, `AdminThemeToggle/`, `ChevronIcons/`, `LocaleSelector/`, `SeoTags/`, `ThemeSelector/`.) **Route-private subcomponents skip the own-folder/barrel convention entirely** — they sit as a bare `Name.tsx` beside their parent route/component instead, since nothing outside that parent ever imports them and a folder+barrel would be indirection with no caller to shorten: `Explore/UpsellCard.tsx`, `AdminPipeline/ConfirmRunModal.tsx`, `AdminPipeline/PipelineRunBreakdown.tsx`, `RichTextEditor/icons.tsx` (toolbar glyphs, not a component). The pattern is consistent and intentional — don't promote one to a folder without a second, cross-parent importer showing up.

`AdminShell/` (`frontend/src/components/`) is the persistent nav-rail chrome every authenticated `/admin/*` screen renders inside. `AdminPipeline/ConfirmRunModal` and `AdminPipeline/PipelineRunBreakdown` are route-local subcomponents beside it, as is `Explore/UpsellCard` (the signed-out sign-in upsell rendered on `/explore`). `Landing/` is the logged-out marketing page (hero markup lives directly in `Landing.tsx` — there is no separate `RadarHero` subcomponent); `Contact/` renders its own `TopBar` + the contact form (via `useContactSubmit`). `Faq/` (`/faq`) does **not** reuse `LegalPage`: it copies its `TopBar` wiring, per-locale loader effect (active locale → `en` → error `PageState`) and structured `renderInline` approach, but renders its own layout — header + section jump-nav, one closed `<details>` per question (answers always in the DOM, for the prerender), and a closing contact CTA — from a `FaqDoc` loaded per-locale from `frontend/src/content/faq/` (`types.ts`, `loaders.ts`'s `FAQ_LOADERS`, `faq.en.ts`; EN is canonical, a missing locale falls back to it). Its `FaqInline` adds a `{ text, to }` internal-route form to `LegalInline`, rendered as a router `Link` through `localePath()` — `LegalInline`'s `href` stays for `mailto:`/`https:` only, since `safeUrl` rejects a relative path. The organizer routes sit behind their own `OrganizerProtected` guard (`App.tsx`, mirrors `Protected` but reads `useOrganizerAuth()` and redirects to `/organizer/login`) — the user and organizer auth tracks never share a route guard, matching their separate token/salt tracks (see `docs/security.md`).

Event-claiming components: `ClaimStrip/` exports `ClaimPanel` (the public "is this your event?" CTA) and `ClaimPill` (the claimant-only pending pill) rendered on `EventDetail`; `ClaimEventPicker/` is the organizer dashboard's claim-discovery combobox (search + email-domain suggestions, same box/pop/option chrome as `VenuePicker`). `ChevronIcons/` holds the prev/next chevrons shared by `DatePicker`/`DateRangeMenu`.
- **Locale-prefixed routing** — every route in `App.tsx`'s `ROUTE_DEFS` is registered twice: once at its bare `ROUTES.*` path (Estonian) and once under a `/:locale` prefix (`localePrefixedPattern`), so `/en/...`/`/ru/...` reach the same element. Two route classes: Home (`/`), `Explore` (`/explore`, issue #236), `EventDetail` (`/events/:id`) and `Faq` (`/faq`, issue #491) are `noRedirect: true` — the four public SEO routes, whose bare path always renders Estonian and never redirects, regardless of any stored preference (crawler/prerender stability). Every other route is wrapped in `BareLocaleGate`, which redirects a bare visit to the stored preference's prefixed URL when that preference (`getStoredLocale()`, distinct from `getLocale()`'s UI-default fallback) is explicitly set to something other than Estonian; a first-time visitor with no stored preference is left on the bare path. An unrecognized `:locale` segment (e.g. `/xx/...`) falls back to Estonian content without redirecting the URL. `useRouteLocale()` (`frontend/src/hooks/`) resolves the current `:locale` param the same way, for callers that just need the value. `useLocaleMutation` resolves its `locale` from the URL segment when present, else from the stored preference (or Estonian for `publicRoute: true` callers — Feed/Landing/Explore/EventDetail/Faq); switching locale navigates to the equivalent prefixed path (`localizedPath`/`stripLocalePrefix`, defined in `frontend/src/lib/urlLocale.ts` and re-exported through `utils.ts` — the one deliberate exception to "all shared helpers in `utils.ts`", explained in that module's own comment) in addition to its existing `localStorage`/`PATCH /users/me` persistence. `Protected`/`OrganizerProtected` guards sit inside this wrapper, unaffected by it.
- Tests co-located as `Name.test.tsx` / `Name.test.ts` beside each subject file. Shared test helpers and factories live in `frontend/src/test/` (`setup.ts`, `utils.tsx`). Stack: Vitest + @testing-library/react + jsdom. **One exception:** `frontend/functions/` stays test-free — Cloudflare's file-based routing would claim a `.test.ts` there as a route — so the Pages Functions' tests live in `frontend/tests/functions/`, mirroring that tree. `npm run lint` covers `src scripts functions`.
- Shared CSS base classes in `frontend/src/components/shared/`: `Card.module.css` (`.card`, `.cardAccentTop`, `.cardDangerTop`, `.cardPage`), `Button.module.css` (`.btnPrimary`, `.btnOutline`), `Menu.module.css` (`.menu`, `.menuPop`, `.triggerButton`/`.triggerButtonActive`, `.triggerInline`/`.triggerInlineActive` — the popover/trigger chrome shared by `FacetMenu`, `SelectMenu`, `MobileMenu`, `DatePicker`, and `SelectField`), and `Animations.module.css` (`.spin`, `.breathe`, `.rise` + their `@keyframes`, tuned per call site via `--spin-duration` / `--breathe-duration` / `--rise-distance` custom properties). Compose from these via CSS Modules `composes` — never copy-paste the same card/button/menu rules into route or component stylesheets. Component CSS composes from `'../shared/X.module.css'`; route CSS from `'../../components/shared/X.module.css'`. All 18 shared modules, the token system they draw on, and the visual rules governing them are documented in `docs/design-system.md` — read it before a visual change. `GoogleSignInButton/` (`frontend/src/components/shared/`) is a plain `<a href>` to the backend's OAuth `start` endpoint — no client-side OAuth logic — composing `btnOutline` and rendering `GoogleGMark`, the real Google "G" mark lifted verbatim from `signin-assets.zip` and inlined in the DOM (never `<img>` — see `docs/adr/0002-google-sign-in-oauth-pkce.md`); its Light/Dark plate colors are Google-mandated hex triples held as `--google-btn-*` tokens in `index.css`, not the app's own palette. Gated by `VITE_GOOGLE_SIGNIN_ORGANIZER_ENABLED`/`VITE_GOOGLE_SIGNIN_CONSUMER_ENABLED` (Cloudflare Pages build-time vars in `frontend/wrangler.toml`'s `[vars]`, both `"true"` in production, unset in dev — same pattern as `VITE_GA_MEASUREMENT_ID`/`VITE_API_BASE`) — frontend-only convenience gate, the backend `start` endpoint 404s independently when its own flag is off.
- API client in `frontend/src/api/client.ts` — `api` (consumer track) plus thin `organizerApi` and `adminApi` wrappers that pass `{ organizer: true }` / `{ admin: true }` on every call, so those routes/hooks never have to remember the flag, and `adminStream()` for the NDJSON job triggers. Every request goes out with `credentials: 'include'`; the session itself is an httpOnly cookie the JS never sees (`docs/adr/0001-session-tokens-in-httponly-cookies.md`), so there is no token in `localStorage` to attach. A 401 means "session expired" on every path but `POST /admin/auth/login` (`NO_SESSION_REDIRECT_ON_401` — there it means "wrong credentials", and must reach the login form as a real `ApiError`); `handleSessionExpiry401` clears the matching track's *signed-in hint* and redirects to `/login`, `/organizer/login` or `/admin/login`. `FormData` bodies (the image upload) skip JSON stringification and the explicit `Content-Type`. React Query used for server state (`@tanstack/react-query`).
- Custom hooks in `frontend/src/hooks/`: `useAuth.ts` (live auth-state subscription), `useLocale.ts` (live locale subscription, mirroring `useAuth` — lets the globally mounted `Footer` re-render on a locale switch from any page), `useLogout.ts` (clear token + redirect), `useMagicLinkRequest.ts` (request-link mutation), `useFeedback.ts` (feedback signal dispatch), `useLocaleMutation.ts` (locale-switch mutation), `useContactSubmit.ts` (contact-form submit mutation), `useDropdown.ts` (open/close + outside-click + Escape + focus + mobile-flip for trigger-button popovers), `useToast.ts` (transient success/error toast state with auto-clear), `useEventReport.ts` (report-modal open/close + sign-in gate + cache invalidation for `ReportModal`; caller supplies `authed`/`onLoginRequired`), `useEventCardNav.ts` (one memoized `{localePath, authed, onLoginRequired}` object resolved by each card list — Feed/Explore/Saved — and passed as `EventCard`'s `nav` prop, so no card subscribes to the router or auth store itself), `useFitsViewport.ts` (whether an element at its CSS sticky `top` fits the viewport — gates EventDetail's wide-band sticky rail), `usePrefersReducedMotion.ts` and `useResolvedTheme.ts` (live subscriptions — the reduced-motion media query, and `lib/theme.ts`'s resolved light/dark value, re-rendering on an OS flip, another tab's write, or an override expiring), `useGoogleSignInError.ts` (Login/OrganizerLogin's shared Google-callback error banner — reads the error param once, then strips it from the URL), and the locale-routing trio `useLocalePath.ts` (locale-prefix an internal `to` against the current URL — every `<Link to>`/`navigate()` target goes through it), `useLocaleNavigate.ts` (the `useNavigate()` wrapper that does the same for programmatic navigation), and `useLocalLocale.ts` (local mirror of the global locale for the switcher routes, so their own tree re-renders immediately). Plus the organizer-track equivalents `useOrganizerAuth.ts` (live organizer-session subscription, backs `OrganizerProtected`), `useOrganizerLogout.ts`, `useOrganizerEventForm.ts` (submit/edit form state for `EventSubmit/`), `useOrganizerContactSubmit.ts` (the `/organizer/contact` mutation, parallel to `useContactSubmit`), `useClaimEventEdit.ts` (form state + save for the claim-editing surface, `ClaimEventEdit/`), and the admin-track ones `useAdminAuth.ts`/`useAdminLogin.ts`/`useAdminLogout.ts` (a third, independent auth track over `lib/adminAuth.ts`) and `useTriggerRun.ts` (streams one `AdminPipeline` trigger's NDJSON run, tracking cold-start/streaming/disconnected state). `useSeoMeta.ts`/`useStaticSeoMeta.ts`/`useRouteLocale.ts` are covered in their own sections below.
- Auth helpers in `frontend/src/lib/auth.ts` (the **signed-in hint** + locale storage, `setSignedInHint()`/`clearSignedInHint()`/`isAuthenticated()`, `beginLogout()`/`isLoggingOut()`, a `subscribeAuth()` emit/subscribe store that `useAuth()` reads, and a parallel `getLocale()`/`subscribeLocale()` store that `useLocale()` reads), with `frontend/src/lib/organizerAuth.ts` and `frontend/src/lib/adminAuth.ts` mirroring it for the other two tracks (own `ORGANIZER_SIGNED_IN_HINT_KEY`/`ADMIN_SIGNED_IN_HINT_KEY` storage keys, `isAuthenticatedOrganizer()`/`isAuthenticatedAdmin()`, `beginOrganizerLogout()`/`isOrganizerLoggingOut()`, `subscribeOrganizerAuth()` behind `useOrganizerAuth()`; no locale store of their own — locale stays in `auth.ts`) — the three hint stores never share a key, matching the separate backend salts. The hint is a `'1'` marker only: the real session is an httpOnly cookie (`docs/adr/0001`), so `isAuthenticated()` answers "should the UI render as signed in", never "is this request authorized" — the backend decides that on every call, and a stale hint only costs one 401-and-redirect. Components must go through `useAuth()`/`useOrganizerAuth()` — never read `isAuthenticated()` directly in render, or auth changes won't re-render.

## i18n

**Single source of truth:** `shared/i18n/{en,et,ru}.json` — split into `"ui"` (frontend strings) and `"email"` (backend digest/magic-link strings). `shared/personas.json` holds persona names + vibes per locale. `shared/app-config.json` holds cross-stack scalars and taxonomies. `shared/calendar.json` holds localized `day_names`/`month_names` (generated into the backend's `DAY_NAMES`/`MONTH_NAMES`).

**Workflow:** Edit the JSON files in `shared/` → run `python scripts/generate_shared.py` → commit both the JSON and the updated `_generated` files. Never edit `_generated/` directly.

- **Frontend** — `frontend/src/i18n.ts` re-exports helpers (`t`, `ti`, `personaName`, `personaVibe`) and imports strings from `frontend/src/_generated/i18nData.ts`. `frontend/src/constants.ts` imports `LOCALES`, `PERSONAS`, TTL, and weight thresholds from `frontend/src/_generated/sharedConstants.ts`.
- **Backend** — `backend/app/i18n.py` re-exports helpers (`t`, `ti`, `day_name`, `month_name`) and imports `TRANSLATIONS`, `DAY_NAMES`, `MONTH_NAMES` from `backend/app/_generated/i18n_data.py`. `backend/app/constants.py` imports cross-stack scalars and frozensets from `backend/app/_generated/shared_constants.py`.
- **Email styling** — `backend/app/email/styles.py` holds `EMAIL_CSS` (shared progressive-enhancement `<style>` block) plus `S_*` inline-style constants, split into shared page chrome (reused by every email type) and per-email groups (event card for the digest, body/note styles for the magic link). `backend/app/email/templates.py` holds the shared `EMAIL_DOCUMENT` page shell (header/content/footer row placeholders) plus per-email header/body/footer templates that fill those slots, and the digest's `EVENT_*` card markup. New email types add their own header/body/footer templates and reuse `EMAIL_DOCUMENT` rather than duplicating the shell.
- **Email digest** — `backend/app/email/digest.py` handles data formatting + assembly and Resend delivery, filling `EMAIL_DOCUMENT` with `DIGEST_HEADER`/`DIGEST_FOOTER`. The digest matches the site's visual design: each event block includes its `image_url` (escaped, falls back to a plain color band when absent) and the header carries an "open feed" button linking to the frontend app (`feed_url`). HTML only, no plain-text part. All subjects, labels, and day/month names resolved via `app/i18n.py`. New email types must follow the same three-file split: presentation CSS in `styles.py`, markup in `templates.py`, assembly + delivery in a dedicated module.
- **Magic-link email** — `backend/app/email/magic_link.py` (`build_magic_link_html`/`build_magic_link_text`) fills `EMAIL_DOCUMENT` with `MAGIC_LINK_HEADER`/`MAGIC_LINK_BODY`/`EMAIL_FOOTER_BRAND`, matching the digest's visual system (dark page, gold CTA button). Sends both an HTML and a plain-text part — unlike the digest, since this is a transactional/deliverability-sensitive send. Called from `app/auth/email.py::send_magic_link`, which stays on a raw (non-retrying) `httpx` call for the reason documented inline (see `docs/security.md`'s Auth section).
- **Contact email** — `backend/app/email/contact.py` (`send_contact_message`) delivers a contact-form submission to the owner inbox (`settings.CONTACT_TO_ADDRESS`, `reply_to` set to the sender) via Resend. This is **internal-only** mail (not user-facing branding), so it skips the `EMAIL_DOCUMENT` shell and uses plain markup — the `CONTACT_HTML_BODY`/`CONTACT_TEXT_BODY` `.format()` constants in `templates.py`, assembled (escaped) in `contact.py` and sent via the shared `send_resend_email()` (`app/email/resend.py`). Falls back to log-only when `RESEND_API_KEY` is unset. Called from `app/routers/contact.py::submit_contact` (`POST /contact`, honeypot + `RATE_LIMIT_CONTACT`), which swallows send errors so no email failure surfaces to the caller.
- **Drift guard** — `backend/tests/test_generated_sync.py` runs the generator into a temp dir and asserts byte-identical output. If it fails: `python scripts/generate_shared.py` and commit.

## SEO: meta tags, structured data, prerendering

- **`useSeoMeta`** (`frontend/src/hooks/useSeoMeta.ts`, pure builder `buildSeoMeta`) — every route's `<title>`/`<html lang>`/default `noindex`; Landing, `/explore`, `/events/:id` and `/faq` additionally pass `indexable: true` (`/faq` only once its `FaqDoc` has loaded) for OG tags, a self-referential canonical, and hreflang alternates (`en`/`et`/`ru` + `x-default`). Every other route goes through the thin `useStaticSeoMeta` wrapper (`frontend/src/hooks/useStaticSeoMeta.ts`). Rendered via `<SeoTags meta={...} jsonLd={...} />` (`frontend/src/components/SeoTags/`), a thin `react-helmet-async` shell. Every JSON-LD body is serialized by `serializeJsonLd()` (`src/lib/jsonLd.ts`: `JSON.stringify` + every `<` escaped to `\u003c`), shared by `SeoTags` and `prerender.ts`'s change-marker re-save — a bare `JSON.stringify` at either site would let event-sourced text containing `</script` break out of the tag (OWASP audit #1).
- **Structured data** — `frontend/src/lib/structuredData.ts` builds schema.org JSON-LD typed against `schema-dts`: `buildEventJsonLd` (event detail — never emits `organizer` or `offers.availability`, since neither is backed by real data; emits an `AggregateOffer` with `lowPrice`/`highPrice`/`priceCurrency` whenever `price_min !== null` — numeric-truthiness, so a free event's `price_min: 0` still emits `lowPrice: 0` — falling back to a plain `Offer` otherwise, issue #236; `priceCurrency` defaults to `DEFAULT_CURRENCY` when `event.currency` is null, since `seoValidation.ts`'s validator requires `priceCurrency` unconditionally once `lowPrice` is present and a free event legitimately loses its currency at ingest — dropping it would silently drop the price offer's rich-result eligibility instead), `buildWebsiteJsonLd` (Landing — `name`/`url`/`inLanguage` only), and `buildExploreItemListJsonLd` (`/explore`, issue #236 — one `ListItem` per rendered card, `position` matching render order; each `item` is the *full* `buildEventJsonLd` payload per event — issue #224 governs over #232's since-superseded "minimal item" note, see issue #236's own contradiction writeup — plus a top-level `url` on that item pointing at the locale-matched canonical detail page, distinct from `offers.url`'s external ticket link).
- **Build-time prerender pipeline** (`frontend/scripts/prerender.ts`) — runs as the last step of `npm run build` (after `tsc --noEmit && vite build`) whenever `$CF_PAGES` or `$PRERENDER_LOCAL` is set, so a Cloudflare Pages build produces it automatically; a plain local `npm run build` skips both the Playwright browser install and this pass entirely (see "Local dry run" below for the opt-in). `main()` first returns early unless this is a production-branch build (`isPreviewBuild()` — `CF_PAGES === '1' && CF_PAGES_BRANCH !== <production branch>`), before any rendering, sitemap/robots write, validation, or marker commit (issue #95). It fetches every published event id from `GET /public/prerender-events` (`backend/app/routers/public.py::prerender_events` — the single source of truth for "what's published", also reused by `sitemap.xml` generation), boots the just-built `dist/` under `vite preview` (its `preview.proxy` config in `vite.config.ts` forwards `/api` to a real backend — `PRERENDER_API_ORIGIN` env var, defaulting to the same Render origin `frontend/functions/api/[[path]].ts`'s proxy already targets), and drives it with Playwright (bounded worker pool, `RENDER_POOL_CONCURRENCY` in the script, currently 6 — `NAV_TIMEOUT_MS`/`CONTENT_READY_TIMEOUT_MS` are set 3x wider than local, confirmed by local repro that this same single-process, software-rendered Chromium is simply slower on a shared, throttled build machine, independent of concurrency) to snapshot Landing, `/explore` (issue #236), and every published `/events/:id`, across all three locale-prefixed URL variants. `/explore`'s target carries no `eventId`/`updatedAt` (same shape as home) and is appended right after home in `buildTargets`, never at index 0 — the live audit reads sitemap freshness off the *first* `<lastmod>`, which depends on home staying first; that same no-`eventId` shape is what makes `classifyTarget` treat it as always-render-fresh (never copy-forward) for free. `eventDetailRateGate` (`GET /events/{id}`'s budget) is keyed on `target.eventId !== undefined`, not `bare !== ROUTES.home`, so `/explore` doesn't consume it. Readiness is deliberately decoupled from indexability for `/explore` (unlike Landing/`/events/:id`, whose canonical-link-attached wait doubles as both signals): `Explore.tsx` sets a `data-prerender-ready="true"` marker once its query settles — `isSuccess` **or** `isError`, never `isLoading` — which `snapshotTarget` waits on instead of the canonical-link selector, and a sibling `data-prerender-error="true"` marker on `isError` that makes `snapshotTarget` throw (routed through the same `failures[]`/build-throw path as any other render failure) rather than silently shipping a `noindex` page. Browser launch (`launchBrowser`) is plain `chromium.launch()` using Playwright's own bundled Chromium (`playwright install chromium`, the `npm run build` step ahead of this script). Each snapshot is written to `dist/<locale-prefix>/.../index.html` — the directory-index shape `functions/[[path]].ts`'s `env.ASSETS.fetch()` resolves before falling through to the app shell, so a prerendered path is served as-is. A page is considered "rendered" once its `<link rel="canonical">` is attached (only present once `useSeoMeta`'s `indexable` flips true, which for `/events/:id` only happens after the event has actually loaded — see `EventDetail.tsx`). The script fails the build (non-zero exit) if the published-events fetch fails or if any target can't be reached/rendered within its timeout.
- **The SPA fallback shell** — `dist/index.html` (the plain CSR entry `vite build` produces) is copied to `dist/app-shell.html` *before* the bare-Estonian Landing snapshot overwrites `dist/index.html`. `frontend/functions/[[path]].ts` (issue #345, the Cloudflare Pages Function providing the SPA fallback) serves `app-shell.html`, not `index.html`, so every non-prerendered route (`/saved`, `/settings`, etc.) keeps serving the untouched CSR shell rather than a stale/mismatched snapshot — `/explore` is prerendered as of issue #236 and lands at `dist/explore/index.html`, no longer part of this untouched-CSR-shell set. The function tries `env.ASSETS.fetch()` against the original request first and only falls through to the shell on a genuine 404; that fetch-first order is load-bearing rather than defensive (issue #354 — Cloudflare's documented "static asset before Function" precedence did not hold in production, and this catch-all was observed swallowing built JS/CSS too). It requests the shell at its *extensionless* path, because `env.ASSETS.fetch()` applies Pages' default `.html`-stripping redirect and would otherwise hand the browser a visible 308. `/api/*` never reaches it — Cloudflare prefers the more specific `functions/api/[[path]].ts` (and its exact-path siblings), so there's no negative-lookahead exclusion to maintain. A nonexistent `dist/assets/*` path falls through to the shell like any other miss, served as a 200 `text/html` response that a browser then rejects as a stylesheet/module script under strict MIME sniffing (issue #97) — the live audit's asset content-type check (below) is what catches it.
- **Change detection & copy-forward asset refs** (issue #80/#82/#97) — every round, `classifyTarget` fetches each event route's *currently-live* production page and diffs its embedded `dateModified` marker (`embedChangeMarker`/`extractChangeMarker`, keyed on `Event.updated_at`) against the target's. An exact match (`unchanged`) copies that live HTML straight to `dist/` with no Playwright render at all — the mechanism that keeps a 4000+-route catalog's per-round render budget survivable; a mismatch (or no live page yet) renders fresh. The same live HTML is also held as a stale-but-real fallback (issue #82) for a route the render budget runs out before reaching, written out after the render pool once it's known which targets were actually skipped. Both write sites route through `rewriteSnapshotAssetRefs(html, shellHtml)` before hitting disk: a copied-forward page is a byte-for-byte capture of a *previous* build's rendered HTML, complete with that build's content-hashed `dist/assets/*` filenames, which Vite re-mints on every source change — with nothing else re-validating a copied-forward snapshot (see the in-build gate's `selectValidationTargets` scoping below), those dead references would otherwise ship to users indefinitely, silently, across every future deploy once the current build's real assets replace the ones being referenced. `rewriteSnapshotAssetRefs` swaps the stale `<head>` `<script>`/`<link>` asset nodes for `shellHtml`'s current ones (order preserved, everything else — JSON-LD, the change marker, Helmet's `data-rh` tags — untouched byte-for-byte) and throws if `shellHtml` itself carries zero asset references, since a silent no-op there would just reintroduce the bug. `shellHtml` is read once per round from `dist/app-shell.html` (`APP_SHELL_FILENAME`), never `dist/index.html` — the latter gets overwritten by the home-route snapshot partway through the same round, so it's not guaranteed pristine. Self-healing: every target is reclassified every round, so the very next production build rewrites every previously-shipped copied-forward snapshot's stale refs, no manual backfill needed. The in-build validation gate's exemption for copied-forward routes (`selectValidationTargets`, issue #94) stays correct despite this: that gate only checks SEO structure (title/canonical/hreflang/JSON-LD), never asset references, so nothing it does was ever aware of — or a defense against — this asset-hash class of bug in the first place.
- **Prerender cost trims** (Big-O audit #455) — `page.goto` waits on `domcontentloaded` — the readiness gate is the *route-specific* canonical (`contentReadySelector`: `link[rel=canonical][href="<this route's canonical>"]`, built from `canonicalUrlFor` in `useSeoMeta.ts`; `/explore` uses `PRERENDER_READY_SELECTOR`), never any canonical, because mid-round `dist/index.html` is the prerendered et Landing snapshot and `vite preview` serves it as the SPA fallback for every not-yet-rendered route, so a bare canonical wait resolves instantly on Landing's tag and captures the loading state or Landing itself. `validateSnapshotStructure`'s `expectedCanonical` option additionally fails any snapshot whose canonical isn't exactly that URL (`networkidle`'s ≥500ms/route bought nothing extra); `extractChangeMarker` scans the first JSON-LD script with a regex instead of a second full DOM parse; `classification[].liveHtml` is nulled once consumed; R2 chain-state PUTs are collected and drained with `Promise.allSettled` after the pools rather than awaited inline, and `r2ChainState.ts` memoizes its `S3Client` on the credential tuple; the in-build live-API staleness comparison runs for the default-locale sibling only (structural checks still cover every locale). `functions/api/seo-audit.ts` fetches the event page + explore locales + snapshot assets concurrently, and finds the first sitemap event URL with an early-exit scan (`parseFirstSitemapEventUrl`). **Measured on the first real Cloudflare burst (2026-10-03, 5442 routes, `PRERENDER_RENDER_BUDGET_MINUTES=10`):** 3 rounds (1012 → 1012 → 334 rendered; queue 1334 → 328 → 0), every round `validated N snapshot(s), no issues found` — `domcontentloaded` + route-specific canonical gate snapshots fully. Render ≈100 routes/min; wall-clock per round ≈16 / 20 / 11 min (~47 min total). Resumed rounds spend 5–6 min in copy-forward (R1: 84 s) and ~3 min validating 1012 snapshots. Each round now logs `prerender: peak RSS` (node process only, excludes Chromium).
- **Chain-state manifest (R2)** (spec #365, shipped in #366–#369) — an **additive optimization layer** over the git-committed `RoundMarker` chain above, not a replacement for it. The problem it solves: the chain already avoids re-*rendering* unchanged routes across rounds of a burst, but every resumed round still called `classifyTarget` — a real production `fetch()` — for *every* target, because `RoundMarker` carries only aggregate counters (`newlyRendered`/`copiedForward`/`queueRemaining`) and no per-target identity. Change-detection traffic therefore stayed pinned at `targets.length` every round instead of shrinking as targets resolved. The manifest gives a resumed round per-target identity, so rounds 2+ read a resolved target's finalized HTML back out of Cloudflare R2 instead of re-fetching production.
  - **Storage.** Cloudflare R2 over its S3-compatible API (`@aws-sdk/client-s3`), *not* a Workers/Pages `[[r2_buckets]]` binding — `scripts/prerender.ts` runs as a Node build script in the Pages build container, not as a Worker. `frontend/src/lib/r2ChainState.ts` is the whole client boundary: `getR2Object`/`putR2Object`/`deleteR2ObjectsByPrefix`, deliberately generic — it knows nothing of the manifest's key format or schema, which keeps it independently testable (`r2ChainState.test.ts`). Bucket `event-radar-prerender-chain-state` and `CLOUDFLARE_ACCOUNT_ID` are non-secret and live in `frontend/wrangler.toml`'s `[vars]`; `R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY` are Cloudflare Pages Secrets in production and `frontend/.env.local` (gitignored) locally.
  - **Layout**, per burst, under `prerender-chain-state/{sanitizedBurstId}/` (`CHAIN_STATE_PREFIX`; `sanitizeBurstIdForR2` replaces `:`/`.` with `-` because `burstId` is an ISO timestamp and some S3 tooling chokes on colons in a key — `RoundMarker.burstId` itself, the value other rounds compare against, is never touched): an **index** at `index.json` (`{ "{locale}:{eventId}": { resolvedAtRound } }`) and one **content object** per resolved target at `targets/{locale}-{eventId}.html`, holding the post-`finalizeSnapshotHtml` bytes. Presence of a key in the index *is* "resolved" — there's no status enum; that distinction stays in `RoundMarker`'s counters. Home and `/explore` targets carry no `eventId`, so no key can be formed for them and they keep rendering fresh every round by construction.
  - **Why content, not just status.** Every round produces a complete fresh `dist/` (each Pages deploy replaces the whole site), so a resolved target still needs its *bytes* in every later round's output. A status-only manifest could skip re-classification but would still have to hit production for the HTML — the exact fetch this exists to remove.
  - **Read path** (`partitionByChainState` + `fetchResolvedTarget`, #368). Round 1 never reads: its `burstId` is freshly minted, so no manifest can exist. Round 2+ reads the index once, partitions `targets` into resolved vs. everything else, and runs both groups through the *same* `mapPool`/`CHANGE_DETECTION_CONCURRENCY` pool — so the concurrency cap against production never stacks and `classification` stays ordered like `targets` with no merge step. `fetchResolvedTarget` returns the same `ChangeDetectionResult` shape `classifyTarget` produces (`unchanged: true`, `liveHtml` set), so every downstream consumer — the copy-forward write loop, `prioritizeRenderQueue`'s `!unchanged` filter, the sitemap builder — needs no change to tell the two apart. It also re-runs the same `extractChangeMarker`/`target.updatedAt` diff against the cached bytes before trusting them, since `fetchPrerenderCandidates()` re-reads `Event.updated_at` fresh every round and a burst can span several: a marker mismatch falls back to a fresh `classifyTarget` fetch rather than serving stale content forward.
  - **Write path** (`persistChainStateTarget` + `finalizeChainState`, #367). A target earns a manifest entry at exactly two points — the copy-forward branch of the classification loop, and a successful `snapshotTarget` render — and only once finalized HTML is in hand. The index entry is written *only after* the content PUT succeeds, so an index can never claim a target is resolved with no bytes behind it. A target `fetchResolvedTarget` already sourced from the manifest is skipped (re-PUTting identical bytes is pure waste). **The stale-fallback write is deliberately excluded**: budget-skipped content isn't done — the render queue still owes that route a real render, and marking it resolved would permanently skip it for the rest of the burst, undermining `skippedTargets`/`prioritizeRenderQueue`'s backlog mechanism. Content objects are PUT eagerly per target (duplicate/orphaned writes are harmless); the index is PUT **once**, at the end of `main()` next to `commitRoundMarker`, because concurrent workers doing read-modify-write against one shared object would race.
  - **Cleanup.** `finalizeChainState` mirrors `shouldCommitRoundMarker`: a `continuing` round writes the index; a `done` round deletes the burst's whole prefix outright, since nothing will ever read it back. `deleteR2ObjectsByPrefix` pages through `ListObjectsV2`'s continuation token (a burst is thousands of targets, past the 1000-key page cap) and deletes each page as it goes; it also checks `DeleteObjectsCommand`'s `Errors` array explicitly, since S3 reports a per-object failure as HTTP 200 rather than throwing. Backstopping that: an R2 bucket **lifecycle rule** (`chain-state-crash-backstop`, prefix `prerender-chain-state/`, expire after `CHAIN_STATE_LIFECYCLE_DAYS` = 3) catches a burst whose `done` round crashed before deleting — comfortably past `CHAIN_STALENESS_TIMEOUT_MINUTES`, mirroring `isMarkerStale`'s crash-recovery posture. That rule is bucket configuration, applied via the Cloudflare dashboard (R2 → bucket → Settings → Object lifecycle rules, issue #369), not application code — `CHAIN_STATE_LIFECYCLE_DAYS` only documents the intended value, so changing the constant does **not** change the rule.
  - **R2 is an optimization, never a correctness dependency** — the locked posture, mirroring `commitRoundMarker`'s existing fail-open precedent. Every failure degrades to today's full-refetch behavior and none of them fail the build: unset credentials or bucket name log and no-op; an index read that fails or returns something that isn't a plain object means "no manifest yet, full re-classify this round"; a content read that misses (evicted, corrupt, or a stale index entry) falls back to a fresh `classifyTarget` for that one target; a failed write costs only this burst's savings. Logging stays at `console.log`/`console.error` — no admin-alert escalation.
  - **Accepted trade-off:** a target resolved early in a multi-round burst can have its production content change again before the burst finishes, so its cached HTML may briefly lag a same-burst edit, self-healing on the next full burst. Judged cosmetic and explicitly decided against mitigating (#363) — it is not an unnoticed bug. In practice the window is narrower than the spec assumed: `fetchResolvedTarget`'s marker re-diff catches any mid-burst edit that moved `Event.updated_at`, leaving only changes invisible to that marker — the same blind spot the pre-existing copy-forward path already has.
- **Snapshots are theme-neutral** (theme-revert-on-refresh fix) — every write site (`snapshotTarget`'s fresh render, and both copy-forward/stale-fallback writes in `main()`) routes through `finalizeSnapshotHtml`, a single choke point that runs `rewriteSnapshotAssetRefs` (copy-forward sites only) then `stripBakedThemeAttr` on the way to disk. `page.content()` captures the build browser's own `document.documentElement.dataset.theme` — set by `index.html`'s pre-paint script against whatever OS theme the build machine happens to have, since there's no `localStorage` in that browser — and without stripping it, every visitor would see the build machine's theme baked in until client JS re-resolved it. `stripBakedThemeAttr` leaves every other `<html>` attribute (`lang`, `data-rh`) untouched and is idempotent; an absent `data-theme` falls through to the dark origin palette only until the pre-paint script (unblocked by the CSP hash — see `docs/security.md`) sets the real value before first paint.
- **`sitemap.xml` + `robots.txt`** (`frontend/scripts/prerender.ts`'s `buildSitemapXml`/`buildRobotsTxt`) — written to `dist/` before the Playwright snapshot pass, off the same `targets` list `buildTargets` produces from the published-event ids, so the sitemap can never list a URL the snapshot pass doesn't also cover. Each target becomes one `<url>` entry (`<loc>` + a `<lastmod>` — `target.updatedAt` when the target has a backing `Event`, else the build timestamp for e.g. home/`/explore`) plus `en`/`et`/`ru`/`x-default` `<xhtml:link rel="alternate">` cross-references, mirroring `useSeoMeta`'s hreflang set. `robots.txt` is an inverse allowlist (`Disallow: /` then explicit `Allow:`s for `/`, `/events/`, `/explore` (**not** `$`-anchored, unlike the home-route `Allow: /$` — a filtered `/explore?category=…` URL must stay crawlable per the canonical-alone crawl-control decision: no `Disallow` on query strings, no param-conditional `noindex`), and their `/en`/`/ru` equivalents, plus a `Sitemap:` directive) so a new authenticated route added later is excluded by default with no robots.txt edit required.
- **Local dry run** — `PRERENDER_LOCAL=1 PRERENDER_API_ORIGIN=http://127.0.0.1:8000 npm run build` (with a local backend running) opts back into the full pipeline against dev data instead of production; `PRERENDER_LOCAL` alone (without `PRERENDER_API_ORIGIN`) exercises it against production data instead.
- **In-build validation gate** (issue #53, `frontend/src/lib/seoValidation.ts` + `prerender.ts`'s `validateTarget`) — runs immediately after every snapshot is written (still inside `prerender.ts`'s `main()`), reads each one back off disk, and checks two assertion categories, **blocking the deploy (non-zero exit)** on either. Scoped to only this round's newly-rendered routes (`selectValidationTargets`, issue #94) — copied-forward routes are byte-identical to what already passed this same gate in an earlier round, so the `prerender: validated N snapshot(s)` log line's `N` is this round's `newlyRendered` count, not the full route set: (1) *structural correctness* — `validateSnapshotStructure` requires a non-default `<title>` (not the app-shell's bare `t('brand', locale)`), a `<link rel="canonical">` on `PRODUCTION_ORIGIN`, all of `SEO_HREFLANG_CODES`'s `<link rel="alternate" hreflang>` alternates, `<meta name="robots" content="index, follow">`, and exactly one valid `<script type="application/ld+json">` — validated by `assertEventJsonLd`/`assertWebsiteJsonLd`/`assertListJsonLd` (`kind: 'event' | 'website' | 'list'`), a hand-rolled runtime check against Google's documented *required* Event fields (`name`, `startDate`, `location`) plus its "image or offers" recommendation (never `eventStatus`/`organizer`/`offers.availability` — those stay unchecked, matching `structuredData.ts`'s deliberate omissions), plus a narrow structural check on `offers.lowPrice`/`highPrice`/`priceCurrency` that only fires once `lowPrice` is present (issue #236); `assertListJsonLd` (issue #236, `/explore`'s `ItemList`) additionally checks `@type`/`itemListElement` shape, exact `1..n` `position` sequencing, every entry's `item` against `assertEventJsonLd` itself (prefixed `item[i]: …`), `item.url` uniqueness/origin/no-fragment, and `item.image` presence (stricter than `assertEventJsonLd`'s own image-or-offers check) — its `itemListElement.length >= 3` check is skipped when a passed-in `liveItemCount` (a live re-query of `GET /explore`, mirroring `compareEventStaleness`'s live re-fetch, `prerender.ts`'s `fetchLiveExploreCount`) proves the catalog itself would render fewer than 3 items, distinguishing a genuinely thin calendar from a builder regression without hardcoding a minimum — `fetchLiveExploreCount` returns not the raw `total` but that count adjusted for the anonymous-view upsell card, which always drops exactly one fetched event to make room for itself (`Explore.tsx`'s `gridItems`); prerendering is always anonymous (Playwright never signs in), so comparing against the unadjusted total would fail every 3-event catalog's build over a UI layout decision, not an actual regression; (2) *non-staleness* — `compareEventStaleness` re-fetches `GET /events/{id}` (sharing `prerender.ts`'s `eventDetailRateGate` budget) and diffs the snapshot's title/venue (read straight off its own JSON-LD, an exact mirror of `event.title`/`venue_name`/`venue_address`) and price against what the live API returns right now. Price isn't part of the JSON-LD payload (issue #46 defers `AggregateOffer`), so `EventDetail.tsx`'s price `<span>` carries `data-testid="event-price"` plus `data-price-min`/`data-price-max`/`data-currency`/`data-has-free-tier` attributes as a machine-readable marker, present exactly when `formatPrice` would render (i.e. `price_min !== null` — see the comment on `compareEventStaleness`). The structural half also fails any snapshot whose JSON-LD script body still contains a literal `<` (`ParsedSnapshot.jsonLdRaw`; a full `</script` breakout truncates the body and fails the JSON-LD parse instead). `seoValidation.ts` is deliberately filesystem/network-free (parses an HTML string, compares against a passed-in live-event object) so the independent live-audit ticket (issue #54) can reuse `parseSnapshotHtml`/`validateSnapshotStructure` unchanged against a `fetch()`-ed production page instead of a local `dist/` file, rather than reimplementing the checks. `/explore` has no non-staleness diff (issue #236) — it's exempt from copy-forward (always renders fresh, see above), so there's no earlier snapshot to diff against.
- **Independent live audit** (issue #54, `frontend/functions/api/seo-audit.ts` + `src/lib/seoAudit.ts`/`seoAuditIssue.ts`/`seoAuditAuth.ts`) — a Cloudflare Pages Function (Fetch API `Request`/`Response`, `context.env` for config), hit every 6h by its own cron-job.org job (offset from the issue #52 prerender-rebuild job), that checks *production*, not a build in progress: the one check that can catch a silently-dead Deploy Hook/cron, since it doesn't depend on any build having run at all. `evaluateLiveAudit` (network-free, unit-tested) checks robots.txt crawlability plus freshness plus structural regressions: (1) reuses `isPathAllowedByRules` (Google's robots.txt matching semantics) against the just-fetched `robots.txt` to flag `sitemap.xml`, the OG fallback image, the built `/assets/`, and each `CRAWLABLE_ICON_PATHS` entry as blocked — the motivating bug for issue #54: a stray `Disallow: /` silently caught `/sitemap.xml` and Google Search Console reported "Couldn't fetch" with nothing else in the pipeline any wiser; (2) treats sitemap.xml's `<lastmod>` (`target.updatedAt` when available, else the build timestamp) older than `SEO_AUDIT_STALE_THRESHOLD_HOURS` (8h — the 6h backend publish/geocode cadence plus a 2h buffer) as a dead cadence; (3) reuses `parseSnapshotHtml`/`validateSnapshotStructure` unchanged (the same reuse `seoValidation.ts`'s module comment anticipated) against `PRODUCTION_ORIGIN/`'s live HTML (`kind: 'website'`) to catch a structural regression that made it to production; (4) does the same against one live `/events/:id` page (`kind: 'event'`, so `assertEventJsonLd` is actually exercised against production, not just Landing's `assertWebsiteJsonLd`) — `api/seo-audit.ts` picks the first bare-Estonian event URL off sitemap.xml via `parseSitemapEventUrls`, best-effort (an empty catalog, or a single flaky event fetch, doesn't fail the whole audit — freshness and Landing are still checked either way); (5) does the same against `/explore`'s canonical URL, all 3 locales (`kind: 'list'`, issue #236) — also best-effort per locale, and with no `liveItemCount` re-query here (unlike the in-build gate), so `assertListJsonLd`'s `>=3` check simply no-ops for the live audit. Separately, `functions/api/seo-audit.ts` itself (not `evaluateLiveAudit`) fetches `/favicon.ico` and flags a non-`image/*` content-type — catching the SPA-catch-all fallthrough, where a missing favicon silently 200s as the HTML app shell instead of 404ing (see `FAVICON_ICO_PATH`'s comment in `constants.ts`). The same app-shell-fallthrough failure mode, for the fetched event snapshot's own built assets rather than the favicon (issue #97): `parseSnapshotAssetUrls` (`src/lib/seoAudit.ts`, pure — pulls every root-relative `/assets/*` `src`/`href` out of `eventHtml`, dropping anything that doesn't resolve to `PRODUCTION_ORIGIN` — so injected `@evil.example/assets/x.css` can't redirect the Worker's fetch) feeds the function's fetch of each one, asserting a `text/css`/`javascript` content-type; a mismatch means the snapshot still references a previous build's now-dead asset hash. Alert-only — never blocks anything, per issue #46's Regression checks; a failure calls `seoAuditIssue.ts`'s `reportAuditFailure` (files a new GitHub issue labeled `seo-audit-failure`, or comments on the existing open one instead of duplicating on repeat failures), a pass calls `reportAuditRecovery` (closes the open issue, if any — a no-op otherwise). Auth is a shared-secret header (`x-seo-audit-token` against `SEO_AUDIT_TOKEN`, constant-time-compared by `seoAuditAuth.ts`'s `isValidAuditToken`) plus a `GH_ISSUE_TOKEN` (GitHub PAT, Issues: write on `allut/event-radar`) for the issue-filing calls — both are Cloudflare Pages project **Secrets** (dashboard or `wrangler pages secret put`, never `wrangler.toml`'s checked-in `[vars]`); without both, the endpoint 500s rather than silently no-op'ing (see `docs/backend-ops.md`).
  - **Routing**: this function lives at `/api/seo-audit`, alongside the `functions/api/[[path]].ts` catch-all that proxies every other `/api/*` path to the Render backend. Cloudflare's file-based routing matches an exact-path function ahead of a catch-all in the same directory, so a new path added under `frontend/functions/api/` is claimed automatically — there is no negative-lookahead exclusion to keep in sync.
  - **Types — don't install `@cloudflare/workers-types`**: `PagesFunction`/`EventContext` (plus a `jsonResponse` helper) are hand-rolled in `frontend/functions/_shared/cloudflare.ts` and shared by every function in the tree. - **`prerender-cadence` gate** (issue #92, ported to a Cloudflare Pages Function in issue #344, `frontend/functions/api/prerender-cadence.ts`) — a second exact-path function, same shape as `seo-audit.ts` (thin handler, `isValidAuditToken` shared-secret auth, the same `_shared/cloudflare.ts` types). cron-job.org hits it every 6h *instead of* POSTing straight to the prerender rebuild's Deploy Hook URL; the handler reads the production branch's tip commit message (an authenticated GitHub API call — the repo is private, so an unauthenticated read always 404s) and skips forwarding to the real Deploy Hook when `shouldSkipCadenceTick` (`src/lib/prerenderChain.ts`) says a chain round is genuinely in flight, closing a race where a cadence-triggered build would resume the same fresh marker a legitimate chain continuation is using and both push to `commitRoundMarker`'s branch. Its own two Pages Secrets are `PRERENDER_CADENCE_TOKEN` and `PRERENDER_CADENCE_DEPLOY_HOOK_URL`, and it authenticates with `X-Prerender-Cadence-Token` — a deliberately distinct header name from the audit job's, see `docs/backend-ops.md`. Routing needs no exclusion (see the Routing bullet above).
