# Security

What's in here: the OWASP-hardening middleware stack, auth (magic-link, sessions, revocation, residual risks), and the canonical explanations for `require_configured_secret`, the External-URL host-pin rule, and the `email_verified` gate.

Read this before touching `app/main.py`, `app/rate_limit.py`, `app/routers/auth.py`, `app/routers/organizer_auth.py`, `app/routers/utils.py`, `app/ingestion/http_client.py`, or any new endpoint (every endpoint needs a `RATE_LIMIT_*`).

## Security Hardening

The backend was hardened against the OWASP Top 10 (2021). The middleware stack and these invariants are wired in `app/main.py`:

- **Rate limiting** — `slowapi` limiter lives in `app/rate_limit.py` (its own module to avoid a circular import between `main.py` and routers), keyed by `client_key()` rather than slowapi's default `get_remote_address` — see the "Rate-limit / audit-log key derivation" bullet below for why. **Every router endpoint** carries `@limiter.limit(...)` — authenticated ones included — with the limit string sourced from a `RATE_LIMIT_*` constant in `app/constants.py` (the only exceptions are `/health` and `/internal/tick`, see below): public unauthenticated routes (`/auth/request-link` + `/organizer/auth/request-link` → `RATE_LIMIT_AUTH_REQUEST_LINK`, `/auth/verify` + `/organizer/auth/verify` → `RATE_LIMIT_AUTH_VERIFY`, `/webhooks/inbound-mail` → `RATE_LIMIT_WEBHOOK_INBOUND_MAIL`, `/public/showcase` → `RATE_LIMIT_PUBLIC`, `/contact` → `RATE_LIMIT_CONTACT`, `/email/unsubscribe` + `/email/resubscribe` → `RATE_LIMIT_UNSUBSCRIBE`, the optional-auth `/events/{id}` → `RATE_LIMIT_EVENTS_DETAIL`); authenticated reads and writes (`/explore` + `/feed` + `/auth/me` → `RATE_LIMIT_BROWSE`, `/feedback*` → `RATE_LIMIT_FEEDBACK`, `/onboarding/persona` + `/users/me` → `RATE_LIMIT_AUTHENTICATED_WRITE`, `/auth/logout-all` + `/organizer/auth/logout-all` → `RATE_LIMIT_LOGOUT_ALL`, every `/organizer/events*` route → `RATE_LIMIT_SUBMIT`); plus every `/admin/*` route sharing **one** bucket via `limiter.shared_limit(RATE_LIMIT_ADMIN, scope="admin")` rather than a separate bucket per route (`"10/minute"` total across the whole `/admin` prefix per client — a per-endpoint `@limiter.limit` would let an attacker cycling all ~17 admin routes attempt far more than the nominal cap per minute; see also the consecutive-failure lockout below). Add the same decorator + constant to any new endpoint, public or not. `ProxyHeadersMiddleware(trusted_hosts="*")` is registered **last** (so it runs outermost) to rewrite `request.client` from `X-Forwarded-For` before the limiter reads it — without it, Render's proxy would collapse all clients into one bucket. **Ops-verification dependency (accepted trade-off, see the invariant comment at `main.py`):** `trusted_hosts="*"` trusts any peer's `X-Forwarded-For` verbatim, so its safety hinges on the process being reachable *only* through Render's proxy and on Render's edge overwriting inbound `X-Forwarded-For`. Render publishes no stable egress CIDR to pin `trusted_hosts` to, so this stays `"*"` — confirm Render's XFF handling on the dashboard rather than in code, and re-derive if the deployment ever sits behind an additional CDN/proxy or gets a public port.
- **Rate-limit / audit-log key derivation (`app/rate_limit.py::client_key`)** — `ProxyHeadersMiddleware(trusted_hosts="*")` itself rewrites `request.client` from the **leftmost** `X-Forwarded-For` entry (uvicorn's `_TrustedHosts.get_trusted_client_address`), which is attacker-controlled: a client can prepend an arbitrary `X-Forwarded-For` value and every `@limiter.limit(...)`/`shared_limit(...)` becomes a no-op, and every `client=%s`-style log line becomes forgeable. `client_key()` instead derives the key from the **rightmost** XFF entry — the one appended by the single trusted hop immediately adjacent to this process (Render's proxy) — which is correct whether Render appends to or overwrites the header, but depends on there being exactly **one** trusted hop between the client and this process (see the `HOP-COUNT ASSUMPTION` comment next to `ProxyHeadersMiddleware` in `main.py`, alongside the pre-existing `trusted_hosts="*"` invariant). `/internal/tick`'s invalid-token log line also goes through `client_key()` rather than raw `request.client.host` for the same reason.
- **Security headers** — the `add_security_headers` middleware sets CSP/`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`Cache-Control: no-store` (nothing from a pure JSON API should ever be cached by an intermediary — most importantly `GET /auth/verify`, whose body carries a bearer session token) on every response from the `SECURITY_HEADERS` dict in `app/constants.py`; HSTS (`HSTS_HEADER_*`) is added only outside development (safe only over HTTPS). The CSP is `default-src 'none'` — the app is a pure JSON API with no first-party HTML/script surface. `TrustedHostMiddleware` (outside development only, `allowed_hosts` derived from `settings.BACKEND_URL`'s hostname) rejects requests with an unexpected `Host` header — low impact today (nothing builds an absolute URL from the request `Host`) but a one-line hardening against intermediary cache-poisoning scenarios.
- **Request body size ceiling** — `MaxBodySizeMiddleware` (`app/main.py`) rejects any request whose body exceeds `MAX_REQUEST_BODY_BYTES` (10 MiB) with 413, before a handler ever reads it. A `Content-Length` request is rejected up front; a chunked request (no `Content-Length`) is rejected mid-stream once the running total crosses the limit, via a wrapped `receive` ASGI callable. It sends the 413 response itself (an ASGI `Response.__call__`) rather than raising `HTTPException` — Starlette places every `add_middleware` entry **outside** its internal `ExceptionMiddleware` (which sits innermost, right next to the router), so an `HTTPException` raised from user-added middleware never reaches it and would surface as a generic 500 instead. Registered so it wraps *inside* `ProxyHeadersMiddleware` (still sees the rewritten client for logging/rate-limiting) — this is the whole-request-body ceiling `IMAGE_UPLOAD_MAX_BYTES` alone doesn't provide (that constant only bounds what the upload handler reads after Starlette has already spooled the full body).
- **API docs** — `/docs`, `/redoc`, and `/openapi.json` are enabled **only** in development (`APP_ENV == "development"`); the strict CSP would block their CDN assets in production anyway.
- **CORS** — `CORSMiddleware` with `allow_credentials=False` (auth is a Bearer header, never a cookie); origins from `settings.CORS_ORIGINS`, methods/headers from `CORS_ALLOWED_METHODS`/`CORS_ALLOWED_HEADERS` constants.
- **`/internal/tick`** — guarded by a constant-time `X-Internal-Token` check against `INTERNAL_TOKEN`; fail-closed outside development (see `require_configured_secret` below).
- **`require_configured_secret` double gate (dev fail-open)** — `app/routers/utils.py::require_configured_secret()` protects every secret-gated surface (`/admin/*` Basic auth, the inbound webhook's Svix signature check, `/internal/tick`'s token check). With the secret unset, it fails open (logs a warning, skips verification) **only** when both `APP_ENV == "development"` **and** the separate `settings.ALLOW_INSECURE_DEV` flag are true — a dev-shaped `APP_ENV` alone is never sufficient, so a stray or never-overridden env var on a real deployment fails closed (503) instead of silently unprotecting the admin surface. `app/main.py`'s lifespan additionally logs an ERROR if `APP_ENV == development` but `DATABASE_URL` resolves to a non-local host (`DEV_DB_LOCAL_HOSTS`), flagging exactly that misconfiguration pattern.
- **Admin auth lockout** — beyond the shared per-client rate-limit bucket above, `routers/admin.py::_require_admin` tracks consecutive Basic-auth failures per `client_key()` in an in-memory dict and locks out further attempts (429) for `ADMIN_AUTH_LOCKOUT_SECONDS` after `ADMIN_AUTH_MAX_FAILURES` consecutive failures — a static username/password pair otherwise has no brute-force damper beyond the rate limit itself. In-memory and single-process (matches this codebase's no-Celery/no-Redis design), so it resets on deploy/restart; accepted since it's a supplement to, not a replacement for, a strong `ADMIN_PASSWORD`.
- **Rate-limit-exempt by design** — `GET /health` and `GET /internal/tick` (`app/main.py`) carry no `@limiter.limit(...)`. `/health` is a platform health-check probe (Render); rate-limiting it risks the platform marking the service unhealthy under legitimate probe traffic. `/internal/tick` is hit every 10 min by the cron-job.org keepalive and is already access-controlled by the `X-Internal-Token` check above — a second layer of IP throttling adds no real protection over a token an attacker doesn't have. Both are deliberate exceptions to the "every public route gets a rate limit" rule above.
- **External-URL sanitization (canonical — cross-referenced from Data Flow §1/§8 and Organizer Event Submission in `docs/pipeline.md`/`docs/organizer-portal.md`)** — the guard picked for a URL field is decided by *whether the server itself fetches it*, not by which field it is. Untrusted `image_url` (rendered into an `href`/`src`, never fetched server-side) passes through `safe_external_url()` (`app/ingestion/http_client.py`), which drops any scheme not in `SAFE_URL_SCHEMES` (guards stored XSS via `javascript:`/`data:` URLs). `event.url` for an adapter-kind source (scraped, **fetched** daily by the refetch job) instead goes through the stronger `safe_fetchable_url()`, which layers a host-allowlist plus `resolves_to_private_ip()` (a DNS-rebinding / private-IP guard) on top of the scheme check. `event.url` for a `user_submission`-kind source is render-only — organizer submissions are excluded from the refetch job (`refetch.py::_select_candidates`, `submitted_by_organizer_id IS NULL`) since an organizer edits their own row directly via PATCH — so `insert_normalized_event()` (`app/ingestion/adapter.py`) picks `safe_external_url()` for it too, off `source.kind == SOURCE_KIND_USER_SUBMISSION`; an organizer's own ticketing domain is otherwise never on `ALLOWED_SOURCE_HOSTS`. Apply the matching guard to any new field, keyed on the same fetched-vs-rendered question. The frontend repeats the scheme check as defense-in-depth in `safeUrl()` (`frontend/src/utils.ts`) — route every untrusted URL through it before putting it in an `href`/`src`; `sanitizeHtml()` (same file) is the matching defense-in-depth pass for the HTML fields below, applied at both `dangerouslySetInnerHTML` sites (`EventDetail.tsx`). **Organizer `image_url` is additionally host-restricted** (`routers/organizer_events.py::_check_image_host`, `ALLOWED_IMAGE_HOSTS = {"res.cloudinary.com"}`): the scheme check alone would let an organizer point `image_url` at an arbitrary https host, which the daily digest embeds as an `<img>` — an unconsented tracking pixel leaking each recipient's IP/open-time to a third party. Submissions must go through the signed `POST /organizer/events/image` Cloudinary upload instead; scraped (non-organizer) sources are unaffected.
- **Stored-HTML sanitization** — every scraped rich-text field the frontend renders as HTML (the localized `description`/`important_info` blocks — `title` is rendered as escaped text, not HTML, so it is not in scope here) is run through `sanitize_html()` (`app/ingestion/sanitize.py`) at ingest — a strict `nh3` (Rust ammonia) tag/attribute allowlist plus block-to-`<br>`, whitespace-collapse, and Cloudflare email-obfuscation-decode passes. `html_to_text()` in the same module is the plain-text converter used by every non-HTML consumer (LLM prompts in `classifier.py`, keyword matching in `content_filters.py`, fuzzy dedup in `dedup/rules.py`). Any new stored field that will be rendered as HTML must pass through `sanitize_html()`; any that feeds an LLM or matcher uses `html_to_text()`. This applies to new `HtmlListingAdapter` subclasses too: the default `extract_localized_text()` (`app/ingestion/sources/html_base.py`) sanitizes its JSON-LD description before returning it, so a subclass that doesn't override the method still stores sanitized HTML.
- **Redirect SSRF guard** — `httpx`'s `follow_redirects=True` has no same-origin restriction on its own, so any client that follows redirects to an untrusted host (e.g. `FientaAdapter`, which needs it for Fienta's localized-path 302s) must pin every hop to the expected host via a `request` event hook (`host_guard_hook` in `app/ingestion/http_client.py`, shared by `fienta.py`, `html_base.py`, and `refetch.py`) — httpx fires that hook once per redirect hop, making it the only point that can validate the redirect's actual destination. Pre-fetch URL checks alone only validate the un-redirected URL. Apply the same hook pattern to any future adapter that enables `follow_redirects`.
- **Webhook signature verification** — `routers/webhooks.py::inbound_mail()` verifies the Resend inbound-mail webhook via Svix HMAC-SHA256 over `"{svix-id}.{svix-timestamp}.{raw body}"` using `settings.RESEND_WEBHOOK_SECRET`, checking the `svix-id`/`svix-timestamp`/`svix-signature` headers (constants `SVIX_ID_HEADER`/`SVIX_TIMESTAMP_HEADER`/`SVIX_SIGNATURE_HEADER`/`SVIX_SECRET_PREFIX` in `app/constants.py`) plus a `WEBHOOK_TIMESTAMP_TOLERANCE_SECONDS` (300s) replay-window check. Fails closed outside development via the shared `require_configured_secret()` helper (`routers/utils.py`) — replaces the old `?secret=` query-string check.
- **Dependency CVE audit** — `.github/workflows/dependency-audit.yml` runs `pip-audit` (backend) and an `npm-audit` job (`npm audit --audit-level=high`, frontend) on push/PR to `master` and weekly (Mon 04:00 UTC) to catch newly-disclosed CVEs in pinned deps.

## Auth

Magic-link email via `itsdangerous` tokens (no third-party auth). Token generation/verification lives in `app/auth/tokens.py`; magic-link delivery in `app/auth/email.py` (Resend, 3k/mo free tier). The signed session token is the credential — it is **not** stored server-side, so there is no per-token row to delete.

Session tokens are issued after magic-link verification and passed as an `Authorization: Bearer <token>` header (`frontend/src/api/client.ts`, `routers/auth.py::get_current_user`). TTL is 2 days (`SESSION_TTL_DAYS`); magic-link TTL is `MAGIC_LINK_TTL_MINUTES`. Both are settings in `app/config.py` defaulting to values in `shared/app-config.json`.

**Per-email resend cooldown:** `POST /auth/request-link` (and its organizer twin) short-circuits — still returning the same 200 anti-enumeration body, no new row, no send — when an *unused* link for that account was issued within `MAGIC_LINK_RESEND_COOLDOWN_SECONDS` (120). Derived from `expires_at` rather than a stored issued-at (a link created T ago has `expires_at = now + TTL − T`). This is the per-account guard against Resend quota exhaustion from rapid repeats; the `@limiter.limit` decorator is the per-IP one.

**Session revocation:** each session token embeds a `v` (version) claim equal to `users.session_token_version` at issue time; `get_current_user` rejects any token whose `v` no longer matches the stored value. `POST /auth/logout-all` increments that counter (atomic `UPDATE ... RETURNING`, mirroring the magic-link consume pattern), invalidating every previously issued token — including the one making the request. This is the only server-side state in the auth flow.

**Email verification gate (canonical — cross-referenced from Key Database Tables in `docs/data-model.md` and the Data Retention table in `docs/backend-ops.md`):** `_get_or_create_user` (`app/routers/auth.py`) inserts a `User` row on an unauthenticated `POST /auth/request-link` before the address is ever proven reachable — `users.email_verified` defaults `false` at row creation. `verify_magic_link` durably flips it to `true` (atomic `UPDATE ... RETURNING`, same idiom as `logout_all`) the first time that user's magic link is successfully consumed; since a session token can only ever be issued from inside `verify_magic_link`, an `email_verified = false` row is provably one nobody has ever logged into — that guarantee holds going forward from migration `0024_users_email_verified.py`, which blanket-backfilled every pre-migration row to `true` (an already-purged `auth_magic_links` history made deriving real verification status for old rows impossible; see the migration's own comment). `build_daily_feeds` (`_verified_user_ids`, `app/ranking/score.py`) and `send_daily_digests` (`app/email/digest.py`) both filter on `email_verified` so an anonymous POST with someone else's address can't enroll them in the daily digest going forward.

**Known residual risk — magic token in URL query string:** `/auth/verify?token=...` carries the one-time sign-in token in the URL (`AuthVerify.tsx`). URLs can leak via browser history, `Referer` headers, and proxy/server access logs. This is mitigated by the token being single-use (atomic `UPDATE ... WHERE used_at IS NULL ... RETURNING`, closes the TOCTOU race) and short-lived (`MAGIC_LINK_TTL_MINUTES`), so a leaked link has a narrow exploitation window. Moving verification to a POST body would close this gap entirely but adds friction to the email-link UX (the whole point of magic links is a single click) — left as a documented trade-off rather than changed.

**Known residual risk — session tokens in `localStorage`:** both the consumer session token (`frontend/src/lib/auth.ts`) and the organizer session token (`frontend/src/lib/organizerAuth.ts`) are stored in `localStorage`, readable by any script running in the origin. The signed session token is the entire credential (2-day TTL, no server-side row — see above), so a successful XSS is a full, silent account takeover; recovery requires the affected user to hit `logout-all`. This is accepted rather than fixed because the XSS surface is already narrow: the SPA CSP is `script-src 'self'` with no `eval`, and every `dangerouslySetInnerHTML` site runs through DOMPurify (`sanitizeHtml()`, `frontend/src/utils.ts`) on top of the server-side `nh3` sanitization at ingest. An httpOnly + Secure + SameSite=Lax cookie issued by `/auth/verify` would close this residual gap (the Vercel `/api` rewrite already makes the SPA same-origin with the API, so no cross-site cookie problem, and `allow_credentials=False` on CORS still holds since the browser would send it same-origin) — left as a documented trade-off, matching the magic-token-in-URL entry above, rather than a cross-cutting auth-flow change.

**Digest unsubscribe:** `app/routers/unsubscribe.py` (`POST /email/unsubscribe`, `POST /email/resubscribe`) flips `email_digest_opt_in` with no login, using a separately-salted (`AUTH_UNSUBSCRIBE_SALT`) `itsdangerous` token minted per-recipient into every digest email (`UNSUBSCRIBE_TOKEN_TTL_DAYS`, 365 — long-lived so an old inbox email keeps working). The digest's visible link points at the frontend `/unsubscribe?token=...` page (`routes/Unsubscribe/`), which POSTs on mount and offers an Undo/resubscribe button; `send_digest_email` (`app/email/digest.py`) also emits the same token as an RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post: List-Unsubscribe=One-Click` header pair (absolute URL via `settings.BACKEND_URL`, since mail providers call it server-side) so Gmail/Apple Mail render a native one-click button. **Known residual risk — no revocation, unlike session tokens:** the token carries no version claim, so a leaked one stays valid for the full year; accepted because the only effect is toggling a reversible preference flag, mirroring the magic-link residual-risk trade-off above.

**Organizer auth:** a separate parallel track for the self-service submission portal — see `docs/organizer-portal.md` for the full auth/salt/table breakdown.
