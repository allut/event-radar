# Security

What's in here: the OWASP-hardening middleware stack, auth (magic-link, sessions, revocation, residual risks), and the canonical explanations for `require_configured_secret`, the External-URL host-pin rule, and the `email_verified` gate.

Read this before touching `app/main.py`, `app/rate_limit.py`, `app/routers/auth.py`, `app/routers/organizer_auth.py`, `app/routers/admin_auth.py`, `app/auth/`, `app/routers/utils.py`, `app/ingestion/http_client.py`, or any new endpoint (every endpoint needs a `RATE_LIMIT_*`).

## Security Hardening

The backend was hardened against the OWASP Top 10 (2021). The middleware stack and these invariants are wired in `app/main.py`:

- **Rate limiting** — `slowapi` limiter lives in `app/rate_limit.py` (its own module to avoid a circular import between `main.py` and routers), keyed by `client_key()` rather than slowapi's default `get_remote_address` — see the "Rate-limit / audit-log key derivation" bullet below for why. **Every router endpoint** carries `@limiter.limit(...)` — authenticated ones included — with the limit string sourced from a `RATE_LIMIT_*` constant in `app/constants.py` (the only exception is `/health`, see below): public unauthenticated routes (`/auth/request-link` + `/organizer/auth/request-link` → `RATE_LIMIT_AUTH_REQUEST_LINK`, `/auth/verify` + `/organizer/auth/verify` → `RATE_LIMIT_AUTH_VERIFY`, `/webhooks/inbound-mail` → `RATE_LIMIT_WEBHOOK_INBOUND_MAIL`, `/public/showcase` + `/public/prerender-events` → `RATE_LIMIT_PUBLIC`, `/contact` → `RATE_LIMIT_CONTACT`, `/email/unsubscribe` + `/email/resubscribe` → `RATE_LIMIT_UNSUBSCRIBE`, the optional-auth `/events/{id}` → `RATE_LIMIT_EVENTS_DETAIL`); authenticated reads and writes (`/explore` + `/feed` + `/auth/me` → `RATE_LIMIT_BROWSE`, `/feedback*` → `RATE_LIMIT_FEEDBACK`, `/onboarding/persona` + `/users/me` → `RATE_LIMIT_AUTHENTICATED_WRITE`, `/auth/logout-all` + `/organizer/auth/logout-all` → `RATE_LIMIT_LOGOUT_ALL`, every `/organizer/events*` route → `RATE_LIMIT_SUBMIT`, `DELETE /organizer/profile/identities/{provider}` → `RATE_LIMIT_AUTHENTICATED_WRITE`, `GET /organizer/auth/google/start` → `RATE_LIMIT_GOOGLE_SIGNIN_START`, `GET /organizer/auth/google/callback` → `RATE_LIMIT_GOOGLE_SIGNIN_CALLBACK`, the `/organizer/claims*` routes → `RATE_LIMIT_CLAIM` for create/cancel/recheck, `RATE_LIMIT_BROWSE` for reads, `RATE_LIMIT_AUTH_REQUEST_LINK`/`RATE_LIMIT_AUTH_VERIFY` for the claim-intent sign-in link, and two `shared_limit(RATE_LIMIT_SUBMIT, …)` buckets — `claim_event_get`/`claim_event_patch` — across the claim-edit GET/PATCH pairs); plus every `/admin/*` route sharing **one** bucket via `limiter.shared_limit(RATE_LIMIT_ADMIN, scope="admin")` rather than a separate bucket per route (`"10/minute"` total across the whole `/admin` prefix per client — a per-endpoint `@limiter.limit` would let an attacker cycling all 26 admin routes attempt far more than the nominal cap per minute; see also the consecutive-failure lockout below). Add the same decorator + constant to any new endpoint, public or not. `ProxyHeadersMiddleware(trusted_hosts="*")` is registered **last** (so it runs outermost) to rewrite `request.client` from `X-Forwarded-For` before the limiter reads it — without it, Render's proxy would collapse all clients into one bucket. **Ops-verification dependency (accepted trade-off, see the invariant comment at `main.py`):** `trusted_hosts="*"` trusts any peer's `X-Forwarded-For` verbatim, so its safety hinges on the process being reachable *only* through Render's proxy and on Render's edge overwriting inbound `X-Forwarded-For`. Render publishes no stable egress CIDR to pin `trusted_hosts` to, so this stays `"*"` — confirm Render's XFF handling on the dashboard rather than in code, and re-derive if the deployment ever sits behind an additional CDN/proxy or gets a public port.
- **Rate-limit / audit-log key derivation (`app/rate_limit.py::client_key`)** — `ProxyHeadersMiddleware(trusted_hosts="*")` itself rewrites `request.client` from the **leftmost** `X-Forwarded-For` entry (uvicorn's `_TrustedHosts.get_trusted_client_address`), which is attacker-controlled: a client can prepend an arbitrary `X-Forwarded-For` value and every `@limiter.limit(...)`/`shared_limit(...)` becomes a no-op, and every `client=%s`-style log line becomes forgeable. `client_key()` instead derives the key from the **rightmost** XFF entry — the one appended by the single trusted hop immediately adjacent to this process (Render's proxy) — which is correct whether Render appends to or overwrites the header, but depends on there being exactly **one** trusted hop between the client and this process (see the `HOP-COUNT ASSUMPTION` comment next to `ProxyHeadersMiddleware` in `main.py`, alongside the pre-existing `trusted_hosts="*"` invariant).
- **Security headers** — the `add_security_headers` middleware sets CSP/`X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`Cache-Control: no-store` (nothing from a pure JSON API should ever be cached by an intermediary — most importantly `GET /auth/verify`, whose body carries a bearer session token) on every response from the `SECURITY_HEADERS` dict in `app/constants.py`; HSTS (`HSTS_HEADER_*`) is added only outside development (safe only over HTTPS). The CSP is `default-src 'none'` — the app is a pure JSON API with no first-party HTML/script surface. `HostCheckMiddleware` (`app/main.py`, outside development only, wraps `TrustedHostMiddleware`) rejects requests with an unexpected `Host` header — low impact today (nothing builds an absolute URL from the request `Host`) but a one-line hardening against intermediary cache-poisoning scenarios. Its allowlist is resolved by `_resolve_allowed_hosts()`: `settings.RENDER_EXTERNAL_HOSTNAME` (Render's auto-injected public hostname, never set by hand) union `settings.BACKEND_URL`'s hostname, with local/dev hostnames (`DEV_DB_LOCAL_HOSTS`) dropped from either source. **Deliberate fail-open:** if both sources are empty or local (`BACKEND_URL` left at its `localhost` default because the Render dashboard var was never set — the 0.1.6 outage), `_resolve_allowed_hosts()` logs an `ERROR` and returns `[]`, and the caller **skips installing the middleware entirely** rather than installing it with an allowlist that rejects all public traffic — Host validation is cache-poisoning hardening only, so degrading it beats a site-wide outage. Registered *before* (i.e. wraps inside) `ProxyHeadersMiddleware` so a rejected request still gets its real client IP resolved before the reject is logged. Every reject also emits a `LOG_EVENT_HOST_REJECTED` warning naming the offending `Host` and path — previously a rejection was a bare access-log 400 with no signal. `/health` (`HOST_CHECK_EXEMPT_PATHS`) is exempted: Render's health probe reaches the process over the private network, so its `Host` is the instance's rotating internal address, not the resolved allowlist's, and Starlette's `allowed_hosts` has no CIDR support to allowlist it instead.
- **Request body size ceiling** — `MaxBodySizeMiddleware` (`app/main.py`) rejects any request whose body exceeds `MAX_REQUEST_BODY_BYTES` (10 MiB) with 413, before a handler ever reads it. A `Content-Length` request is rejected up front; a chunked request (no `Content-Length`) is rejected mid-stream once the running total crosses the limit, via a wrapped `receive` ASGI callable. It sends the 413 response itself (an ASGI `Response.__call__`) rather than raising `HTTPException` — Starlette places every `add_middleware` entry **outside** its internal `ExceptionMiddleware` (which sits innermost, right next to the router), so an `HTTPException` raised from user-added middleware never reaches it and would surface as a generic 500 instead. Registered so it wraps *inside* `ProxyHeadersMiddleware` (still sees the rewritten client for logging/rate-limiting) — this is the whole-request-body ceiling `IMAGE_UPLOAD_MAX_BYTES` alone doesn't provide (that constant only bounds what the upload handler reads after Starlette has already spooled the full body).
- **API docs** — `/docs`, `/redoc`, and `/openapi.json` are enabled **only** in development (`APP_ENV == "development"`); the strict CSP would block their CDN assets in production anyway.
- **Frontend CSP (`frontend/public/_headers`)** — Cloudflare's static-headers format, copied into `dist/` by the Vite build. Separate from the backend's `default-src 'none'` above: the SPA does have a first-party HTML/script surface, so its policy started narrower-but-non-empty (`script-src 'self'`/`connect-src 'self'`, plus `style-src`/`font-src`/`img-src` exceptions for inline styles, self-hosted fonts, and remote event images). Widened for GA4 (issue #106, follow-up to #55's provisioning) to add exactly `https://www.googletagmanager.com` to `script-src` (the gtag.js loader) and `https://www.google-analytics.com`/`https://www.googletagmanager.com` to `connect-src` (the collect beacon + gtag's own config fetch) — no wildcard subdomains, since GA4's non-regional collection endpoint and loader both resolve to those exact hosts. `frontend/src/lib/gtag.ts` loads gtag.js, sets `client_storage: 'none'` (GA4 stays cookieless — no `_ga`/`_ga_<id>` cookie is ever set — matching the "cookieless and aggregated" claim `frontend/src/content/legal/privacy.*.ts` makes about analytics, and avoiding a cookie-consent-banner obligation this app has never needed) and disables its automatic pageview (`send_page_view: false`), sending pageviews explicitly (`App.tsx`'s `GoogleAnalytics` component, on mount and every route change) through `maskAnalyticsUrl()` so the `/auth/verify` magic-link token or an `/explore` free-text search query string never leaves as a GA4 `page_path`. Also no-ops under Playwright's `navigator.webdriver` flag (`isPrerenderRender()`) so the prerender build (`docs/pipeline.md`'s prerender pipeline, `frontend/scripts/prerender.ts`) never loads GA4 during a snapshot render — it would otherwise send a fake pageview per build and add live network activity for `page.goto`'s `networkidle` wait to settle around. `VITE_GA_MEASUREMENT_ID` (unset in dev; set as a Cloudflare Pages build-time variable only, never committed — mirrors `VITE_API_BASE`) is the single on/off switch: unset, `initGtag()` no-ops and nothing loads. `script-src` also carries a `sha256-…` hash entry for `index.html`'s inline pre-paint theme script (theme-revert-on-refresh fix) — that script has no `nonce` (CSP nonces need a per-request server to mint them; this is a static build), so a hash pinned to its exact byte content is the only way to let it execute without `'unsafe-inline'`. Any new inline `<script>` added to `index.html` needs its own hash added here or the browser silently refuses to run it — no console error surfaces to a user, only a CSP violation report if one is configured. `frontend/src/lib/csp.test.ts` is a drift guard: it re-derives every inline script's hash from the real `index.html` and asserts each one is present in `public/_headers`' document `script-src`, and that `'unsafe-inline'` is never added alongside a hash (a browser ignores hash-based sources entirely once `'unsafe-inline'` is present, silently reopening the exact hole the hash exists to close). It reads `frontend/public/_headers` specifically, not a repo-root `_headers` — Cloudflare Pages only reads the file out of the build output. The dev server sends no CSP at all, so a script blocked by a hash mismatch is invisible locally — verify a CSP change against the *built* `dist/index.html` and `dist/_headers`, not just source, before shipping.
- **CORS** — `CORSMiddleware` with `allow_credentials=False`, kept `False` deliberately even now that auth is a `Set-Cookie` session (see `docs/adr/0001-session-tokens-in-httponly-cookies.md`): the cookie is scoped to this API's own origin and only ever travels through the same-origin `/api` proxy the SPA is served behind (`frontend/functions/api/[[path]].ts`), never a cross-origin browser fetch/XHR, so credentialed CORS would only widen the attack surface for no functional gain. Origins from `settings.CORS_ORIGINS`, methods/headers from `CORS_ALLOWED_METHODS`/`CORS_ALLOWED_HEADERS` constants. `CORS_ORIGINS` also seeds `CsrfOriginCheckMiddleware`'s trusted-origin allowlist (see below) — widening it for CORS silently widens CSRF trust too.
- **CSRF Origin check (`CsrfOriginCheckMiddleware`, `app/main.py`)** — second CSRF layer behind `SameSite=Strict`, added once session tokens moved into cookies (see the Auth section below and `docs/adr/0001-session-tokens-in-httponly-cookies.md`). Rejects any mutating request (`CSRF_UNSAFE_METHODS`: POST/PATCH/DELETE/PUT) whose `Origin` header is present and not in `frozenset(settings.CORS_ORIGINS) | {settings.FRONTEND_URL}`. A request with no `Origin` header is let through — browsers omit it on some simple/no-CORS navigations, and the legitimate server-to-server callers (`/webhooks/inbound-mail`, the RFC 8058 one-click unsubscribe) never send one either. Non-mutating methods (GET, HEAD, OPTIONS, ...) are never checked. **Google sign-in's callback (`GET /organizer/auth/google/callback`, `docs/adr/0002-google-sign-in-oauth-pkce.md`) needs no exemption here** — it's a GET, structurally outside `CSRF_UNSAFE_METHODS`, since the authorization code arrives via a 302's query string rather than a POST body.
- **`require_configured_secret` double gate (dev fail-open)** — `app/routers/utils.py::require_configured_secret()` protects every secret-gated surface (`/admin/*` Basic auth, the inbound webhook's Svix signature check). With the secret unset, it fails open (logs a warning, skips verification) **only** when both `APP_ENV == "development"` **and** the separate `settings.ALLOW_INSECURE_DEV` flag are true — a dev-shaped `APP_ENV` alone is never sufficient, so a stray or never-overridden env var on a real deployment fails closed (503) instead of silently unprotecting the admin surface. `app/main.py`'s lifespan additionally logs an ERROR if `APP_ENV == development` but `DATABASE_URL` resolves to a non-local host (`DEV_DB_LOCAL_HOSTS`), flagging exactly that misconfiguration pattern.
- **Admin auth lockout** — beyond the shared per-client rate-limit bucket above, `routers/admin.py::_require_admin` tracks consecutive Basic-auth failures per `client_key()` in an in-memory dict and locks out further attempts (429) for `ADMIN_AUTH_LOCKOUT_SECONDS` after `ADMIN_AUTH_MAX_FAILURES` consecutive failures — a static username/password pair otherwise has no brute-force damper beyond the rate limit itself. In-memory and single-process (matches this codebase's no-Celery/no-Redis design), so it resets on deploy/restart; accepted since it's a supplement to, not a replacement for, a strong `ADMIN_PASSWORD`.
- **Rate-limit-exempt by design** — `GET /health` (`app/main.py`) carries no `@limiter.limit(...)`: it's a platform health-check probe (Render), and rate-limiting it risks the platform marking the service unhealthy under legitimate probe traffic. This is a deliberate exception to the "every public route gets a rate limit" rule above. `/health` is also exempt from `HostCheckMiddleware`'s Host-header check for the same private-network-probe reason (see above).
- **External-URL sanitization (canonical — cross-referenced from Data Flow §1/§8 and Organizer Event Submission in `docs/pipeline.md`/`docs/organizer-portal.md`)** — the guard picked for a URL field is decided by *whether the server itself fetches it*, not by which field it is. Untrusted `image_url` (rendered into an `href`/`src`, never fetched server-side) passes through `safe_external_url()` (`app/ingestion/http_client.py`), which drops any scheme not in `SAFE_URL_SCHEMES` (guards stored XSS via `javascript:`/`data:` URLs). `event.url` for an adapter-kind source (scraped, **fetched** daily by the refetch job) instead goes through the stronger `safe_fetchable_url()`, which layers a host-allowlist plus `resolves_to_private_ip()` (a DNS-rebinding / private-IP guard) on top of the scheme check. `event.url` for a `user_submission`-kind source is render-only — organizer submissions are excluded from the refetch job (`refetch.py::_select_candidates`, `submitted_by_organizer_id IS NULL`) since an organizer edits their own row directly via PATCH — so `insert_normalized_event()` (`app/ingestion/adapter.py`) picks `safe_external_url()` for it too, off `source.kind == SOURCE_KIND_USER_SUBMISSION`; an organizer's own ticketing domain is otherwise never on `ALLOWED_SOURCE_HOSTS`. Apply the matching guard to any new field, keyed on the same fetched-vs-rendered question. The frontend repeats the scheme check as defense-in-depth in `safeUrl()` (`frontend/src/utils.ts`) — route every untrusted URL through it before putting it in an `href`/`src`; `sanitizeHtml()` (same file) is the matching defense-in-depth pass for the HTML fields below, applied at both `dangerouslySetInnerHTML` sites (`EventDetail.tsx`). **Organizer `image_url` is additionally host-restricted** (`routers/organizer_events.py::_check_image_host`, `ALLOWED_IMAGE_HOSTS = {"res.cloudinary.com"}`): the scheme check alone would let an organizer point `image_url` at an arbitrary https host, which the daily digest embeds as an `<img>` — an unconsented tracking pixel leaking each recipient's IP/open-time to a third party. Submissions must go through the signed `POST /organizer/events/image` Cloudinary upload instead; scraped (non-organizer) sources are unaffected.
- **Stored-HTML sanitization** — every scraped rich-text field the frontend renders as HTML (the localized `description`/`important_info` blocks — `title` is rendered as escaped text, not HTML, so it is not in scope here) is run through `sanitize_html()` (`app/ingestion/sanitize.py`) at ingest — a strict `nh3` (Rust ammonia) tag/attribute allowlist plus block-to-`<br>`, whitespace-collapse, and Cloudflare email-obfuscation-decode passes. `html_to_text()` in the same module is the plain-text converter used by every non-HTML consumer (LLM prompts in `classifier.py`, keyword matching in `content_filters.py`, fuzzy dedup in `dedup/rules.py`). Any new stored field that will be rendered as HTML must pass through `sanitize_html()`; any that feeds an LLM or matcher uses `html_to_text()`. This applies to new `HtmlListingAdapter` subclasses too: the default `extract_localized_text()` (`app/ingestion/sources/html_base.py`) sanitizes its JSON-LD description before returning it, so a subclass that doesn't override the method still stores sanitized HTML. **Two allowlists, one sanitizer:** `sanitize_html()` takes optional `tags`/`attrs` overrides, and the organizer-submission boundary (`app/routers/organizer_events.py`, #267) passes the narrower `ORGANIZER_HTML_SANITIZE_ALLOWED_TAGS`/`ORGANIZER_HTML_SANITIZE_ALLOWED_ATTRS` — the set the `RichTextEditor` (Tiptap) toolbar can actually produce — so organizer-authored `description`/`important_info` is held to a tighter allowlist than scraped source HTML. An `attribute_filter` enforces the resolved allowlist as the true ceiling (nh3 otherwise always keeps a few generic attributes like `title`/`lang`, which the organizer allowlist omits); `rel` is the one exemption, since that value is nh3's own injected `noopener noreferrer`, not organizer input.
- **Redirect SSRF guard** — `httpx`'s `follow_redirects=True` has no same-origin restriction on its own, so any client that follows redirects to an untrusted host (e.g. `FientaAdapter`, which needs it for Fienta's localized-path 302s) must pin every hop to the expected `(scheme, hostname, port)` via a `request` event hook (`host_guard_hook` in `app/ingestion/http_client.py`, shared by `fienta.py`, `html_base.py`, and `refetch.py`) — httpx fires that hook once per redirect hop, making it the only point that can validate the redirect's actual destination, and re-runs the private-IP check (`resolves_to_private_ip()`) on every hop too. Pre-fetch URL checks alone only validate the un-redirected URL. Apply the same hook pattern to any future adapter that enables `follow_redirects`.
- **Webhook signature verification** — `routers/webhooks.py::inbound_mail()` verifies the Resend inbound-mail webhook via Svix HMAC-SHA256 over `"{svix-id}.{svix-timestamp}.{raw body}"` using `settings.RESEND_WEBHOOK_SECRET`, checking the `svix-id`/`svix-timestamp`/`svix-signature` headers (constants `SVIX_ID_HEADER`/`SVIX_TIMESTAMP_HEADER`/`SVIX_SIGNATURE_HEADER`/`SVIX_SECRET_PREFIX` in `app/constants.py`) plus a `WEBHOOK_TIMESTAMP_TOLERANCE_SECONDS` (300s) replay-window check. Fails closed outside development via the shared `require_configured_secret()` helper (`routers/utils.py`) — replaces the old `?secret=` query-string check. A validly-signed request is still replayable within that 300s window unless the `svix-id` itself is deduped — `_seen_webhook_ids`, a bounded in-memory LRU (`WEBHOOK_SEEN_IDS_MAX_ENTRIES`, mirroring `admin.py`'s `_admin_auth_failures` pattern), rejects a repeated id with 401 (OWASP audit G-6). The sender-domain allowlist check (`_sender_domain_allowed()` against `NEWSLETTER_SENDER_ALLOWED_DOMAINS`) also runs — and can reject — before the `RawInboundEmail` row is ever inserted, so a non-allowlisted sender's content is never persisted.
- **Dependency CVE audit** — `.github/workflows/dependency-audit.yml` runs `pip-audit` (backend) and an `npm-audit` job (`npm audit --audit-level=moderate`, frontend) on push/PR to `master` and weekly (Mon 04:00 UTC) to catch newly-disclosed CVEs in pinned deps.

## Auth

Magic-link email via `itsdangerous` tokens (no third-party auth). Token generation/verification lives in `app/auth/tokens.py`; magic-link delivery in `app/auth/email.py` (Resend, 3k/mo free tier). The signed session token is the credential — it is **not** stored server-side, so there is no per-token row to delete.

**Tokens are signed, not encrypted.** Every token in `app/auth/tokens.py` uses `itsdangerous.URLSafeTimedSerializer`, which base64-encodes a *signed* payload — anyone holding a cookie can read its plaintext claims (e.g. `{"uid": N, "v": N}`, `{"oid": N, "v": N}`, the OAuth state cookie's `{"state", "code_verifier", "track"}`). This is fine today: no field in any payload is a secret, the cookies are httpOnly + Secure + `SameSite=Strict` (`Lax` for the two OAuth state cookies, by necessity — see below), and the PKCE verifier is single-use and only readable by someone who already holds the cookie. A future field added to any token payload must not be assumed confidential.

Session tokens are issued after magic-link verification and set as an httpOnly + Secure + `SameSite=Strict` cookie (`SESSION_COOKIE_NAME = "session"`, scoped `Path=/api`; `app/constants.py`, `routers/auth.py::get_current_user`) — never readable by client-side JS. TTL is 2 days (`SESSION_TTL_DAYS`); magic-link TTL is `MAGIC_LINK_TTL_MINUTES`. Both are settings in `app/config.py` defaulting to values in `shared/app-config.json`. Because JS can't read or clear an httpOnly cookie, the client only ever sees a boolean *signed-in hint* in `localStorage` (`frontend/src/lib/auth.ts`) — it carries no credential value and grants no access on its own, and its presence in `localStorage` is what keeps the existing cross-tab `storage`-event sign-out propagation working. Sign-out is consequently a server concept: `POST /auth/logout` clears the cookie for the current device only, alongside `logout-all` below for every device (see `docs/adr/0001-session-tokens-in-httponly-cookies.md` for the full rationale and rejected alternatives).

**Per-email resend cooldown:** `POST /auth/request-link` (and its organizer twin) short-circuits — still returning the same 200 anti-enumeration body, no new row, no send — when an *unused* link for that account was issued within `MAGIC_LINK_RESEND_COOLDOWN_SECONDS` (120). Derived from `expires_at` rather than a stored issued-at (a link created T ago has `expires_at = now + TTL − T`). This is the per-account guard against Resend quota exhaustion from rapid repeats; the `@limiter.limit` decorator is the per-IP one.

**Session revocation:** each session token embeds a `v` (version) claim equal to `users.session_token_version` at issue time; `get_current_user` rejects any token whose `v` no longer matches the stored value. `POST /auth/logout-all` increments that counter (atomic `UPDATE ... RETURNING`, mirroring the magic-link consume pattern), invalidating every previously issued token — including the one making the request. This is the only server-side state in the auth flow.

**Email verification gate (canonical — cross-referenced from Key Database Tables in `docs/data-model.md` and the Data Retention table in `docs/backend-ops.md`):** `_get_or_create_user` (`app/routers/auth.py`) inserts a `User` row on an unauthenticated `POST /auth/request-link` before the address is ever proven reachable — `users.email_verified` defaults `false` at row creation. `verify_magic_link` durably flips it to `true` (atomic `UPDATE ... RETURNING`, same idiom as `logout_all`) the first time that user's magic link is successfully consumed. Google sign-in (ADR 0002, #296) is the column's second writer — `routers/auth.py::_apply_google_linking_gate`'s authoritative/absorption branches also flip it to `true`, in the same transaction as the identity link, before minting a session — but every session-issuing path still flips it in the same transaction as issuance, so an `email_verified = false` row remains provably one nobody has ever logged into — that guarantee holds going forward from migration `0024_users_email_verified.py`, which blanket-backfilled every pre-migration row to `true` (an already-purged `auth_magic_links` history made deriving real verification status for old rows impossible; see the migration's own comment). `build_daily_feeds` (`_verified_user_ids`, `app/ranking/score.py`) and `send_daily_digests` (`app/email/digest.py`) both filter on `email_verified` so an anonymous POST with someone else's address can't enroll them in the daily digest going forward.

**Resolved — magic token moved out of the verify request's URL:** the email link still carries the one-time token as `?token=...` (`AUTH_VERIFY_PATH`, `app/auth/email.py`) — a clickable link can't avoid that — but `AuthVerify.tsx` strips it from the address bar via `window.history.replaceState` before ever issuing the verify call, and that call is now `POST /auth/verify` with the token in the request body (`VerifyTokenBody`), not a `GET .../verify?token=...`. This closes the part of the original risk that mattered most: the token no longer appears in a request line that a proxy or server access log records, and it no longer persists in browser history past the initial click. The token remains single-use (atomic `UPDATE ... WHERE used_at IS NULL ... RETURNING`) and short-lived (`MAGIC_LINK_TTL_MINUTES`) as before. What's left — the token still transits the URL of the initial email-link click itself (so it can still appear in a mail client's own history/`Referer` on that first navigation) — was judged not worth the single-click UX cost of a redirect/landing-page indirection, and is accepted on the same narrow-window reasoning as before.

**Resolved — session tokens moved out of `localStorage` into httpOnly cookies:** both the consumer and organizer session tokens are now set as httpOnly + Secure + `SameSite=Strict` cookies (`SESSION_COOKIE_NAME`/`ORGANIZER_SESSION_COOKIE_NAME`, `app/constants.py`) instead of being stored in `localStorage`, so client-side JS — including a successful XSS payload — can no longer read the credential at all. This reopens a decision this doc previously recorded as *accepted*: the earlier reasoning (narrow XSS surface — CSP `script-src 'self'`, DOMPurify on every `dangerouslySetInnerHTML` site, server-side `nh3` sanitization at ingest) was a probability argument against a total-consequence risk (a single XSS was a silent, full account takeover for the token's 2-day life), and a supply-chain compromise of any frontend dependency executes happily under `script-src 'self'` regardless of how narrow the first-party surface is. Being pre-soft-launch made the migration free — no live sessions to strand. Moving the credential into a cookie opened a CSRF surface that a Bearer header made structurally impossible; that's mitigated by `SameSite=Strict` (free here — the SPA has no SSR, so no flow needs the cookie on a cross-site navigation) plus the CSRF Origin-check middleware described above. Full option analysis in `docs/adr/0001-session-tokens-in-httponly-cookies.md`.

**Digest unsubscribe:** `app/routers/unsubscribe.py` (`POST /email/unsubscribe`, `POST /email/resubscribe`) flips `email_digest_opt_in` with no login, using a separately-salted (`AUTH_UNSUBSCRIBE_SALT`) `itsdangerous` token minted per-recipient into every digest email (`UNSUBSCRIBE_TOKEN_TTL_DAYS`, 365 — long-lived so an old inbox email keeps working). The digest's visible link points at the frontend `/unsubscribe?token=...` page (`routes/Unsubscribe/`), which POSTs on mount and offers an Undo/resubscribe button; `send_digest_email` (`app/email/digest.py`) also emits the same token as an RFC 8058 `List-Unsubscribe` / `List-Unsubscribe-Post: List-Unsubscribe=One-Click` header pair (absolute URL via `settings.BACKEND_URL`, since mail providers call it server-side) so Gmail/Apple Mail render a native one-click button. **Known residual risk — no revocation, unlike session tokens:** the token carries no version claim, so a leaked one stays valid for the full year; accepted because the only effect is toggling a reversible preference flag, mirroring the magic-link residual-risk trade-off above. Two more consequences of the same trade-off, accepted for the same reason: (1) `token` is a query parameter on both `POST` routes, so it lands in uvicorn access logs (shipped to the Axiom drain) and any intermediary log — unlike the magic-link token, which was deliberately moved out of `/auth/verify`'s URL into the request body for this exact reason (see "Resolved" below); the two tokens are handled inconsistently on purpose, since the magic-link token grants a full session and this one only flips a boolean. (2) The same token authorizes `POST /email/resubscribe`, so a leaked token can silently re-opt-in a user who had unsubscribed — again bounded by the "reversible preference flag" ceiling on impact.

**Organizer auth:** a separate parallel track for the self-service submission portal — see `docs/organizer-portal.md` for the full auth/salt/table breakdown.

**Google sign-in (narrative — the per-track subsections below carry the endpoint/cookie inventory):** a second, permanently-coexisting sign-in method on both tracks, added via server-side OAuth 2.0 authorization-code flow with PKCE (S256) — no Google Identity Services JS, no rendered widget/iframe, just a first-party link that top-level-navigates to `accounts.google.com` and back to a first-party callback. Full rationale, rejected alternatives, and the cookie/CSRF/CSP delta are in `docs/adr/0002-google-sign-in-oauth-pkce.md`; this subsection is the narrative summary of the two load-bearing security decisions.

*The flow, once:* the callback exchanges the authorization code for tokens server-to-server, verifies the ID token (`iss`/`aud`/RS256 signature via `PyJWKClient` against Google's published JWKS), and only then hands the verified `{sub, email, email_verified, hd}` claims to a per-track **linking gate** (`_apply_google_linking_gate` in `app/routers/auth.py` and `app/routers/organizer_auth.py`) that decides what account, if any, the identity attaches to before a normal session cookie is minted — exactly like `POST /auth/verify` mints one today.

*The linking gate is authoritative-only, with no exceptions.* A Google identity auto-links into an existing account only where Google is authoritative for the address — `@gmail.com`/`@googlemail.com`, or an `hd` (hosted-domain) claim, both requiring `email_verified: true`. Every other address goes through one confirmation magic link before any identity row is created. This exists because Google's own verification guidance says it is *not* authoritative for `email_verified: true` on a non-Gmail/non-Workspace address — that flag can be `true` merely because the address was verified at Google-account creation, while ownership of the underlying third-party mailbox may since have changed. Without the authoritative gate, an attacker who acquires an abandoned third-party address could walk straight into an existing account that used it. An earlier version of the consumer-track gate absorbed an existing unverified `User` row (a placeholder any unauthenticated caller could have created via `POST /auth/request-link`) unconditionally, on the reasoning that the row holds no personas/feedback/bookmarks and so "there is nothing to take over" — but the row's *email address* is itself the thing being claimed, and a non-authoritative Google identity proves nothing about ownership of that address (OWASP audit M-1). That branch was removed: an unverified row now only auto-links when the identity is also authoritative; a non-authoritative identity falls through to the confirmation-magic-link path like any other non-authoritative case.

*Two new cookies, one per track — the app's first non-`Strict` cookies.* The top-level cross-site redirect back from `accounts.google.com` doesn't send a `SameSite=Strict` cookie, so the short-lived state+PKCE-verifier cookie (`oauth_state` / `organizer_oauth_state`) is `SameSite=Lax` instead — everywhere else in this app is still `Strict`, so a future reader must check `SameSite` per-cookie rather than assume it app-wide. `CsrfOriginCheckMiddleware` needs no exemption for the callback: it's a `GET` (the code arrives via a 302's query string), structurally outside `CSRF_UNSAFE_METHODS`.

**Google sign-in (organizer track, `docs/adr/0002-google-sign-in-oauth-pkce.md`):** server-side OAuth 2.0 authorization-code + PKCE (S256), flag-gated off by default (`GOOGLE_SIGNIN_ORGANIZER_ENABLED`, both endpoints 404 when off). `GET /organizer/auth/google/start` signs `{state, code_verifier, track}` (`app/auth/tokens.py::generate_oauth_state_token`, own salt `AUTH_OAUTH_STATE_SALT`) into a new cookie kind, `organizer_oauth_state` — **the first non-`Strict` cookie in this app**: httpOnly, Secure, but `SameSite=Lax` (required to survive the top-level cross-site redirect back from `accounts.google.com`; `SameSite=Strict` is not sent on that leg), `Path=/api/organizer/auth/google/callback` (narrower than the session cookie's `/api/organizer` — read on exactly one route), 10-minute TTL (`OAUTH_STATE_TTL_MINUTES`). `GET /organizer/auth/google/callback` verifies the state, exchanges the code for tokens server-to-server (`http_post`, never a browser request), verifies the ID token (PyJWT `PyJWKClient` against Google's published JWKS — see `docs/conventions.md`'s `PyJWKClient` entry among the documented `http_get`/`http_post` bypasses for why this one call bypasses the shared retry wrapper), then applies the linking gate: an existing `organizer_identities` row logs in directly; a new provider identity is auto-linked to (or creates) an `Organizer` row only when Google is authoritative for the address (`@gmail.com`/`@googlemail.com` or an `hd` claim, both requiring `email_verified: true`) — every other address goes through one confirmation magic link (`OrganizerMagicLink.pending_google_sub`) before any `organizer_identities` row is created, closing the account-takeover path where Google's own `email_verified` is honest-but-not-authoritative for a third-party address it didn't issue. The state cookie is single-use and deleted on every outcome, success or failure; every failure path (bad/expired/mismatched state, denied consent, token-exchange or verification failure) redirects back to the organizer login page with an error code — **never a 500**. `Organizer.email` is never written from the token; `sub` is the sole match key. `DELETE /organizer/profile/identities/{provider}` is an unconditional hard-delete (no last-factor guard — magic link always remains as a fallback sign-in path) that bumps `session_token_version` and re-issues the caller's own cookie at the new version, so unlinking is a sign-out-everywhere-but-here shape, mirroring `logout-all`.

**Google sign-in (consumer track, #296):** the mirror of the organizer flow above — same PKCE/state-cookie/never-a-500 shape, own flag (`GOOGLE_SIGNIN_CONSUMER_ENABLED`) and own cookie, `oauth_state` (`Path=/api/auth/google/callback`, `SameSite=Lax` — the app's **second** non-`Strict` cookie, so a future reader must check `SameSite` per-cookie rather than assume `Strict` app-wide), `GET /auth/google/start`/`GET /auth/google/callback`, `DELETE /users/me/identities/{provider}`. Same `verify_oauth_state_token(..., track="user")` check keeps a consumer state token from ever verifying against the organizer callback or vice versa — confirmed by a dedicated cross-track test. The consumer-track gate diverges from the organizer track only by flipping `User.email_verified` on every auto-link/absorb path (`Organizer` has no analogous column) — an unverified existing `User` row auto-links exactly when the identity is authoritative, same as any other row; a non-authoritative identity always goes through the confirmation magic link first, whether or not a `User` row already exists (OWASP audit M-1 — see above). `User.email_verified` now has two writers — `verify_magic_link` (unchanged) and this callback's authoritative auto-link branch — so a future reader must not assume only a consumed magic link ever sets it. `verify_magic_link`'s confirmation-link branch (a non-authoritative Google identity's `AuthMagicLink.pending_google_sub`) links the identity the moment the address is proven, exactly mirroring the organizer track's `verify_organizer_magic_link`.

**Admin console auth (issue #154):** a third, distinct track behind `/admin/auth/*` (`app/routers/admin_auth.py`) for the lazy-loaded `/admin/*` frontend shell — password + a required TOTP step (RFC 6238) against the same `ADMIN_USERNAME`/`ADMIN_PASSWORD` env vars the pre-existing HTTP Basic surface (`app/routers/admin.py::_require_admin`) already checks, not a new credential pair. Session is an httpOnly/Secure/`SameSite=Strict` cookie (`ADMIN_SESSION_COOKIE_NAME`, `Path=/api/admin`) minted by `app/auth/tokens.py::generate_admin_session_token` — distinct salt (`AUTH_ADMIN_SESSION_SALT`) so it can never verify as a user/organizer token, but unlike those two it carries no id or `session_token_version` claim: there is no admins table, so "a valid session" is the only fact worth asserting, and revocation is TTL expiry only (`ADMIN_SESSION_TTL_SECONDS`, 12h — shorter than the 2-day consumer/organizer TTL precisely because there's no other revocation path; see `docs/adr/0001-session-tokens-in-httponly-cookies.md`). `_require_admin` accepts **either** this cookie **or** HTTP Basic, but only on the two non-PII read-only routes (`GET /admin/counts`, `GET /admin/stats`) — so existing `curl -u`-based tooling still works for those. Every other `GET` (`/admin/reports`, `/admin/events/{id}`, `/admin/submissions`, `/admin/claims`, `/admin/dedup/groups`) and every mutating (`POST`) route instead requires `get_current_admin`, which accepts **only** the session cookie (OWASP audit F3 — the PII-bearing GETs disclose reporter/organizer PII, including `is_illegal_allegation`, so a leaked plaintext password alone must not be enough to read them; `/admin/dedup/groups` moved to session-only too in OWASP audit G-5, since it discloses unpublished/moderation-sensitive event content — `title`, `venue`, `url`, `is_explicit` — for `draft`/`classified`/`rejected` rows, not just aggregate counts). This split exists because the Basic branch only ever checks `ADMIN_USERNAME`/`ADMIN_PASSWORD` — it never verifies TOTP — so accepting it on a PII-disclosing or mutating route would make the console's required second factor bypassable with the password alone (fixed post-launch; see the OWASP audit's H-1). Failed `/admin/auth/login` attempts (wrong password or wrong/reused TOTP code) share the *same* consecutive-failure lockout counter as failed Basic-auth attempts (`docs/backend-ops.md`'s Admin Endpoints section has the full helper breakdown) — a leaked admin password can't be brute-forced faster by splitting attempts across the two auth surfaces. The two surfaces do **not** share a rate-limit bucket: `POST /admin/auth/login` carries its own `@limiter.limit(RATE_LIMIT_ADMIN_LOGIN)`, and `admin_auth.py`'s other two routes carry their own buckets too (`POST /admin/auth/logout` → `RATE_LIMIT_LOGOUT`, `GET /admin/auth/me` → `RATE_LIMIT_BROWSE`) — all three distinct from the `limiter.shared_limit(RATE_LIMIT_ADMIN, scope="admin")` bucket the 26 routes in `app/routers/admin.py` share — the lockout counter is what's shared, not the bucket. TOTP secret enrollment is a one-time local script (`backend/scripts/admin_totp_enroll.py`), not an app endpoint — there are no backup codes, so losing the authenticator means rotating `ADMIN_TOTP_SECRET`. The session token also carries an `"e"` (epoch) claim, derived (`app/auth/tokens.py::_admin_session_epoch`) as a SHA-256 digest of `ADMIN_SESSION_EPOCH` + `ADMIN_PASSWORD` + `ADMIN_TOTP_SECRET` rather than from the standalone env var alone (OWASP audit F4) — so rotating either credential, not just bumping `ADMIN_SESSION_EPOCH` on a redeploy, auto-invalidates every outstanding admin session with no separate revocation step to remember.
