# Data Model

What's in here: every key database table and what its columns mean. Read this before writing a migration, a query touching a new column, or a serializer.

## Key Database Tables

- `users` — email (citext unique), email_verified (bool, set true on first successful magic-link verification — see `docs/security.md`'s email verification gate; gates `build_daily_feeds`/`send_daily_digests`), locale (et|en|ru), home_city, email_digest_opt_in (bool, gates the daily digest send), session_token_version (int, bumped to revoke all sessions — see `docs/security.md`)
- `auth_magic_links` — token_hash (sha256), expires_at, used_at; one-use only; `pending_google_sub` (nullable) marks a link sent to confirm a pending Google-identity link (ADR 0002) rather than to start a session — no second token type
- `user_identities` — linked external sign-in provider identities (ADR 0002): `user_id` FK (`ON DELETE CASCADE`), `provider` (data value, e.g. `"google"` — not hardcoded), `provider_sub`, `created_at`. `UniqueConstraint("provider", "provider_sub")` is per-table, not global — the same Google account may hold both a `User` row and an `Organizer` row that never merge, mirroring the `auth_magic_links`/`organizer_magic_links` split. Deliberately no `email` column: the address lives on `users.email`/`organizers.email`, and a provider identity is keyed only by its stable `sub`. Plain index on `user_id` for the reverse "which providers does this account have linked" lookup.
- `personas` — 9 static personas with JSONB affinity vectors; display names in et/en/ru
- `user_personas` — M2M join with a per-rank `weight`. Onboarding is a ranked 1–`PERSONA_MAX_SELECTABLE` (3) multi-pick; each pick's weight comes from `PERSONA_RANK_WEIGHTS` by position (1.0 / 0.4 / 0.2), first pick leads (`routers/onboarding.py`)
- `sources` — ingestion source registry
- `raw_events` — source payload as JSONB
- `event_sources` — M2M: links events to source + external_id; unique index on `(source_id, external_id)` enforces ingestion idempotency at the DB level (migration 0007)
- `events` — normalized: slug, title_orig, description_orig, important_info (ticket/access notes block scraped from HTML-listing sources), url, image_url, price_hint (raw price text from ingestion, fed to LLM classification), starts_at/ends_at, venue_name/venue_address, lat/lng (backfilled by the geocoding job when missing), price_min/price_max/currency (parsed from price_hint by classification), has_free_tier (paid event that also offers a free/companion/member tier; OR-merged, see Classification in `docs/pipeline.md`), status (draft→classified→published|cancelled — `published` is set by the publish gate, not directly by classification), is_explicit (NSFW filter flag), is_non_event (non-event filter flag: gift cards/merch/webinars; blocks the publish gate), is_out_of_area (LLM `in_target_city` signal; blocks the publish gate), detail_refetched_at/detail_refetch_count (bookkeeping for the daily detail-refetch sync), geocode_attempted_at (bookkeeping for the geocoding backfill), title_localized/description_localized/important_info_localized (JSONB `{locale: html}`, filled by per-locale page fetches at ingest, by the organizer submit/edit form's per-locale fields, and backfilled per-missing-locale by the daily detail-refetch pass — a source publishing one page with multiple languages concatenated in a single field is stored as-is, unsplit), dedup_group_id, created_at, updated_at (trigger-maintained, migration 0027 — bumped only when a column other than `detail_refetched_at`/`detail_refetch_count`/`geocode_attempted_at` actually changes, so the prerender pipeline's change-detection (issue #80, `GET /public/prerender-events`) doesn't see a marker mismatch on every routine sync pass)
- `event_classifications` — categories[], vibes[], quality_score, why_go_bullets[3], why_go_localized JSONB ({locale: [bullets]}), language_detected, model_used
- `user_event_feedback` — two signal classes: **preference** signals (like/dislike/bookmark, `PREFERENCE_SIGNALS`) are a current-state model — one row per (user, event), enforced by a partial unique index (migration 0019); POST `/feedback` upserts, DELETE `/feedback/{event_id}` removes. **Passive** signals (view/click_external, the rest of `VALID_SIGNALS`) stay append-only/multi-row (page-view + ticket-click analytics, not covered by the index). `GET /feedback/events?signal=` reads the preference rows (Saved Events page). Mixing the two under one upsert-by-(user,event) rule would let a ticket click overwrite a bookmark — keep them split.
- `user_event_scores` — cached ranking score per (user, event); unique constraint. Cache is invalidated by deleting **all** rows for a user whenever that user records or removes a **score-affecting** feedback signal (`like`/`dislike` — `SCORE_AFFECTING_SIGNALS`, `app/constants.py`) or changes their personas — the affinity / indirect-feedback terms mean either change shifts scores on every co-categorical event, so per-row invalidation would leave neighbours stale. `bookmark` and the passive `view`/`click_external` signals are never read by the scorer (`ranking/score.py`, `browse.py` both filter feedback to `like`/`dislike` only), so recording/removing those does **not** invalidate — gating on `SCORE_AFFECTING_SIGNALS` keeps the cache warm across every ticket click and bookmark instead of wiping it on every one. Shared via `invalidate_user_scores()` (`routers/utils.py`), called from `routers/feedback.py` (record/delete, gated) and `routers/onboarding.py` (`set_persona`, before the feed rebuild, unconditional).
- `daily_feeds` — user_id, feed_date, event_ids BigInteger[]
- `organizers` — self-service submission account (see `docs/organizer-portal.md`): email (citext unique), locale, session_token_version (int, bumped to revoke all organizer sessions), verified (bool, default false — gates auto-publish, flipped true by an admin's first `POST /admin/submissions/{id}/approve`)
- `organizer_magic_links` — mirrors `auth_magic_links` for the organizer auth track: token_hash (sha256), expires_at, used_at, `pending_google_sub`
- `organizer_identities` — mirrors `user_identities` for the organizer auth track (`organizer_id` FK, `ON DELETE CASCADE`); same per-table unique constraint and no-email-column reasoning
- `organizer_image_uploads` — one row per successful `POST /organizer/events/image` upload (organizer_id, created_at); exists purely to count-then-act against `ORGANIZER_DAILY_IMAGE_UPLOAD_CAP` (an upload can happen before the organizer ever submits/edits an event, so it can't be derived from `Event.created_at` the way `ORGANIZER_DAILY_SUBMISSION_CAP` is). Never read back; no retention sweep.
- `venues` — an organizer's reusable venue, built up and picked across event submissions (#173/#174; the submit/edit form picks one via `frontend/src/components/VenuePicker/`): `organizer_id` FK (`ON DELETE CASCADE`), `name`/`name_en`/`name_ru` as separate per-locale text columns (personas-table pattern, not Event's JSONB pattern; `address` is a single non-localized column — street names don't translate across locales), `lat`/`lng` (backfilled by the geocoding job's `geocode_pending_venues` sub-pass, then propagated onto linked `Event`s — both initial fill and later address-correction resync — by `_sync_venue_linked_coords`, #179), `price_min`/`price_max`/`currency` (copy-in defaults only — not authoritative once copied onto an Event), `geocode_attempted_at` (own cooldown clock, separate from `Event.geocode_attempted_at`), `deleted_at` (soft-delete — hides the venue from `GET /organizer/venues` but never touches events that already reference it). CRUD lives under `routers/organizer_venues.py`, scoped to `get_current_organizer`; update/delete 404 (not 403) on cross-organizer access, matching `organizer_events.py`'s convention. Editing any address field synchronously clears `lat`/`lng`/`geocode_attempted_at` to force re-resolution. Daily creation capped by `ORGANIZER_DAILY_VENUE_CREATION_CAP`, same count-then-insert pattern as `ORGANIZER_DAILY_SUBMISSION_CAP`.
- `events.submitted_by_organizer_id` (FK → `organizers.id`, indexed) / `events.needs_review` (bool, partial index on true) — attribute an organizer-submitted event back to its account and flag it for the admin post-hoc review queue (`GET /admin/submissions`)
- `publishers` — organizer event claiming foundation (#409/#410; see CONTEXT.md's Event Claiming glossary): the real-world entity a claim is granted against. `source_id` FK, nullable `external_id` (unique with `source_id` — one row per Fienta organizer id or Piletilevi promoter id, `external_id` NULL for the single KUMU/Estonia Concert Hall row), `name`, `status` (`active`/`retired`). `event_sources.publisher_id` (nullable FK, `ON DELETE SET NULL`) links a listing to its resolved Publisher. Schema only as of #410 — no ingestion/admin code populates it yet.
- `claims` — an organizer's claim over a Publisher or an event series (#409/#410). `organizer_id` FK (`ON DELETE CASCADE`), `kind` (`publisher`/`series`, polymorphic tag), `publisher_id` (nullable FK, set for `kind="publisher"`) / `event_series_key` (nullable text, set for `kind="series"` — the `event_series_key()` tuple from `routers/utils.py` serialized as `"<normalized_title>\x1f<normalized_venue>"`), `status` (`pending`/`approved`/`revoked`). Schema only as of #410.
- `events.pinned_fields` — JSONB array (default `[]`) of field names a claim has pinned against overwrite by ingestion/detail-refetch; a per-locale text field (`title_localized`/`description_localized`/`important_info_localized`) is pinned per-locale via a `"<field>:<locale>"` entry. Price fields (`price_min`/`price_max`/`currency`/`has_free_tier`) never participate. Schema only as of #410 — no read path enforces pinning yet.
