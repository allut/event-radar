# Backend Operations

What's in here: deployment topology, admin endpoints, data retention/cleanup, logging, and maintenance scripts.

Read this before touching `render.yaml`, `vercel.json`, `app/routers/admin.py`, `app/cleanup.py`, `app/logging_config.py`, or `backend/scripts/`.

## Deployment

Production runs on three free-tier services:

- **Backend — Render web service** (`render.yaml`): `rootDir: backend`, health check `/health`, `plan: free`, `PYTHON_VERSION=3.12` pinned to match CI (`.github/workflows/tests.yml`) and the devcontainer — Render's unpinned default drifted to a newer Python that CI never exercises. Migrations run at boot — `startCommand` chains `alembic upgrade head && uvicorn ...` because Render's `preDeployCommand` is paid-only. Secrets (`DATABASE_URL` in asyncpg form `postgresql+asyncpg://...?ssl=require`, `ADMIN_PASSWORD`, `INTERNAL_TOKEN`, LLM/Resend keys, `CORS_ORIGINS`, `FRONTEND_URL`, `BACKEND_URL` — the API's own absolute URL, `https://event-radar-api.onrender.com`, needed by the digest email's RFC 8058 `List-Unsubscribe` header since mail providers call it server-side and can't go through the SPA's relative `/api` proxy, `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` — organizer image upload, see `docs/organizer-portal.md`) are `sync: false` env vars; `SECRET_KEY` is auto-generated. There is **no Render cron service** — Render cron jobs are paid.
- **Frontend — Vercel** (`frontend/vercel.json`): static Vite build. The API client calls a relative `/api` prefix, so a rewrite proxies `/api/:path*` to the Render URL **and strips the `/api` prefix** (backend routes have no `/api` prefix — mirrors the dev Vite proxy); a second rewrite is the SPA fallback to `index.html`. Same-origin proxying also sidesteps CORS. `vercel.json` also carries a `headers` block applying security headers to the served HTML document (`X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, HSTS, and a **tailored** CSP) — the backend's `default-src 'none'` CSP only covers JSON API responses, not the app document. The SPA CSP is `default-src 'self'` with `img-src 'self' https: data:` (event images come from arbitrary source hosts), `style-src 'self' 'unsafe-inline'` (React inline styles), and `script-src`/`connect-src`/`font-src` all `'self'` — the latter works because fonts are **self-hosted** (`@fontsource/dm-sans` + `@fontsource/cormorant-garamond`, imported in `src/main.tsx`, bundled into the build; the former Google Fonts `<link>` is gone) and Vercel Analytics/Speed Insights are served first-party under the same-origin `/_vercel/` path (excluded from the SPA-fallback rewrite). If any of those move off-origin (a CDN font host, an off-platform analytics beacon), the CSP must be widened to match or they break silently. `App.tsx` also mounts Vercel `<Analytics>` + `<SpeedInsights>`; analytics URLs pass through `maskAnalyticsUrl()` (`frontend/src/utils.ts`) first, which strips query/hash and collapses `/events/:id` to `/events/[id]` so no event id or token reaches the analytics vendor. Any new dynamic route added to the app must be masked the same way.
- **Keepalive — cron-job.org**: Render free tier sleeps after 15 min idle, which would halt APScheduler. A cron-job.org job pings `https://event-radar-api.onrender.com/internal/tick` every 10 minutes with the `X-Internal-Token` header (same value as Render's `INTERNAL_TOKEN`). GitHub Actions cron was tried and dropped — its schedule is too imprecise for a keepalive cadence.

## Admin Endpoints

`/admin/*` uses HTTP Basic auth (`ADMIN_USERNAME`, default `"admin"`, + `ADMIN_PASSWORD` env vars), checked with `secrets.compare_digest`. Failed auth attempts log a warning (audit trail). With no password set, any credentials are accepted (logs a warning) **only** when both `APP_ENV=development` and `ALLOW_INSECURE_DEV=true` (`app/config.py`) — see `docs/security.md`'s `require_configured_secret` double gate for the full rationale (the same double gate protects the inbound webhook and `/internal/tick`). Otherwise the password is required — unset = 503. `app/main.py`'s lifespan also logs an ERROR if `APP_ENV=development` but `DATABASE_URL` resolves to a non-local host (`DEV_DB_LOCAL_HOSTS`), flagging exactly that misconfiguration. `ENABLE_SCHEDULER=false` (`app/config.py`) disables the embedded scheduler via `app/main.py::_start_scheduler()`, but only when `APP_ENV=development` — ignored elsewhere — and it's absent from `render.yaml`, so production always defaults to on. Every `/admin/*` route is also rate-limited (`RATE_LIMIT_ADMIN`, see `docs/security.md`).

List endpoints that can grow unbounded (e.g. `/admin/dedup/groups`) are paginated via `limit`/`offset` query params with caps in `app/constants.py` (`ADMIN_*_PAGE_SIZE`, `ADMIN_*_MAX_PAGE_SIZE`). Pagination is by logical unit (dedup group, not row) so a single noisy cluster cannot dominate a page. Add the same pattern to any new admin list endpoint.

Manual pipeline triggers: `POST /admin/dedup`, `POST /admin/classify`, `POST /admin/publish`, `POST /admin/geocode`, `POST /admin/refetch` run the corresponding scheduled job synchronously (dedup/classify use the drain-now variant, see `docs/pipeline.md`'s Backlog drain) for ad-hoc operation outside the cron cadence. `POST /admin/geocode` and `POST /admin/refetch` run standalone (`geocode_pending_job` / `refetch_event_details_job`) — neither is part of `POST /admin/pipeline/run`. Run `/admin/refetch` before a manual `/admin/geocode` if you want coords NULLed by an address change re-resolved in the same operation. `POST /admin/cleanup` runs `cleanup_stale_data` (see Data Retention & Cleanup below) standalone, outside `/admin/pipeline/run`; defaults to `dry_run=true`. The remaining routes are `POST /admin/ingest` (runs ingestion for every enabled source) + `POST /admin/ingest/{slug}` (single source), `POST /admin/build-feeds`, `POST /admin/send-digests`, `GET /admin/dedup/groups`, `GET /admin/stats`, and the organizer submission review queue — `GET /admin/submissions` (paginated, excludes cancelled), `POST /admin/submissions/{event_id}/retract`, `POST /admin/submissions/{event_id}/approve` (see `docs/organizer-portal.md`). Every synchronous job trigger goes through the shared `run_admin_job()` helper (`routers/utils.py`) — use it for any new one rather than calling the job directly. **Exception:** `POST /admin/pipeline/run` (`admin_pipeline_run`) hand-rolls its own per-stage `try`/`except` instead, because it needs stop-on-first-failure semantics with a per-stage result dict — `run_admin_job()`'s single-shot success/500 conversion can't express "run stage N, stop and report which stage failed, but still return the results of stages before it." This is the only endpoint that should bypass the helper for this reason.

## Data Retention & Cleanup

`app/cleanup.py::cleanup_stale_data()` runs weekly (Sun 03:30 Europe/Tallinn, right after organizer sync) and prunes aged rows from satellite/audit tables via a fixed set of bulk `DELETE`s (one per table, no N+1). **`events` rows are never deleted** — only satellite data (auth tokens, audit logs, raw payloads, old feed snapshots, cached scores, never-verified user/organizer account rows) — preserving event history and the `user_event_feedback` indirect-feedback signal indefinitely.

| Table | Retention window (`app/constants.py`) | Notes |
|---|---|---|
| `auth_magic_links` | `MAGIC_LINK_RETENTION_DAYS` (7) | sweeps both expired-unused and long-used rows |
| `organizer_magic_links` | `MAGIC_LINK_RETENTION_DAYS` (7) | mirrors `auth_magic_links` (organizer auth track) |
| `llm_calls` | `LLM_CALLS_RETENTION_DAYS` (90) | also the dedup/classification cache window — a content hash re-seen after 90 days costs one fresh LLM call instead of a cache hit |
| `raw_events` | `RAW_EVENTS_RETENTION_DAYS` (90) | a one-off forensic/backfill script that reads `raw_events.payload` cannot recover a row pruned past this window |
| `ingestion_runs` | `INGESTION_RUNS_RETENTION_DAYS` (90) | |
| `raw_inbound_emails` | `RAW_INBOUND_EMAILS_RETENTION_DAYS` (90) | |
| `daily_feeds` | `DAILY_FEEDS_RETENTION_DAYS` (30) | |
| `user_event_scores` | `USER_EVENT_SCORES_RETENTION_DAYS` (30) | keyed on the underlying event's end date via `event_not_ended_filter` (inverted, evaluated at the retention cutoff), not the score's own `computed_at` |
| `users` (unverified only) | `UNVERIFIED_ACCOUNT_RETENTION_DAYS` (30) | only `email_verified = false` rows with no unused, unexpired magic link — a row `_get_or_create_user` inserts on an unauthenticated `POST /auth/request-link` before the address is proven reachable (see `docs/security.md`'s email verification gate for the full rationale) |
| `organizers` (unverified only) | `UNVERIFIED_ACCOUNT_RETENTION_DAYS` (30) | only rows with no consumed magic link, no unused-unexpired magic link, and no submitted event — mirrors the `users` sweep for the organizer auth track, which has no `email_verified` column of its own |

`POST /admin/cleanup` triggers this on demand — like every other destructive admin/maintenance tool in this codebase, it **defaults to dry-run** (`?dry_run=false` to actually delete).

## Logging

`app/logging_config.py::configure_logging()` is the single logging entry point. It is called at import time in `app/main.py` — deliberately *after* uvicorn configures its own logging, so it runs last and wins. It strips the framework loggers (`uvicorn`, `uvicorn.error`, `uvicorn.access`, `sqlalchemy.engine`) of their own handlers and re-points them at the root logger, so every line (app, uvicorn, SQL echo) shares one timestamped format. `configure_logging()` is idempotent (safe under `--reload` and in tests).

- **Development** — human-readable text to the console **and** a rotating file under `backend/logs/` (sizes/names in the `LOG_*` constants). SQL echo logs at INFO.
- **Production** (`APP_ENV != development`) — JSON-lines (`JsonLogFormatter`) to the console. SQL echo drops to WARNING. If `LOG_SHIP_URL` is set, logs are also shipped to an HTTP drain (e.g. Axiom) via a `QueueHandler` → background `QueueListener` thread so the request path never blocks; auth is `Bearer LOG_SHIP_TOKEN`. An `_AccessPathFilter` drops successful (`< 400`) uvicorn access lines for the paths in `LOG_SHIP_SUPPRESS_ACCESS_PATHS` (`/health`) before shipping, so the platform health probe doesn't dominate the drain; errors on those paths still ship. Each record is POSTed as a single-element JSON array (`[{…}]`) because Axiom's ingest endpoint expects an array of events, not a bare object — also accepted by other JSON drains.
- **Never crash the app** — log-shipping network failures are swallowed (`handleError`); `shutdown_log_shipping()` stops the listener thread on app shutdown (wired into the lifespan in `main.py`).
- All logging literals (formats, date format, file size/backup count, queue size, timeouts) live in `app/constants.py` (`LOG_*`); `LOG_LEVEL` / `LOG_SHIP_URL` / `LOG_SHIP_TOKEN` are settings in `app/config.py`.
- **Monitoring spec** — `docs/observability.md` is the version-controlled source of truth for the Axiom side: the shipped log-record shape, the `LOG_EVENT_*` `event` taxonomy, and the APL queries behind each hand-created Axiom monitor (Axiom's free tier has no monitors-as-code, so the doc stands in for it). Update it whenever a `LOG_EVENT_*` constant or a shipped log field is added or renamed.

## Maintenance Scripts

`backend/scripts/` holds one-off operational scripts run manually from `backend/` with the venv active (they add `backend/` to `sys.path`, so `from app.*` resolves regardless of CWD). **Naming convention:** an `_`-prefixed filename means a throwaway, machine-local one-off — `.gitignore` excludes `backend/scripts/_*`, so those are never committed. Give a script a plain name only when it is meant to live in version control; otherwise prefix it with `_` (a truly local working copy may exist there without appearing in this list).

- **`reset_events.py`** — wipes all event/pipeline data and resets IDs to 1. `TRUNCATE ... RESTART IDENTITY CASCADE` over `events`, `raw_events`, `event_sources`, `event_classifications`, `user_event_feedback`, `user_event_scores`, `daily_feeds`, `ingestion_runs`, `llm_calls`, `raw_inbound_emails`, then sets `sources.last_run_at`/`last_status` back to `NULL` so ingestion re-fetches from scratch. **`users`, `personas`, and `sources` rows are preserved** (only the sources' run state is cleared). Dry run by default (prints the masked `DATABASE_URL` + per-table BEFORE counts); pass `--yes` to truncate. Verifies all targets are zero AFTER and warns on any nonzero. The truncate cannot be undone — intended for resetting a dev/staging DB or clearing bad ingested data before soft launch, not routine use.

```bash
cd backend                              # venv active
python scripts/reset_events.py          # dry run: target DB + row counts
python scripts/reset_events.py --yes    # actually truncate (irreversible)
```
